# Feature Specification: Resume, Halt Recovery, and Re-Grounding for the Work-Item Driver

Extends the work-item driver so a run survives a stopped session and a halt: the driver records its per-item progress durably on the branch, offers the operator an in-session recovery menu instead of a dead-end halt, and re-establishes its own context through one named re-grounding routine whenever it resumes.

## Outcome

A run of the work-item driver is no longer single-pass and disposable. Its progress is recorded durably on the run's branch as the items complete, so re-invoking the driver on the same work-items file continues the run from the first unfinished item rather than refusing the branch or rebuilding committed work ([D2](artifacts/decision-log.md#d2-committed-greppable-per-item-ledger), [D10](artifacts/decision-log.md#d10-fresh-vs-resume-detection)). When the driver reaches a state it cannot settle unattended, it presents the same five-part halt frame it presents today — with its final "what to do next" part now an in-session recovery menu — so the operator can fix the issue and have the driver re-attempt the item, grant more automated fix rounds, skip the item, or stop the run, without leaving the session and without losing the items already committed ([D5](artifacts/decision-log.md#d5-in-session-recovery-menu)). Every point at which the driver re-enters an in-progress run — after a foreground hand-off, after a human review, on a cross-session resume, and after a recovery-menu re-attempt — runs one shared re-grounding routine that re-reads the durable progress record and the working tree before it acts ([D9](artifacts/decision-log.md#d9-re-grounding-as-one-shared-routine)).

This reopens two behaviors the driver deliberately deferred: cross-session resume and a defined re-grounding routine ([D1](artifacts/decision-log.md#d1-feature-scope-and-reopened-deferrals)). It does not reopen automatic mid-run compaction survival, which stays out of scope: recovery is always driven by the operator re-invoking or steering, never by an automatic trigger ([D4](artifacts/decision-log.md#d4-re-invocation-only-recovery)).

## Actors and Triggers

- **Actors**
  - **Operator:** the engineer who invoked the driver on a trusted work-items file, and who now may stop and resume the run across sessions, or steer a halted item back onto its feet through the recovery menu.
  - **The driver:** the orchestrating loop that builds, verifies, reviews, fixes, and commits each item. It gains the responsibility of recording its progress durably, detecting a resumable run at invocation, re-grounding itself, and presenting the recovery menu. Exactly one live driver operates on a checkout at a time ([D17](artifacts/decision-log.md#d17-single-writer-per-checkout)).
  - **Build and review sub-agents:** unchanged from today; the driver dispatches them per item and per fix round.
- **Triggers**
  - The operator invokes the driver on a work-items file. The driver resolves the target branch, then reads that branch's history for this run's progress record. If the record is present, the invocation is a **resume**; if the branch carries no prior run commits, it is a **fresh run**; if the branch carries commits but no run record for this file, the run is refused rather than committed onto a foreign base ([D10](artifacts/decision-log.md#d10-fresh-vs-resume-detection)).
  - During a live run, the driver reaches a state it cannot settle unattended, which raises the recovery menu ([D5](artifacts/decision-log.md#d5-in-session-recovery-menu)).
- **Preconditions**
  - A resume requires the run's branch, carrying the run's durable progress record, to be present in the checkout. The record travels with the branch, so a resume works in a fresh clone of the branch; a checkout that lacks the branch or the record cannot resume ([D2](artifacts/decision-log.md#d2-committed-greppable-per-item-ledger), [T1](artifacts/feature-technical-notes.md#t1-greppable-per-item-ledger-markers-in-commit-history)).
  - A fresh run keeps today's start preconditions unchanged: a clean working tree apart from the run's own planning artifacts, and a green suite where the project defines one.
  - On a resume, the one expected exception to the clean-tree precondition is the uncommitted work of the item that was in progress when the run stopped; the driver inspects that work rather than refusing the run for it ([D12](artifacts/decision-log.md#d12-resume-preconditions)).
  - One live driver per checkout. Two drivers sharing one working tree would interleave commits and corrupt the run; concurrent invocation on the same checkout is unsupported ([D17](artifacts/decision-log.md#d17-single-writer-per-checkout)).

## Primary Flow

This flow describes the resume-aware invocation and the progress-recording and recovery behavior layered over the existing per-item loop. The build, verify, review, fix, and commit stages inside the loop are unchanged except where noted.

1. **Classify the invocation.** On invocation, the driver resolves the target branch (from the branch input or the folder-derived default), then reads that branch's history for this run's durable progress record before anything else. If a record for this work-items file is present, it enters the resume flow (see "Resuming a partially complete run"). If the branch carries no prior run commits, it proceeds as a fresh run. If the branch carries commits but no record for this file, it refuses rather than commit a run onto a foreign base ([D10](artifacts/decision-log.md#d10-fresh-vs-resume-detection)). A run's identity is keyed on the work-items file's location, so a resume matches the same file the record was written for ([D10](artifacts/decision-log.md#d10-fresh-vs-resume-detection), [T1](artifacts/feature-technical-notes.md#t1-greppable-per-item-ledger-markers-in-commit-history)).
2. **Set up a fresh run.** After the operator confirms the plan, the driver creates the branch and commits the planning artifacts as today, and additionally records the run's opening progress entry to the branch, carrying the run's effective configuration (the gate threshold, fix-loop cap, build/fix model, branch, and verification configuration) and the work-items file it is driving. This opening entry is what a later invocation reads to recognize the run and restore its configuration rather than re-deriving it ([D2](artifacts/decision-log.md#d2-committed-greppable-per-item-ledger), [D13](artifacts/decision-log.md#d13-durable-ledger-content-vs-ephemeral-state)). The run's progress is recorded durably in the branch history, separate from the per-item code commits, and conforms to the repo's commit convention so the project's commit hooks accept it ([T1](artifacts/feature-technical-notes.md#t1-greppable-per-item-ledger-markers-in-commit-history), [D20](artifacts/decision-log.md#d20-marker-commits-conform-to-convention-and-fail-as-a-distinct-class)).
3. **Per item, bracket the work durably.** For each item in run order the driver records a start-of-item entry to the branch before any build, then runs the existing per-item loop (decide, build, verify, review, fix). The start-of-item entry is the point the item's changed-file set is measured against, replacing today's in-session baseline reference so the baseline survives a stopped session ([D2](artifacts/decision-log.md#d2-committed-greppable-per-item-ledger), [D3](artifacts/decision-log.md#d3-per-item-resume-granularity)). If the item requires a pre-work decision, the driver captures it within the session and passes it to the build; the decision is not recorded durably, so a resume of an item that still needs one re-asks it ([D13](artifacts/decision-log.md#d13-durable-ledger-content-vs-ephemeral-state)).
4. **The inner loop is not recorded per transition.** The build, verify, review, and fix transitions inside the loop are not committed; only the item's own code commit and the item-boundary entries reach history. Resume granularity is therefore per item, not per inner phase: a run that stopped mid-item resumes at that item, not at an exact inner step, keeping the branch history free of transitional commits with no code between them ([D3](artifacts/decision-log.md#d3-per-item-resume-granularity)).
5. **On the item clearing, record it done — and guard the commit boundary.** Before it commits, the driver re-reads its own instructions and reloads them if they were truncated, so an item is never committed and marked done by a driver running on partial instructions ([D18](artifacts/decision-log.md#d18-commit-boundary-self-check)). When the item clears its gate and the driver commits the item's code as today, it then records a done entry to the branch referencing the item's code commit ([D2](artifacts/decision-log.md#d2-committed-greppable-per-item-ledger), [D13](artifacts/decision-log.md#d13-durable-ledger-content-vs-ephemeral-state)). The driver advances to the next item.
6. **On a state it cannot settle, recover in session.** When the driver reaches a state it cannot settle unattended — an untrustworthy build report, verification still failing after the fix cap, an untrustworthy review verdict, a review escalation needing a human decision, or a rejected commit — it presents the five-part halt frame, whose "what to do next" part is the recovery menu, rather than ending the run ([D5](artifacts/decision-log.md#d5-in-session-recovery-menu)). See "A run reaches a state it cannot settle".
7. **On completion, summarize and leave the record in place.** When every item is done or skipped, the driver reports the completion summary as today. The run's progress record stays in the branch history; the summary notes it is present, that a re-invocation on the same file would recognize the completed run, and that the operator may strip the record by hand if they want clean per-item history, at the cost of the branch's resumability ([D8](artifacts/decision-log.md#d8-ledger-markers-left-in-history)).

## Alternate Flows and States

### Resuming a partially complete run

- **Entry condition:** the operator invokes the driver on a work-items file whose run's branch already carries this run's durable progress record ([D10](artifacts/decision-log.md#d10-fresh-vs-resume-detection)).
- **Sequence:** the driver runs its re-grounding routine ([D9](artifacts/decision-log.md#d9-re-grounding-as-one-shared-routine)): it re-reads the durable record to reconstruct which items are done, which is in progress, and which were skipped, and re-derives the dependency graph from the current work-items file so a dependent of a skipped item is not picked up ([D11](artifacts/decision-log.md#d11-ledger-and-history-integrity-safety)); it re-reads the working tree; and it re-reads its own instructions. It restores the run configuration from the opening entry rather than re-deriving or re-asking it, so the resumed items are gated against the same criteria as the committed ones; if the operator supplied a configuration flag that conflicts with the restored value, the driver names it as ignored rather than silently overriding it ([D13](artifacts/decision-log.md#d13-durable-ledger-content-vs-ephemeral-state)). It shows a resume summary — done, skipped, in progress, remaining, and the restored configuration and branch — instead of replaying the full fresh-run plan preview. It then **announces the concrete next action** (the specific next item, the phase it will resume at, and the disposition of any in-progress item) and **waits for the operator's go-ahead before the first build or any discard** ([D19](artifacts/decision-log.md#d19-cross-session-resume-go-ahead)). Before continuing past a clean between-items point, it re-establishes the verification baseline; a baseline that is now red (a done item that regressed from between-session drift) is surfaced as a distinct condition, not silently adopted ([D12](artifacts/decision-log.md#d12-resume-preconditions)).
- **Exit:** on the go-ahead, the run proceeds from the first item that is neither done, skipped, nor blocked by a skipped dependency; done and skipped items are not rebuilt. A record in which every item is done is reported as an already-complete run, and the driver starts nothing ([D11](artifacts/decision-log.md#d11-ledger-and-history-integrity-safety)).

### Resuming an in-progress item

- **Entry condition:** on a resume, one item has a start-of-item entry but no done entry ([D3](artifacts/decision-log.md#d3-per-item-resume-granularity)).
- **Sequence:** the driver first checks whether the item's code already landed in history — a code commit exists in the item's start-of-item-to-HEAD range that cleared its gate. If it did, the driver reconciles forward: it records the missing done entry and advances, rather than rebuilding and double-committing an item that was committed but not yet marked done ([D16](artifacts/decision-log.md#d16-committed-but-unmarked-forward-reconcile)). Otherwise it inspects the in-progress work against the start-of-item entry and decides its state by re-running verification as the completeness signal ([D6](artifacts/decision-log.md#d6-in-progress-item-inspect-and-decide)): work whose verification passes and whose changed-file set is the item's own is kept and re-reviewed; an empty or partial tree, or verification that fails, is treated as partial and rebuilt from the start-of-item entry; an item that still needs a pre-work decision re-asks it. The driver does not pre-validate the item's commit range: a commit the operator made, or history they rewrote, on the branch between sessions is not caught here; its files fall in the item's changed-file set and surface through the item's re-review as a scope finding the operator resolves at the recovery menu ([D11](artifacts/decision-log.md#d11-ledger-and-history-integrity-safety), Deferred (YAGNI)). Any marker or record state the driver cannot positively classify as safe is still surfaced and asked rather than acted on ([D11](artifacts/decision-log.md#d11-ledger-and-history-integrity-safety)). A foreground item's hand-built work is never discarded without the operator's explicit agreement ([D6](artifacts/decision-log.md#d6-in-progress-item-inspect-and-decide)). The driver completes this inspection and any discard before it re-establishes the verification baseline, so leftover partial work cannot redden the baseline and be misread as a regression ([D12](artifacts/decision-log.md#d12-resume-preconditions)).
- **Exit:** the in-progress item continues at the phase its inspected state warrants (advance, re-review, rebuild, or re-decide), or the driver surfaces and asks; the run proceeds only after the go-ahead ([D19](artifacts/decision-log.md#d19-cross-session-resume-go-ahead)).

### Resuming an interrupted foreground item

- **Entry condition:** the item in progress at resume was a foreground or human-driven item whose interactive state is not part of the durable record ([D6](artifacts/decision-log.md#d6-in-progress-item-inspect-and-decide), [D13](artifacts/decision-log.md#d13-durable-ledger-content-vs-ephemeral-state)).
- **Sequence:** the durable record cannot reconstruct an interview or a hand-build in flight, so the driver surfaces the interrupted item — showing its commits and uncommitted diff since its start-of-item entry as recognition support rather than asking the operator to recall whether the work was finished ([T2](artifacts/feature-technical-notes.md#t2-no-interleaved-ledger-commits-during-foreground-items)) — and offers to re-drive it, or, if the operator confirms the shown work is complete, to treat it as confirmed and resume at verify, keeping the item in progress rather than silently restarting or dropping it. During a foreground item the driver does not interleave its own progress entries with the commits the foreground skill makes, so the item's start-of-item-to-done range cleanly brackets that skill's own commits and the resume can tell the item's work from the driver's bookkeeping ([T2](artifacts/feature-technical-notes.md#t2-no-interleaved-ledger-commits-during-foreground-items)).
- **Exit:** the foreground item resumes at verify or is re-driven, per the operator's confirmation.

### A run reaches a state it cannot settle

- **Entry condition:** during a live run the driver reaches a state it cannot settle unattended (as in Primary Flow step 6) ([D5](artifacts/decision-log.md#d5-in-session-recovery-menu)).
- **Sequence:** the driver presents the five-part halt frame — status line, one-sentence reason, tree-state disclosure, supporting evidence, then the recovery menu as the "what to do next" part (the frame's fifth part now points at resumption, not at abandoning the branch) ([D5](artifacts/decision-log.md#d5-in-session-recovery-menu)). The menu offers, filtered to what the halting state allows, with each option's consequence stated on its label:
  - **Fix in place, then re-attempt** — the operator fixes the issue and tells the driver to re-attempt the item (see "Operator fixes an issue and re-attempts") ([D5](artifacts/decision-log.md#d5-in-session-recovery-menu), [D7](artifacts/decision-log.md#d7-re-attempt-detection-first-and-non-destructive)).
  - **Run more automated fix rounds** — the operator grants a further, stated number of automated fix rounds for this item, re-entering the fix loop without editing anything by hand; the driver halts again if they do not clear the gate; offered when the halt was a fix-cap-exceeded state. Rounds granted here are within-session and do not survive a stop ([D5](artifacts/decision-log.md#d5-in-session-recovery-menu), [D13](artifacts/decision-log.md#d13-durable-ledger-content-vs-ephemeral-state)).
  - **Skip this item, continue** — the driver names the dependents the skip will strand before the operator commits to it; on skip, it returns the working tree to the last clean committed baseline (inspecting and confirming before discarding, never discarding an interactive item's hand-built work) so the skipped item's files do not contaminate the next item, records a skip entry to the branch, and continues to the next item whose dependencies are met ([D5](artifacts/decision-log.md#d5-in-session-recovery-menu), [D15](artifacts/decision-log.md#d15-skip-returns-the-tree-to-a-clean-baseline), [D13](artifacts/decision-log.md#d13-durable-ledger-content-vs-ephemeral-state)).
  - **Stop the run (resumable)** — always present; the driver stops cleanly, leaving the completed items committed and the run resumable by a later invocation on the same file.
- **Exit:** the driver re-attempts, grants fix rounds, skips, or stops per the operator's choice, and either continues the run or ends it resumably. The recovery menu offers no gate override, upstream repair, or triage pass; those stay out of scope ([D5](artifacts/decision-log.md#d5-in-session-recovery-menu)).

### Operator fixes an issue and re-attempts

- **Entry condition:** at the recovery menu (in session), or by editing the tree before a re-invocation resume, the operator has addressed the halting issue and wants the driver to re-attempt the item ([D7](artifacts/decision-log.md#d7-re-attempt-detection-first-and-non-destructive)).
- **Sequence:** the driver shows what it detects changed since the item's start-of-item entry (the working tree, and the item's text if the item itself was edited) and offers two non-destructive paths, stating what each does to the operator's edits ([D7](artifacts/decision-log.md#d7-re-attempt-detection-first-and-non-destructive)):
  - **Re-check the current tree as-is** — re-verify and re-review the tree without dispatching a build. This covers a hand-edited code fix and a "nothing in the repo changed" fix (an environment, dependency, or flake fix), and never rebuilds away the operator's edits.
  - **Build further toward the item** — dispatch a build sub-agent that continues from the current tree (never resetting the operator's edits) with the changed item and the residual findings as context, then verify and review. This covers a changed item or spec, and the case where the operator changed both the code and the item, because the build extends the operator's edits rather than replacing them.
  A manual fix does not consume an automated fix-round; the fix-round budget bounds only the driver's own automated fix loop ([D7](artifacts/decision-log.md#d7-re-attempt-detection-first-and-non-destructive)).
- **Exit:** the re-attempted item re-enters the gate. If it clears, the driver commits it and records it done; if it does not, the driver returns to the recovery menu.

### Ledger and history disagree on resume

- **Entry condition:** on a resume the durable record and the current state disagree, or the driver cannot positively classify the resume state as safe ([D11](artifacts/decision-log.md#d11-ledger-and-history-integrity-safety)).
- **Sequence:** the driver never proceeds on a guessed base or reports an item done whose commit is gone. It surfaces the specific divergence with the unmatched entries named, adds a one-line plain-language cause and meaning (for example, "the commit recorded as finishing this item is no longer in this branch's history — a rebase, reset, or history cleanup likely rewrote it"), and offers one uniform, consequence-labeled option set with the safe option (inspect or abort to reconcile) marked: abort to reconcile by hand; restart the run (which supersedes the prior record so a later resume reads only the new run); or, only where the driver can show it is safe, proceed from the first unmatched item. "Proceed from first unmatched" is withheld when the resumption point would fall before a dependency (for example, an edge the operator added between runs) or when the record is internally inconsistent; those surface and ask instead ([D11](artifacts/decision-log.md#d11-ledger-and-history-integrity-safety)). The enumerated divergences — a missing branch or absent prior commits, a done entry's commit that no longer resolves, an edited or renumbered file, a wholly different file on a branch carrying another run's record, a partially-stripped record — are examples of this default-deny rule, not a closed list ([D11](artifacts/decision-log.md#d11-ledger-and-history-integrity-safety)).
- **Exit:** the operator chooses; the driver resumes, restarts, or aborts, but never silently rebuilds a committed item, continues on the wrong base, or reports done an item whose body was rebuilt away.

## Edge Cases and Failure Modes

| Condition | Required Behavior |
|-----------|-------------------|
| The operator re-invokes on a branch that carries this run's durable record | The driver treats it as a resume: it re-grounds, shows the resume summary, announces the next action, and waits for a go-ahead before mutating, rather than refusing the branch (today's behavior) or rebuilding committed items ([D10](artifacts/decision-log.md#d10-fresh-vs-resume-detection), [D19](artifacts/decision-log.md#d19-cross-session-resume-go-ahead)). |
| The target branch carries commits but no run record for this file | The driver refuses rather than committing a run onto a foreign base, preserving today's guardrail against the wrong base ([D10](artifacts/decision-log.md#d10-fresh-vs-resume-detection)). |
| The item's code committed but its done entry did not (a killed session, a rejected bookkeeping commit) | On resume the tree is clean and the item has a start entry but no done entry; the driver detects the item's code already landed and cleared its gate, records the missing done entry, and advances, rather than rebuilding and double-committing ([D16](artifacts/decision-log.md#d16-committed-but-unmarked-forward-reconcile)). |
| The in-progress item's uncommitted work is in the tree at resume | The driver treats that work as the one allowed exception to the clean-tree precondition, re-runs verification to classify it, and keeps-and-re-reviews, discards-and-rebuilds, or surfaces-and-asks, rather than refusing the resume for a dirty tree ([D6](artifacts/decision-log.md#d6-in-progress-item-inspect-and-decide), [D12](artifacts/decision-log.md#d12-resume-preconditions)). |
| The driver cannot positively classify the resume state as safe | It surfaces what it found and asks the operator rather than proceeding on the markers; the named divergences are examples of this default-deny rule, not the whole of it ([D11](artifacts/decision-log.md#d11-ledger-and-history-integrity-safety)). |
| An out-of-band rebase, or a foreign operator commit on the branch between sessions, lands in the in-progress item's start-to-HEAD range | The driver does not pre-validate the range; the extra files fall in the item's changed-file set, and the item's re-review flags them as a scope finding — gating when the reach is substantial (a reordered item's work, an unrelated feature), so the recovery menu then lets the operator drop the commit and re-attempt, skip, or stop. A below-threshold one-liner does not gate and may ride into the commit — an accepted residual of deferring a dedicated range check ([D11](artifacts/decision-log.md#d11-ledger-and-history-integrity-safety); Deferred (YAGNI)). |
| The operator skips a halting item that has uncommitted work in the tree | The driver returns the tree to the last clean committed baseline before the next item (inspecting and confirming, never discarding an interactive item's hand-built work), so the skipped item's files do not contaminate the next item's commit ([D15](artifacts/decision-log.md#d15-skip-returns-the-tree-to-a-clean-baseline)). |
| The operator skips a halting item, and later items depend on it | The driver names the stranded dependents before the skip is chosen, records the skip durably, re-derives the dependency graph on resume, and starts no item that depends on the skipped one ([D5](artifacts/decision-log.md#d5-in-session-recovery-menu), [D11](artifacts/decision-log.md#d11-ledger-and-history-integrity-safety)). |
| The re-established verification baseline is red on resume (a done item regressed from between-session drift) | The driver surfaces the red baseline as a distinct condition — naming the failing tests and noting they were green when the done items committed — with a stop-or-abort choice, rather than adopting a red floor against which new regressions would pass ([D12](artifacts/decision-log.md#d12-resume-preconditions)). |
| The operator changed the code by hand, changed the item, changed both, or changed neither, then asks to re-attempt | The driver shows what it detected changed and offers re-check-as-is (no build) or build-further-from-the-current-tree (never resetting edits); the code-only, spec-only, both, and environment-fix cases all have a non-destructive path, and the manual fix does not consume an automated fix-round ([D7](artifacts/decision-log.md#d7-re-attempt-detection-first-and-non-destructive)). |
| The operator edits an already-done item's body while stopped, then resumes | The item is trusted done by its identifier; the driver does not detect the body change and does not rebuild it. To rebuild an already-done item the operator restarts the run; the completion and resume messaging note that done items are trusted by identifier ([D21](artifacts/decision-log.md#d21-done-items-trusted-by-identifier)). |
| A done entry's referenced commit no longer resolves at resume | The driver does not accept the item as done on the entry alone; it surfaces the unresolved reference with its plain-language cause and asks the operator to reconcile ([D11](artifacts/decision-log.md#d11-ledger-and-history-integrity-safety)). |
| The recorded branch is missing, or the checkout lacks the run's prior commits | The driver surfaces that and asks rather than continuing on the wrong base ([D11](artifacts/decision-log.md#d11-ledger-and-history-integrity-safety)). |
| The work-items file was edited or renumbered between runs | The driver surfaces the mismatch with the unmatched entries and offers the uniform option set (abort, restart, or proceed-from-first-unmatched only where safe), each labeled with its consequence; a resumption point that would fall before a newly-added dependency withholds the proceed option ([D11](artifacts/decision-log.md#d11-ledger-and-history-integrity-safety)). |
| A wholly different work-items file is driven against a branch carrying another run's record | Folded into the uniform divergence handling: the driver surfaces it and offers restart (superseding the prior record) or abort, rather than building the new file's items atop the old run's commits ([D11](artifacts/decision-log.md#d11-ledger-and-history-integrity-safety)). |
| The run's durable record was stripped by hand, then the operator re-invokes | With no record present, the driver classifies the invocation as fresh (or refuses if the branch carries non-record commits); the operator forgoes resumability when they strip the record, as the completion summary warned ([D8](artifacts/decision-log.md#d8-ledger-markers-left-in-history), [D10](artifacts/decision-log.md#d10-fresh-vs-resume-detection)). |
| The opening run entry fails to record (a rejected commit, a lock, a full disk) | The run stops, and because no record was written, a re-invocation starts a fresh run rather than resuming; the driver says so at the failure rather than implying a resume is available ([D13](artifacts/decision-log.md#d13-durable-ledger-content-vs-ephemeral-state)). |
| A later progress entry (start-of-item, done, or skip) fails to record | The driver does not advance and does not discard verified, reviewed work; it surfaces the failure and its remedy and stops resumably (enough prior record exists to resume). A bookkeeping-commit rejection is a distinct class from a code-commit failure and is never routed into the fix loop ([D13](artifacts/decision-log.md#d13-durable-ledger-content-vs-ephemeral-state), [D20](artifacts/decision-log.md#d20-marker-commits-conform-to-convention-and-fail-as-a-distinct-class)). |
| The repo's commit hooks reject the driver's bookkeeping commit (a commit-message-convention gate, a no-empty-commit rule) | The progress record conforms to the repo's commit convention so hooks accept it; if a bookkeeping commit is nonetheless rejected, the driver surfaces it as a marker-write failure (surface-and-stop), and may probe at run-start so a strict-hook repo is caught at plan-confirmation rather than at item 1 ([D20](artifacts/decision-log.md#d20-marker-commits-conform-to-convention-and-fail-as-a-distinct-class)). |
| A mid-run auto-compaction truncates the driver's own instructions but leaves it able to proceed | The commit-boundary self-check re-reads and reloads the driver's instructions before committing and marking an item done, so a truncated driver cannot falsely mark an item done; the blast radius is bounded to the in-progress item, which resume re-inspects ([D18](artifacts/decision-log.md#d18-commit-boundary-self-check)). |
| A mid-run auto-compaction leaves the run unable to proceed | Recovery is re-invocation-driven: the operator re-invokes and the driver re-grounds from the durable record. The driver carries no automatic mid-run compaction trigger ([D4](artifacts/decision-log.md#d4-re-invocation-only-recovery), [D9](artifacts/decision-log.md#d9-re-grounding-as-one-shared-routine)). |
| A second driver is invoked on the same checkout while one is live | Unsupported: one live driver per checkout. The driver does not detect or arbitrate a concurrent invocation; the operator is expected not to run two on one working tree ([D17](artifacts/decision-log.md#d17-single-writer-per-checkout)). |
| The operator picks "stop the run" at the recovery menu | The driver stops cleanly, leaving completed items committed and the run resumable; a later invocation on the same file resumes it ([D5](artifacts/decision-log.md#d5-in-session-recovery-menu), [D10](artifacts/decision-log.md#d10-fresh-vs-resume-detection)). |
| The operator supplies a configuration flag on resume that conflicts with the restored config | The restored config wins (config is immutable within a run); the driver names the conflicting flag as ignored in the resume summary rather than silently overriding it, so the operator knows a config change requires a fresh run ([D13](artifacts/decision-log.md#d13-durable-ledger-content-vs-ephemeral-state)). |
| A run stops mid-fix-loop and is resumed across sessions | The automated fix-round count is within-session, so it re-arms on resume; this is accepted because each resume is operator-initiated and each halt is loud. The resume summary notes how many prior sessions touched the in-progress item, so a repeatedly-stuck item is visible ([D13](artifacts/decision-log.md#d13-durable-ledger-content-vs-ephemeral-state)). |

## User Interactions

Operator-facing copy uses plain terms — "the driver's recorded progress in the branch history," "the recorded run" — rather than the internal "ledger"/"marker" vocabulary this spec uses structurally ([D2](artifacts/decision-log.md#d2-committed-greppable-per-item-ledger)).

- **Affordances:** the operator resumes a run by re-invoking the driver on the same work-items file; no separate resume command is needed, and the fresh-run plan preview and the completion and stop messaging all state that re-invoking the same file resumes rather than restarts ([D10](artifacts/decision-log.md#d10-fresh-vs-resume-detection)). On a cross-session resume the operator gives a go-ahead after seeing the announced next action, before the driver builds or discards ([D19](artifacts/decision-log.md#d19-cross-session-resume-go-ahead)). At a halt the operator chooses from the consequence-labeled recovery menu (fix in place and re-attempt, run a stated number of automated fix rounds, skip this item — with its stranded dependents named first, or stop the run), and when re-attempting after a fix picks re-check-as-is or build-further, each labeled with what it does to their edits ([D5](artifacts/decision-log.md#d5-in-session-recovery-menu), [D7](artifacts/decision-log.md#d7-re-attempt-detection-first-and-non-destructive)). On a resume divergence the operator chooses from the uniform, consequence-labeled option set with the safe option marked ([D11](artifacts/decision-log.md#d11-ledger-and-history-integrity-safety)).
- **Feedback:** on a resume the driver announces the concrete next action (the specific item, the phase it will resume at, and what will happen to any in-progress item) and shows the resume summary (done, skipped, in progress, remaining, restored configuration and branch, and any conflicting flag it is ignoring) rather than the full fresh-run preview ([D9](artifacts/decision-log.md#d9-re-grounding-as-one-shared-routine), [D12](artifacts/decision-log.md#d12-resume-preconditions), [D13](artifacts/decision-log.md#d13-durable-ledger-content-vs-ephemeral-state)). At a halt it shows the five-part frame with the recovery menu as its "what to do next" part, so the actionable choices are the frame's conclusion rather than a stale instruction to abandon the branch ([D5](artifacts/decision-log.md#d5-in-session-recovery-menu)). The completion summary states that the recorded progress remains in history and how to strip it if wanted ([D8](artifacts/decision-log.md#d8-ledger-markers-left-in-history)).
- **Error states:** a resume that cannot proceed safely is surfaced as a reconciliation prompt naming the specific divergence, its plain-language cause, and the uniform option set with the safe option marked, not a silent rebuild ([D11](artifacts/decision-log.md#d11-ledger-and-history-integrity-safety)). A failure to record a progress entry is surfaced with its remedy; an opening-entry failure states that a re-invocation will start fresh, and a later-entry failure stops the run resumably ([D13](artifacts/decision-log.md#d13-durable-ledger-content-vs-ephemeral-state)).

|---------------------|-----------|-------------|-----------------------------------|
| Version-control commit history | outbound and inbound | The driver writes its progress durably to the branch history — an opening entry carrying the run configuration and work-items file, a start-of-item entry per item, done entries referencing each item's code commit, and skip entries — recorded separately from the per-item code commits; and reads that record back on the next invocation to classify and resume the run ([D2](artifacts/decision-log.md#d2-committed-greppable-per-item-ledger), [D13](artifacts/decision-log.md#d13-durable-ledger-content-vs-ephemeral-state)) | The record must travel with the branch and be reconstructable from history alone; recorded separately from code so the item's changed-file set stays clean; never staged into an item's code commit and never counted as a scope finding; never interleaved into a foreground skill's own commit run; and conformant to the repo's commit convention so hooks accept it ([T1](artifacts/feature-technical-notes.md#t1-greppable-per-item-ledger-markers-in-commit-history), [T2](artifacts/feature-technical-notes.md#t2-no-interleaved-ledger-commits-during-foreground-items), [D20](artifacts/decision-log.md#d20-marker-commits-conform-to-convention-and-fail-as-a-distinct-class)) |

## Out of Scope

- **Automatic mid-run compaction survival.** No external trigger re-grounds the driver mid-run without the operator re-invoking or steering; recovery is re-invocation-driven ([D4](artifacts/decision-log.md#d4-re-invocation-only-recovery)).
- **Concurrent drivers on one checkout.** One live driver per checkout; the driver does not lock or arbitrate a second concurrent invocation on the same working tree ([D17](artifacts/decision-log.md#d17-single-writer-per-checkout)).
- **Detecting edits to an already-done item.** A done item is trusted by its identifier; a changed body on an already-done item is not detected or rebuilt ([D21](artifacts/decision-log.md#d21-done-items-trusted-by-identifier)).
- **A richer recovery menu.** Gate override, upstream repair, an on-demand triage pass, and accept-a-flagged-change are not offered; the menu is fix-and-re-attempt, more fix rounds, skip, and stop ([D5](artifacts/decision-log.md#d5-in-session-recovery-menu)).
- **A mid-run clean-stop affordance separate from the recovery menu.** The operator stops through the recovery menu at a halt, or by not re-invoking; a message-driven stop mid-item is not part of this feature.
- **An end-of-run history cleanup flow.** The driver leaves the progress record in history and does not automate stripping it ([D8](artifacts/decision-log.md#d8-ledger-markers-left-in-history)).
- **Producing or hardening the work items, and pushing or opening pull requests.** Unchanged from the driver's existing scope.

## Deferred (YAGNI)

### Automatic mid-run compaction survival via an external trigger

- **Why deferred:** the evidence test is met (auto-compaction can truncate the driver mid-run), but the simpler-version test replaces it: re-invocation reloads the full driver and re-grounds from the durable record, and the commit-boundary self-check ([D18](artifacts/decision-log.md#d18-commit-boundary-self-check)) bounds a truncated driver's blast radius in the meantime. The prior attempt's hook-plus-marker machinery was its heaviest and most inconsistent part ([D4](artifacts/decision-log.md#d4-re-invocation-only-recovery)).
- **Reopen when:** operators run unattended stretches long enough that mid-run auto-compaction routinely strands a run before a natural re-invocation point, and re-invoking is too late to be useful.
- **Source:** user decision (compaction question); prior attempt's re-grounding research; F14.

### Durable persistence of a captured pre-work decision

- **Why deferred:** the durable decision marker only earns its keep when a session stops in the narrow window between a decision being captured and the item's build dispatching; re-asking the decision on resume satisfies the same need, and the operator is present on resume anyway ([D13](artifacts/decision-log.md#d13-durable-ledger-content-vs-ephemeral-state)). Dropping it also removes a marker type and an inspection state.
- **Reopen when:** pre-work decisions are shown to be expensive to re-make, or operators routinely lose a decision to a stop in that window.
- **Source:** user decision (decision-persistence question); F25 (junior-developer, edge-case-explorer).

### Detecting and rebuilding an edited already-done item

- **Why deferred:** the user chose to trust done items by identifier; detecting a body edit would add a per-item body-identity record and a comparison for a case the operator can avoid by restarting the run when they edit already-done items ([D21](artifacts/decision-log.md#d21-done-items-trusted-by-identifier)).
- **Reopen when:** operators routinely edit already-done item bodies mid-run and are surprised by the silent skip, and restarting is too costly.
- **Source:** F22 (edge-case-explorer); user decision (edited-items question).

### A lifetime (cross-session) fix-round cap

- **Why deferred:** the fix-round cap is a within-session bound; a stuck item re-arms it on each operator-initiated resume, and each halt is loud, so the operator-in-the-loop already bounds total churn. A lifetime cap adds a durable counter for no measured need ([D13](artifacts/decision-log.md#d13-durable-ledger-content-vs-ephemeral-state)).
- **Reopen when:** stuck items routinely burn many rounds across resumes before the operator notices, at a cost worth a durable lifetime counter.
- **Source:** F20 (on-call-engineer, junior-developer, edge-case-explorer).

### Pre-validating the in-progress item's commit range on resume

- **Why deferred:** the evidence test is met (an out-of-band rebase or a foreign between-session commit can pollute the item's start-to-HEAD range), but the simpler-version test replaces the dedicated check: the item's re-review already computes its changed-file set from the start-of-item entry and flags files beyond the item's work as a scope finding that gates when the reach is substantial, and the recovery menu gives the operator an exit (drop the commit by hand and re-attempt, skip, or stop). A mid-run history rewrite is low-probability (rebase and squash cleanup land after a run completes), and a general "is this commit foreign" test is not reliably buildable for a foreground item whose interactive skill commits its own work. The cheaper, higher-value integrity checks the range check was bundled with are kept: the committed-but-unmarked forward-reconcile ([D16](artifacts/decision-log.md#d16-committed-but-unmarked-forward-reconcile)) and the done-entry-commit-still-resolves check ([D11](artifacts/decision-log.md#d11-ledger-and-history-integrity-safety)), which guard the far more likely killed-session-between-commit-and-done-marker case ([D11](artifacts/decision-log.md#d11-ledger-and-history-integrity-safety)).
- **Residual accepted:** a below-threshold pollution (a one-liner the review tiers as a Suggestion) after a rare mid-run history rewrite may be folded into the item's commit; the review judged it trivial, and a substantial pollution still gates.
- **Reopen when:** mid-run history rewrites or foreign commits routinely contaminate item commits below the scope-gate threshold, or a cheap structural check (another item's marker inside the range; any commit inside an unattended item's range, since unattended builds never commit) proves worth expressing.
- **Source:** F3 (on-call-engineer, edge-case-explorer); user decision (defer the range-integrity check).

## Open Items

No open question blocks implementation. Every fork the review surfaced was settled — by evidence or by an operator decision — and is recorded in the decision log and reflected in the flows above. Two candidates were weighed during synthesis and are recorded here as deliberate delegations to `plan-implementation`, not unresolved questions:

- **The exact form of the durable progress record** (for example, an empty marker commit versus a committed record file updated with a conventional message), the convention that locates it on resume, and how the changed-file set is derived from the start-of-item entry. Deferred by design to `plan-implementation` ([T1](artifacts/feature-technical-notes.md#t1-greppable-per-item-ledger-markers-in-commit-history)).
  - **Resolves when:** `plan-implementation` selects the record form against the target repo's hook and history constraints.
  - **Blocks implementation:** No. The spec fixes every behavior that depends on the record (it is durable, travels with the branch, is recorded separately from code, and is hook-conformant); only the form is left open, and it is open by design.
- **Whether bookkeeping commits conform to the repo's convention or bypass its hooks.** Settled at the spec level: they conform, and a rejection is surfaced-and-stopped rather than routed into the fix loop ([D20](artifacts/decision-log.md#d20-marker-commits-conform-to-convention-and-fail-as-a-distinct-class)). The conform-versus-bypass mechanism follows from the record form and is a `plan-implementation` choice.
  - **Resolves when:** `plan-implementation` picks the record form.
  - **Blocks implementation:** No. The spec-level behavior is decided; only the mechanism is delegated.
