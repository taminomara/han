# Feature Technical Notes: Resume, Halt Recovery, and Re-Grounding for the Work-Item Driver

These notes capture the load-bearing mechanics behind the durable run-progress record. They are consumed by `plan-implementation` and by a reader who asks "why this mechanic and not another?" Behavioral statements live in [../feature-specification.md](../feature-specification.md).

## T1: Greppable per-item ledger markers in commit history

- **Context:** The spec's Outcome, Primary Flow, and Coordinations commit to a run whose progress survives a stopped session and a fresh clone, reconstructed on the next invocation, with a scope baseline (the start-of-item entry) that survives too. That commitment is correct only because progress is recorded durably in a form that travels, can be located without a stored reference, and can be integrity-checked against a rewritten history. The current driver stores per-item state in a gitignored `.implement-work-items/state.json`, which does not travel and is wiped by `git clean`, so the mechanic behind the new behavior must be named.
- **Technical detail:** Run progress is recorded as distinguishable entries in the branch history, committed separately from the per-item code commits, and located on resume by scanning the branch log (for example, a distinguishing commit-message convention or commit trailer the driver greps) rather than by reading a stored commit hash. The entries to record are: an opening run entry carrying the run configuration and the work-items file's repo-root-relative path (the identity a resume matches on); a start-of-item entry per item (the item's changed-file baseline, replacing today's in-session baseline reference); a done entry per item referencing that item's code commit; and a skip entry. Constraints the marker form must satisfy, each load-bearing for a spec behavior:
  - **Excluded from code:** the entries are never staged into an item's code commit and never counted as a scope finding — today's `.implement-work-items/` exclusion in the stage-by-path commit (SKILL.md Step 3.4) and the scope diff (`references/review-verdict-contract.md`) must be extended to cover the durable record, whatever its form ([D13](decision-log.md#d13-durable-ledger-content-vs-ephemeral-state)).
  - **Hook-conformant:** the entries pass the repo's commit hooks (commit-message-convention gates, no-empty-commit rules), so a bookkeeping commit is not rejected at item 1; this constrains the choice between an empty marker commit (which a no-empty-commit hook rejects and which needs an explicit allowance) and a committed ledger file updated with a conventional message ([D20](decision-log.md#d20-marker-commits-conform-to-convention-and-fail-as-a-distinct-class)).
  - **Done-entry resolution kept; range-pollution pre-check deferred:** because the entries are real commits in history rather than stored hashes, the driver can detect on resume that a done entry's referenced commit still resolves — a rewrite that drops it is caught instead of silently wrong — which the done-marker check and the forward-reconcile rely on ([D11](decision-log.md#d11-ledger-and-history-integrity-safety), [D16](decision-log.md#d16-committed-but-unmarked-forward-reconcile)). The stronger check, that the start-of-item-to-HEAD range contains only the item's work, is deferred as YAGNI (spec Deferred (YAGNI)); a foreign or reordered commit surfaces instead through the item's re-review scope check. The marker-in-history form keeps that stronger check cheaply expressible if reopened (another item's entry inside the range, or — since an unattended build never commits — any commit inside an unattended item's range).
  `plan-implementation` owns the exact marker form (empty marker commit vs. a committed ledger file updated with a trailer), the grep convention, and how the changed-file set is computed from the start-of-item entry.

## T2: No interleaved ledger commits during foreground items

- **Context:** The spec commits to resuming a foreground (HITL) item whose interactive skill made its own commits, reading those commits as the item's work and showing them to the operator as recognition support. That is correct only if the driver's own progress entries do not land in the middle of the foreground skill's commit sequence, which would scramble the item's start-to-done range and confuse the changed-file baseline.
- **Technical detail:** For a foreground item, the driver records the start-of-item entry before handing control to the interactive skill, does not record any progress entry while that skill is committing its own work, and records the done entry only after the operator confirms and the driver's verify/review/fix complete. The item's start-of-item-to-done range then cleanly brackets the foreground skill's commits plus any fix commits, so a resume's changed-file inspection ([D6](decision-log.md#d6-in-progress-item-inspect-and-decide)) and the operator-facing recognition diff see the item's real work and not an interleaved bookkeeping commit. This is the operator's constraint "instruct the orchestrator not to commit while running HITL items," interpreted as not interleaving ledger commits into the foreground skill's own commit run.
