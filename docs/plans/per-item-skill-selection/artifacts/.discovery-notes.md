# Implementation Discovery Notes: Per-Item Skill Selection

Single source of truth for project context. Specialists read this first and do not re-grep for what is here.

## Tech stack / repo nature

- **Not an application codebase.** Han is a Claude Code plugin suite; "implementation" means editing **skill definitions** (`SKILL.md` markdown with YAML frontmatter) plus their `references/`, `scripts/`, and long-form docs. No compiler, no app runtime.
- **No automated test suite or CI.** No `package.json`, `Makefile`, `justfile`, or `.github/workflows/`. Verification is review-based: coherent skill prose, resolvable references, consistent format invariants, and updated long-form docs. The PR checklist and authoring rules are the gate (`CONTRIBUTING.md`; `han-plugin-builder/skills/guidance/`).
- **Authoring conventions:** `CONTRIBUTING.md` (which plugin owns what; docs follow `docs/templates/skill-long-form-template.md`; YAGNI applies to docs). Skill/agent authoring rules live in `han-plugin-builder/skills/guidance/references/`.

## The two skills this feature changes

- **Producer — `plan-work-items`** (`han-planning/skills/plan-work-items/`):
  - `SKILL.md` — Step 1 (locate plan), Step 5 (project-manager drafting brief: today classifies AFK/HITL, derives expected-paths), Step 6 (assign W-N ids), Step 7 (print breakdown), Step 8 (write file + closing recommendation). Operating Principles ("runs autonomously end to end", "never gate on approval"), Rules ("source plan is read-only input").
  - `references/work-item-template.md` — the per-item schema. **Currently has `**Type.** AFK or HITL. Required.` (line 36) and `**Expected paths.**` (line 38).** This is where the field-set change lands.
  - `references/work-items-file-format.md` — title/intro/preamble/ordering.
  - `references/reference-artifact-inventory.md` — include/exclude list for artifacts.
- **Driver — `implement-work-items`** (`han-coding/skills/implement-work-items/`):
  - `SKILL.md` — Step 1.7 (validate: "Every item carries **Expected paths.** and **Type.**"; "All AFK. No item is typed HITL"), Step 2.1 (preview "each named with its build skill (`han-coding:tdd`)"), Step 3.1 (build: "instructing it to run `han-coding:tdd`"), Step 3.3 (review: "run `han-coding:code-review`"), Step 3.4 (fix round dispatches `tdd`), Step 2.2 (state file `.implement-work-items/state.md` records run config).
  - `references/build-report-contract.md` — the `tdd` build-report contract (test-failure-then-pass evidence).
  - `references/review-verdict-contract.md` — the `code-review` verdict contract.
  - `scripts/detect-driver-context.sh` — git/manifest detection (does NOT touch Type; no change expected).

## Consumers of the work-item schema (the `Type`-removal ripple)

- **CONTAINED.** `work-items-to-issues` (`han-github`), `work-items-to-jira` (`han-atlassian`), and `work-items-to-linear` (`han-linear`) were grepped for `AFK|HITL|Type|expected.path|implementation.skill`: **zero matches.** They parse only the `## <W-N> — <title>` heading and the `**Depends on.**` line (confirmed in `work-items-to-issues/SKILL.md` Step 3 and its `scripts/`), copying slice bodies verbatim. Removing `Type` and adding new fields does not break them (additive to bodies they pass through). One-line RAID note only.
- **The only real consumer of `Type` is the driver** (`implement-work-items`), which this feature changes anyway.
