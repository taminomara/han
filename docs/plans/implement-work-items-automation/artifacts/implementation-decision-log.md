## Full decisions

### D-1: One `write_and_commit` helper is the atomic paved path for every bookkeeping write

- **Question:** How do the five clerical concerns that D5 moves into the writer — atomic write-then-commit, rollback on a rejected commit, no-op-versus-rejection classification, narrow staging, and post-commit trailer readback — get implemented so every subcommand honors them identically rather than each re-deriving them?
- **Decision:** `write-run-record.sh` grows one internal helper (`write_and_commit`) that every git-touching subcommand (`init`, `log`, `block`) calls, folding this sequence into a single code path: write the record atomically (reusing the existing `write_atomic`), stage only the exact record file (`git add -- "$rec"`), classify nothing-staged as an idempotent no-op via `git diff --cached --quiet -- "$rec"`, commit, read the commit's own trailers back and assert they survived, and on any commit failure roll the record file back to its pre-write content (reusing `write_atomic`) and reset the staged path. A commit that fails with content staged is an unambiguous rejection surfaced as a resumable stop; a commit with nothing staged is a clean no-op.
- **Rationale:** OCE-001/003/007/008 are four separate hazards (torn write on a hook rejection, no-op-versus-rejection ambiguity, a formatter-on-save edit swept into a bookkeeping commit, a trailer-stripping hook silently breaking resume) that all live at the same seam: the moment a record write becomes a commit. Implementing them once, in a helper every subcommand calls, is the simpler version of implementing them per-subcommand: it keeps the write-and-commit atomic "by construction" so a future subcommand added later inherits the guarantees instead of re-earning them. The writer already owns `write_atomic`, so rollback reuses an existing primitive rather than adding one. This is critical-path data-integrity work (a torn or mis-scoped bookkeeping commit silently breaks resume), so it passes the YAGNI evidence test as correctness work, not speculative hardening.
- **Evidence:** R1 on-call-engineer OCE-001, OCE-003, OCE-007, OCE-008 (all Evidenced, plan-level, three of them marked "blocks ship"); `write-run-record.sh:46-53` (`write_atomic`, the reused rollback primitive), `:57-68` (`append_atomic` shows the existing append path each subcommand uses today), `:70-152` (the three subcommands that must each route through the helper); `durable-record-protocol.md` §Commit trailers (the trailers the readback asserts survived), §Commit model ("Bookkeeping commits … stay separate from code commits and are never mixed"); spec D5 ("treating the write and its commit as one atomic action that either lands both or leaves the record file unchanged, staging only the exact record file it wrote"); T1 (resume-critical state must be durable, which a torn commit defeats).
- **Rejected alternatives:**
  - Implement atomicity, no-op classification, narrow staging, and readback inline in each of `init`, `log`, and `block` — rejected because it triplicates four subtle guards and lets a future subcommand omit one silently; the failure that omission causes (a torn or mis-scoped commit) is invisible on the happy path, which is exactly the class OCE-001/007 name.
  - Add a general-purpose commit-orchestration layer with pluggable hooks — rejected as a single-implementation abstraction (YAGNI Rule of Three): there is one caller shape (write the record, commit the record file), so one helper satisfies the same evidence as a framework would.
  - Keep the driver composing the commit in SKILL.md prose and leave the writer git-free — rejected because it is the exact toil D5 and the operator retrospective (point 5, "write-run-record.sh can perform commit maintenance itself") remove, and it leaves the four hazards in prose the driver must re-get-right every item.
- **Specialist owner:** on-call-engineer (resilience seam); test-engineer owns the harness that proves it (test-plan T2/T3/T13).
- **Revisit criterion:** if a bookkeeping write is found that genuinely cannot route through the single helper (a write whose commit shape differs from record-file-only), reopen to decide whether the helper gains a parameter or a second helper is justified.
- **Dissent (if any):** none.
- **Driven by rounds:** R1
- **Dependent decisions:** D-2, D-4
- **Referenced in plan:** Implementation Approach, On-Call Resilience Posture, Decomposition and Sequencing, Definition of Done, Testing Strategy

### D-2: Idempotent record writes and baseline re-emission

- **Question:** When the writer commits a lifecycle entry (a `start-of-item` baseline, or a branch/record setup) and then dies before the driver records the result, how does re-entry avoid appending a duplicate entry or creating a duplicate baseline commit — and how does the run's opening setup stay safe to re-run?
- **Decision:** The writer's setup and lifecycle writes are idempotent. `init` (branch + record-area creation + opening write) is a create-or-switch: if the branch already exists it switches to it rather than failing, and it re-emits the existing opening state rather than committing a second opening (the existing `[ -s "$rec" ]` refuse-to-overwrite guard is preserved and extended to the git side). `log start-of-item` guards on the entry already being present (the `grep -Fxq` existence-check pattern `cmd_block` already uses) and, when the baseline commit already exists, re-emits that existing baseline ref instead of appending a second `start-of-item` line and creating a second baseline commit.
- **Rationale:** OCE-002 is a concrete data-corruption path: `cmd_log` has no duplicate guard today, so a writer that commits `start-of-item` and dies before returning the baseline ref would, on re-entry, append a second `start-of-item` and create a duplicate baseline commit — and the spec's own Edge Cases row ("A tool bookkeeping commit lands, then the tool fails before recording the baseline for the driver … the tool recognizes the already-recorded start rather than appending a duplicate baseline") requires exactly this behavior. OQ-6 (branch-creation idempotency) resolves into the same decision: the setup subcommand is a create-or-switch, matching the SKILL.md 2.2 step-1 behavior the driver does today ("If the branch already exists, switch to it"). The existence-check and re-emit pattern already exist in the writer (`cmd_block:147`), so this extends a present primitive rather than inventing one.
- **Evidence:** R1 on-call-engineer OCE-002 (Evidenced, plan-level, "blocks ship") and OQ-6 resolution (idempotent create-or-switch); `write-run-record.sh:94-132` (`cmd_log`, no duplicate guard today), `:147` (`grep -Fxq` existence check the guard reuses), `:86` (the `[ -s "$rec" ]` opening-overwrite guard to preserve); spec Edge Cases "A tool bookkeeping commit lands, then the tool fails before recording the baseline"; spec Primary Flow 5.1 (baseline recorded and returned); SKILL.md Step 2.2 step 1 ("If the branch already exists, switch to it"); T1 hazard (2) ("the record writer has no duplicate-guard").
- **Rejected alternatives:**
  - Rely on the reader's default-deny to catch a duplicate baseline on resume — rejected because a duplicate baseline commit is not a record-versus-history disagreement the reader flags; it is two valid-looking baselines, so the corruption is silent. The guard belongs at the write, before the second commit exists.
  - Make `init` fail loud when the branch already exists — rejected because the resume path legitimately re-enters `init`'s territory (the branch and record already exist), so failing would break resume; create-or-switch is the behavior SKILL.md already documents.
- **Specialist owner:** on-call-engineer.
- **Revisit criterion:** if the run ever needs more than one `start-of-item` per item (it does not today — one baseline per item), reopen the single-entry idempotency guard.
- **Dissent (if any):** none.
- **Driven by rounds:** R1
- **Dependent decisions:** —
- **Referenced in plan:** Implementation Approach, On-Call Resilience Posture, Testing Strategy

### D-3: Extend the existing input guards to every new git sink

- **Question:** D5, D10, and D11 route new values — item IDs, pre-work decision free-text, iteration markers, branch names, base refs, fetched ref names — into commit messages, commit trailers, `git add` pathspecs, and new grammar-valid record lines. How are the two prior bug classes (trailer/line forgery via control characters, and `git add` scope-escape via option/pathspec injection) prevented at each new sink?
- **Decision:** The repo's two existing guard primitives are applied at every new sink rather than re-invented. (1) `require_single_line` runs on every value that reaches a commit message, a commit trailer, or an appended record line — including the new D10 decision free-text and the D11 iteration/marker values (SEC-001, SEC-005); any item ID reaching a trailer is additionally regex-validated (the writer's existing `^W-[0-9]+$` check is the pattern). (2) Every new `git add` of item paths uses `--` before the pathspecs and refuses a leading `-` or `:` argument, reusing `normalize_path` plus the existing `../`/absolute refusal to confine staging to the intended area (SEC-002). (3) The new D3 fetch and D5 branch commands inherit the sibling scripts' `--end-of-options`/`--` ref pinning, and branch names are validated with `git check-ref-format --branch` (SEC-004). The working-tree ledger fallback is gated so it never satisfies a resume-critical read (SEC-003, see D-5).
- **Rationale:** The theme across all five security findings is one recurring bug, not five: the repo already owns both guard primitives (`require_single_line` at `write-run-record.sh:33-40`; `--end-of-options`/`--` ref pinning at `detect-driver-context.sh:39-41` and `scan-run-history.sh:94,106`), and the failure mode is forgetting to apply an owned primitive at a newly added sink. Because D5/D10/D11 add sinks (trailers built from item IDs and decision text; `git add` of item paths; a fetch and a branch-create), each new sink is a place the primitive must be re-applied. This is exploit-path correctness work (a forged trailer or a scope-escaped `git add` corrupts the run's committed state), so it passes YAGNI trivially as critical-path security, and the simpler version — reuse the owned primitive — is also the correct one.
- **Evidence:** R1 adversarial-security-analyst SEC-001..005 (all Evidenced; SEC-001/002 reproduced against git 2.54.0); `write-run-record.sh:33-40` (`require_single_line`), `:101` (`^W-[0-9]+$` item-ID regex, the validation pattern), `:76-82` (per-arg guarding already applied to config args in `cmd_init`); `detect-driver-context.sh:39-41` (`--end-of-options` ref pinning to inherit); `scan-run-history.sh:94,106` (`--end-of-options` on the base ref), `:45-67` (`normalize_path`), `:138-140` (the `../`/absolute traversal refusal to reuse); `durable-record-protocol.md` §Commit trailers (the four exact-key trailers the new values populate).
- **Rejected alternatives:**
  - Add a new central sanitizing layer that wraps all git invocations — rejected as an abstraction heavier than the evidence: the sinks are few and named, and the primitives already exist; a wrapper is a single-implementation abstraction that also hides which guard applies where.
  - Trust the item IDs and branch names as internal inputs (they come from a validated work-items file) — rejected because the free-text decision and correction values (D10) are operator-supplied at run time, item IDs and paths flow into shell-adjacent git argument positions, and SEC-001/002 were reproduced, so these are system-boundary inputs, not trusted internal contracts.
- **Specialist owner:** adversarial-security-analyst.
- **Revisit criterion:** if a new value-carrying git sink is added that neither `require_single_line` nor the ref-pinning/pathspec guards cover, reopen to add the sink to this decision's enumeration.
- **Dissent (if any):** none.
- **Driven by rounds:** R1
- **Dependent decisions:** D-5
- **Referenced in plan:** Implementation Approach, Security Posture, Decomposition and Sequencing, Testing Strategy

### D-4: Bounded single-attempt self-fetch with resume-before-fetch classification

- **Question:** The detector now performs the base refresh itself (spec D3). How is the fetch bounded so an offline or slow network cannot stall the run, and how is a resume kept from paying a fetch it does not need?
- **Decision:** The detector wraps its fetch in a single bounded wall-clock attempt (`timeout <N>s git fetch …`) and emits `fetch-status: failed` on expiry or error, which folds into the spec's already-defined stale-counts / no-recommendation base prompt. There is no retry and no backoff — one attempt, one deadline. `<N>` is a literal value in the script, not a configurable knob. Classification runs before the fetch: the run recognizes an existing run record (resume) first and skips the fetch entirely on resume; the fetch runs only on a fresh run whose base is unresolved.
- **Rationale:** OCE-004 (unbounded fetch on the critical path) and OCE-005 (fetch on resume) are the two resilience gaps folding the refresh into the detector opens, and spec D3 already commits to a bounded deadline and a resume-restores-base-without-refresh ordering — this decision is the implementation of that commitment. A single bounded attempt is the simpler version that satisfies the evidence: the spec asks for "a bounded deadline," not resilience-through-retry, and no measured evidence of transient fetch failure frequency exists, so retry/backoff is deferred (see Deferred YAGNI). Making `<N>` a literal (not a knob) is the simpler version per the evidence rule — no caller sets a non-default value, and the spec's own OI-1 already carries the "make refresh suppressible" question, so a configuration surface here would duplicate an open item.
- **Evidence:** R1 on-call-engineer OCE-004 (Evidenced, plan-level, "blocks ship"), OCE-005 (Evidenced, plan-level); spec D3 (detector refreshes within a bounded deadline; "a run recognized as a resume restores its base from the record and performs no refresh"); spec Edge Cases ("a slow refresh folds into the same failed-refresh path as a hard failure"); `detect-driver-context.sh:56-59` (today's `IWI_FETCH_STATUS` passthrough the self-fetch replaces), `SKILL.md:122-126` (Step 1.6 `git fetch --all` + re-detect, the sequence being folded in); spec OI-1 (suppressibility remains open, non-blocking).
- **Rejected alternatives:**
  - Retry with backoff on a failed fetch — rejected under YAGNI: no measured frequency of transient fetch failure justifies it now; deferred with a reopen trigger.
  - A configurable fetch-deadline knob — rejected as a speculative configuration surface (no caller sets it); the literal value is the simpler version and OI-1 already owns the suppressibility question.
  - Fetch on every invocation and let the resume path discard the result — rejected because it pays a network round-trip (and a potential stall) on a resume that the spec says must restore its base from the record without refreshing.
- **Specialist owner:** on-call-engineer.
- **Revisit criterion:** transient fetch failures observed frequent in real runs (reopens the retry/backoff question); or OI-1 resolves toward a suppression flag (reopens the always-attempt default).
- **Dissent (if any):** none.
- **Driven by rounds:** R1
- **Dependent decisions:** —
- **Referenced in plan:** Implementation Approach, On-Call Resilience Posture, Decomposition and Sequencing, Testing Strategy, Deferred (YAGNI)

### D-5: Resume-critical reads gate on committed artifacts; marker-last ordering enforced by construction

- **Question:** T1 requires resume-critical state (pre-work decisions, fix-round count, in-progress-round findings) to be reconstructable only from committed artifacts, and D14 requires a durable marker never to precede the artifact it attests. With the working-tree ledger fallback present in the scanner and the code-commit and marker-write now split across two actors (driver commits code, tool writes markers), how are both invariants held?
- **Decision:** Two enforcement points. (1) Resume-critical reconstruction (decisions, fix-round count, in-progress-round findings) is sourced only from `git show HEAD:` — the scanner's working-tree ledger fallback (`scan-run-history.sh:146-152`) must not satisfy those reads, and the existing traversal refusal (`:138-140`) is preserved. The general items block may still consult the fallback where it does today, but the newly-durable resume-critical fields never do (this updates the existing `scan-run-history.test.sh` case 17 from "fallback populates items" to T1's committed-only boundary for those fields). (2) Marker-last ordering is enforced by construction across the two-actor split: the terminal/lifecycle marker is committed only after the artifact it attests (the code commit or the review-record commit) is committed; the tool optionally verifies the backing commit resolves before writing a terminal marker, with the reader's default-deny remaining the crash-time backstop, not the sole defense.
- **Rationale:** T1's hazard (1) is concrete — the scanner falls back to reading an uncommitted working-tree ledger, so once decisions and iteration markers share that file, an uncommitted decision would be read as durable and silently steer a build (D10 is the first restored state that directly drives a build). Gating resume-critical reads on `git show HEAD:` is the minimal change that honors T1 while leaving the general items-block behavior the fallback serves today intact. OCE-006 establishes that marker-last (D14) cannot be a runtime check alone once two actors write the pieces; enforcing it by construction (the tool's terminal write is sequenced after the attested commit) collapses the partial-state set to the single safe state D14 names. SEC-003 is the security face of the same T1 requirement (the fallback must not disclose or admit resume-critical state) and is satisfied by the same gate. This is correctness work protecting resume integrity — it passes YAGNI as data-integrity, not speculation.
- **Evidence:** R1 adversarial-security-analyst SEC-003 (Evidenced, "honors T1"), on-call-engineer OCE-006 (Evidenced, "honors D14/T2"); T1 (resume-critical state from committed artifacts only; the two named hazards); T2 (audit done resolves against its confirmation-record commit); spec D14 (marker committed only after the artifact it attests; default-deny extended); `scan-run-history.sh:146-152` (the working-tree fallback), `:138-140` (traversal refusal to preserve), `:154-158,203-208` (`ITEM_RESOLVED` / done-resolution the audit path reuses per T2); `durable-record-protocol.md` §Integrity (default-deny table, the crash-time backstop); test-plan T9 (the case-17 T#-contradiction, resolved here toward the committed-only boundary), T10 (mid-step-death reconstructs as in-progress).
- **Rejected alternatives:**
  - Remove the working-tree fallback entirely — rejected as broader than the evidence requires: the fallback serves the general items block for a fresh in-flight run (case 17), which is not resume-critical; T1 scopes the prohibition to resume-critical fields, so the narrower gate is the simpler version.
  - Enforce marker-last only via the reader's default-deny at resume time — rejected because OCE-006 shows default-deny is the crash-time backstop, not a substitute for writing the marker after the attested commit; relying on it alone leaves a window where a marker can be committed before its artifact.
- **Specialist owner:** adversarial-security-analyst (SEC-003 gate) and on-call-engineer (OCE-006 ordering); test-engineer owns the T9/T10 harness resolution.
- **Revisit criterion:** if case 17's general-items-block fallback is later found to also leak into a resume-critical field, reopen to remove the fallback entirely rather than narrow it.
- **Dissent (if any):** none.
- **Driven by rounds:** R1
- **Dependent decisions:** —
- **Referenced in plan:** Implementation Approach, Security Posture, On-Call Resilience Posture, Testing Strategy, Definition of Done

### D-6: Retire `no-commit-done`; audit done resolves against its confirmation-record commit

- **Question:** The spec (D8/T2) removes the `no-commit-done` terminal state and resolves an audit's `done` against its committed confirmation record. Which exact tokens, state strings, and code paths are removed from the two scripts, and what replaces the audit's resolution path?
- **Decision:** The `no-commit-done` lifecycle token is removed from the writer's `cmd_log` accepted set (leaving `start-of-item|done|skip`), and the `done-no-commit` reconstructed-state alias plus its token-to-state mapping are removed from the scanner. An audit's confirmation-record commit carries the same item-resolution trailer a code item's commit carries, so the scanner resolves an audit's `done` through the identical `ITEM_RESOLVED` path (one shared resolution rule, not a second no-commit code path). The integrity table's separate no-commit row is dropped: a completed item — audit or deliverable — is one terminal token backed by one resolvable commit.
- **Rationale:** T2 makes this exact commitment ("the record grammar then drops the separate `no-commit-done` lifecycle token and its `done-no-commit` reconstructed-state alias, and the integrity table drops its separate no-commit row"), and it is unlocked by D11 committing every audit's confirmation record — so the resolving commit T2 needs already exists. The naming split between the `no-commit-done` token and the `done-no-commit` state repeatedly read as a possible bug (spec F14), so retiring it removes a real source of confusion, not just a redundant state. Reusing the one `ITEM_RESOLVED` rule for both item kinds is the simpler version: two divergent resolution paths (one trailer-based, one no-commit) collapse to one.
- **Evidence:** R1 test-engineer T6/T7 (round-trip parity + negative-removal check, both Evidenced); spec T2 (the token/state/row removals, verbatim); spec D8 (no distinct no-commit terminal state) and D14 ("done is safe when its backing commit resolves" covers audits and code items alike); `scan-run-history.sh:184-198` (the token-to-state case statement mapping `no-commit-done`→`done-no-commit`), `:154-158,203-208` (`ITEM_RESOLVED` the audit path reuses); `write-run-record.sh:97-100` (the four-token accepted set to narrow to three); `durable-record-protocol.md:118` (the `no-commit-done` integrity row to drop); `no-output-completion.md` (the reference that shrinks — its `no-commit-done` mechanics fold into the audit's ordinary done path).
- **Rejected alternatives:**
  - Keep `no-commit-done` as an accepted-but-deprecated token for backward compatibility with old records — rejected because no committed record for an in-flight run predates this change in a way that must resume across it (the dogfood is a single session, D-7), and keeping it retains the exact naming split F14 flagged; the negative-removal test (T7) asserts the token is gone from both scripts.
  - Give the audit's confirmation commit a distinct audit-resolution trailer — rejected because T2 requires the same item-resolution marker so a resume resolves an audit's done identically to a code item's; a distinct trailer would rebuild the two-path divergence this decision removes.
- **Specialist owner:** test-engineer (owns the round-trip and negative-removal proof); the token/state removal is mechanical.
- **Revisit criterion:** if a real record is found that still carries `no-commit-done` and must be resumed across this change, reopen to decide on a one-time migration read.
- **Dissent (if any):** none.

### D-7: Build/verify sequence, single-session dogfood, and `git revert` rollback

- **Question:** The run edits its own resume machinery. In what order are the changes built and verified so a mid-migration stop cannot corrupt an in-flight run, and what is the rollback story given there is no CI?
- **Decision:** A stated build order gates the change: (1) the three scripts, the record grammar, and their `*.test.sh` harnesses are changed and run green first — including the harness rewrites (writer gains a per-case git sandbox) and the T9/case-17 resolution — before any SKILL.md driver-prose change; (2) the reference files are consolidated/renamed next; (3) the SKILL.md driver prose is changed last; (4) the long-form doc is updated in the same change. The building run itself stays on the current (pre-change) logic — no mid-run hot-swap of the machinery it depends on. Verification is two-phase: all `*.test.sh` harnesses green (the only automated gate, no CI), then a dogfood scoped to a single continuous session with no cold stop/resume across the migration boundary. Rollback is `git revert` of the change's commits.
- **Rationale:** The second-run retrospective recorded a concrete hazard — a run that stops mid-migration and resumes against a scanner that now looks in a different place than the still-old writer left its record. Front-loading the script/grammar/harness changes to green before touching the driver prose means the correctness burden is carried by the harnesses (which run against crafted repos, needing no live run of the machinery being changed), and the dogfood only has to prove the driver-level integration and D7's prompt-level scope judgment — the things the harnesses cannot reach. A single continuous dogfood session avoids the exact stop/resume-across-the-boundary hazard the retrospective named. `git revert` is the only rollback available (no CI, no deploy), and it is sufficient for a self-contained skill change.
- **Evidence:** R1 junior-developer JD-1 and test-engineer two-phase verification (both Evidenced, plan-level); test-plan §"On the dogfooding-safe verification problem" (Phase 1 harness-green-first, Phase 2 single-session dogfood); `docs/research/implement-work-items-second-run-feedback.md` (the observed mid-migration hazard); `.discovery-notes.md` §Tests ("No project-wide test suite and no CI … the `*.test.sh` harnesses are the only automated gate"); test-plan T15 (harness-wide sandbox migration must precede using the changed writer).
- **Rejected alternatives:**
  - Change SKILL.md driver prose alongside the scripts in any order — rejected because a driver running new prose against a not-yet-rewritten script (or vice versa) is the mixed-state hazard; the harnesses must be green on the new scripts before the prose that calls them changes.
  - Rely on an interrupt-and-resume dogfood to exercise resume — rejected because resuming across the migration boundary is the specific corruption the retrospective observed; resume correctness is proved by the harnesses (T8/T9/T10), not by a live cross-boundary resume.
- **Specialist owner:** junior-developer (sequence) and test-engineer (verification phases).
- **Revisit criterion:** if CI is added to the repo (`.github/workflows` appears), reopen to make the harness gate automated rather than manual.
- **Dissent (if any):** none.

### D-11: Two-actor reference split, return-format ownership, and the enumerated end-state file list

- **Question:** D6 consolidates the references to an actor-labeled scheme. Precisely which files exist after the change, where does the sub-agent return format live versus the driver's parse/halt logic, and what stays a residual driver step?
- **Decision:** The reference set is restructured by actor, not reduced by a flat count. The hand-off collapses to two actor-named references: a **driver-facing** reference holding how to compose each dispatch and which sections the driver parses plus its halt conditions, and a **sub-agent-facing** reference holding the sub-agent's full working guidance and the required return format (the format the worker must produce). The return format lives in the sub-agent-facing reference; the driver-facing reference holds only the headers it parses and the halt conditions — the split the current `build-report-contract.md` / `review-verdict-contract.md` files already draw internally. The other references are renamed to the consistent actor-prefixed scheme and some fold: `durable-record-protocol.md` (driver-facing, renamed), `foreground-handoff-protocol.md` (renamed), `human-review-capture.md` (renamed), `no-output-completion.md` shrinks post-F14 (its `no-commit-done` mechanics retire) and folds, and `re-grounding-routine.md` is gutted by D4 (steps 1-3 move into tooling) leaving only step 4 (reload-instructions) as a residual driver step folded into the driver-facing reference. The `expected-paths` inputs are removed from the dispatch payload and the review-scope section per spec D7 (no predicted-path list supplied).

### D-12: Opening co-commit is an explicit exception to narrow staging

- **Question:** D5 stages only the exact record file on every bookkeeping commit, but the opening commit must also carry the run's planning artifacts. How is the exception scoped so it does not weaken the narrow-staging guarantee everywhere else?
- **Decision:** The opening commit (`init`) is an explicit, enumerated exception to D5's narrow staging: it stages the record file plus the enumerated planning-artifact paths (the work-items file and the local `.md` files it links in its preamble, per SKILL.md 1.4) as one commit, so a failed opening leaves an empty fresh branch. Every other bookkeeping commit (`log`, `block`, the per-item lifecycle and marker commits) stages only the exact record file it wrote (`git add -- "$rec"`). The exception is confined to the opening write and does not generalize.
- **Rationale:** JD-5 identified that the opening co-commit (record + planning artifacts) genuinely needs to stage more than the record file — the run must be identifiable and its planning content committed together so the branch is self-contained — while every per-item bookkeeping commit must stay narrowly staged (OCE-007) so a formatter-on-save edit is never swept in. Naming this as one explicit exception, rather than loosening staging generally, keeps the narrow-staging guarantee intact everywhere it protects against concurrent-edit contamination. The planning-artifact paths are already enumerable (SKILL.md 1.4 and 2.1 already have the driver enumerate exactly what the opening commit stages).
- **Evidence:** R1 junior-developer JD-5 (Evidenced, plan-level, "refines D5"); spec D5 ("staging only the exact record file it wrote") and Primary Flow 4 ("commits it together with the run's planning artifacts … as one tool action"); SKILL.md Step 1.4 (identifying the planning artifacts), Step 2.1 ("Enumerate exactly what the opening commit (2.2) will stage"), Step 2.2 step 3 ("Co-commit it with any uncommitted planning artifacts (1.4) as one commit"); `durable-record-protocol.md` §Exclusion (the per-item stage-by-path sites that stay narrow).
- **Rejected alternatives:**
  - Stage the planning artifacts in a separate commit before the opening record commit — rejected because the spec requires the opening to be one commit so a failed opening leaves an empty fresh branch, not a half-committed planning set with no run record.
  - Loosen narrow staging generally to a plan-folder scope — rejected because it reopens the concurrent-edit contamination window OCE-007 closes on every per-item commit; the exception must be confined to the opening.
