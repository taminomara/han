# Feature Technical Notes: implement-work-items Driver Automation and Resumability Hardening

Captures the one load-bearing mechanic whose correct specification required naming it and that is not already fixed by the current code. Behavioral statements live in [../feature-specification.md](../feature-specification.md).

## T1: Resume-critical state lives in committed artifacts

- **Context:** The spec commits the run to restoring, on resume, the operator's pre-work decisions ([D10](decision-log.md#d10-persist-pre-work-decisions-durably)) and the per-item fix-round count and the in-progress round's findings ([D11](decision-log.md#d11-durable-iteration-markers-and-committed-review-records)) without re-asking or re-deriving, and to a resume-integrity invariant where a marker never precedes the work it attests ([D14](decision-log.md#d14-durable-markers-committed-last-resume-default-deny-extended)). Those behaviors are only correct if this state is durable in the same sense the existing run record is: reconstructable from committed artifacts, not from the live session and not from the uncommitted working tree.
- **Technical detail:** Each kind of resume-critical state must be written into the committed run record (or a committed sibling under the run's bookkeeping area) and committed as bookkeeping before the run could stop — not merely written to a working-tree file. Specifically: a pre-work decision is committed before the item's build begins; each fix-round iteration is recorded in the run record; and each round's durable review record is committed when it is written. A durable marker is committed only after the artifact it attests (the code commit or review record), so the only reachable partial state on a mid-step death is artifact-present-marker-absent, read as in-progress. Two hazards the current code makes concrete: (1) the existing history scanner falls back to reading an *uncommitted* working-tree ledger for a fresh in-flight run — that fallback must not be used to satisfy resume-critical state, or an uncommitted decision would be read as durable; and (2) the record writer has no duplicate-guard, so a tool that commits then dies before recording its result to the driver must, on re-entry, recognize the already-recorded start rather than append a second entry. The existing append-only record grammar and the resume-marker trailers (`references/durable-record-protocol.md`) are the pattern to extend; a plan-implementation that writes any of this state only to the session or to an uncommitted file would pass a happy-path run but silently break resume. The exact record grammar for the new entries is plan-implementation's to design.
- **Supports decisions:** D10, D11, D14
- **Driven by findings:** F1, F2, F8
- **Referenced in spec:** Outcome, Primary Flow, Resume, Edge Cases and Failure Modes

## T2: Audit completion resolves against its confirmation-record commit

- **Context:** The No-output audit exit ([D8](decision-log.md#d8-no-output-carried-by-the-item-type)) and the resume-integrity rule ([D14](decision-log.md#d14-durable-markers-committed-last-resume-default-deny-extended)) require a completed audit to be verifiable by the same "done is safe when its backing commit resolves" rule as any item, with no distinct no-commit terminal state. That is only correct if a resume can positionally resolve an audit's done against a real commit rather than against nothing.
- **Technical detail:** An audit produces no code, but per D8/D11 its confirmation record is committed. That confirmation-record commit is made the audit's resolving commit — it carries the same item-resolution marker a code item's commit carries, so a resume resolves an audit's done identically to a code item's done. The record grammar then drops the separate `no-commit-done` lifecycle token and its `done-no-commit` reconstructed-state alias, and the integrity table drops its separate no-commit row; a completed item — audit or deliverable — is one terminal token backed by one resolvable commit. The confirmation-record commit is committed before the terminal entry, per the marker-last ordering ([D14](decision-log.md#d14-durable-markers-committed-last-resume-default-deny-extended)). The exact marker or trailer reused is plan-implementation's to choose; the load-bearing constraint is only that an audit's done must resolve against a real, identifiable commit.
- **Supports decisions:** D8, D14
- **Driven by findings:** F14
- **Referenced in spec:** No-output audit, Edge Cases and Failure Modes
