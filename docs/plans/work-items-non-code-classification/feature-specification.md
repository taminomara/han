# Feature Specification: Non-code, meta, and non-deliverable work items

Extend how `plan-work-items` classifies work and how `implement-work-items` drives it, so a plan whose deliverables are non-code (docs, skills, agents), meta (editing an existing plugin definition), or non-deliverable (a verification pass, a spike) produces correctly-classified, drivable work items without overriding the catalog or straining the template — and so the driver's relaxations for no-output work are guarded, not silent.

## Outcome

An operator can take a plan whose work is not application code — authoring or editing a skill or agent, running a verification pass, proving a spike — break it into work items with `plan-work-items`, and drive the whole set with `implement-work-items`, and every item routes on its own recorded markers with no manual override and no repurposed template field.

Concretely, three gaps close, each with a guard so the relaxations that close them cannot silently pass broken or no-op work:

- **A non-code change an agent can draft is marked unattended.** A work item whose deliverable is a markdown or config edit that an agent can draft from a detailed plan records an unattended build, so the driver drafts it in a sub-agent and routes only the review to the operator — the same "agent drafts, human reviews" split that code already gets. An edit to an artifact the tooling loads (a skill, agent, or manifest) still gets a human read, so a structurally-broken draft cannot ship green ([D3](artifacts/decision-log.md#d3-agent-drafted-non-code-build-runs-through-the-general-purpose-agent), [D16](artifacts/decision-log.md#d16-an-edit-to-an-executable-plugin-artifact-requires-a-human-read), [T1](artifacts/feature-technical-notes.md#t1-general-purpose-is-a-built-in-always-available-agent-type)).
- **Editing an existing skill, agent, or plugin file has a correct classification.** The most common plugin-maintenance task — changing an existing definition rather than creating a new one — maps to a classification that names something that can actually perform the edit and links the authoring guidance the editor must honor, instead of a reference-only skill that cannot edit ([D4](artifacts/decision-log.md#d4-editing-an-existing-plugin-definition-is-its-own-classification), [D5](artifacts/decision-log.md#d5-guidance-is-reference-only-never-the-implementer)).
- **Work that produces no deliverable can be classified and driven — under a validated guard.** A verification pass or a spike is classified for what it is, and a verification pass that changes no files completes and is recorded without forcing an empty commit. That no-output path is reachable only through validation: an item may declare it produces nothing only when it is a verification, and such an item's review is always a human confirmation, so a failed or no-op build cannot slip onto the accept-nothing path ([D6](artifacts/decision-log.md#d6-a-type-marker-distinguishes-deliverable-verification-and-spike-items), [D9](artifacts/decision-log.md#d9-a-verification-item-may-declare-no-output-and-is-then-driven-without-a-commit), [D11](artifacts/decision-log.md#d11-the-type-marker-is-driver-validated-with-startup-refusals), [D12](artifacts/decision-log.md#d12-a-no-output-item-is-reviewed-by-a-human-confirmation)).

## Actors and Triggers

- **Actors** — the **operator** running the skills; the **producer** (`plan-work-items`) that classifies a plan into work items; the **driver** (`implement-work-items`) that validates, builds, verifies, reviews, and commits each item; and the **build and review agents** the driver dispatches unattended.
- **Triggers** — the operator runs `plan-work-items` on a trusted plan whose deliverables include non-code, meta, or non-deliverable work; later, the operator runs `implement-work-items` on the resulting `work-items.md`.
- **Preconditions** — a trusted plan or equivalent context exists; for the driver, a work-items file produced (or hand-edited) to the extended format exists, on a clean tree with a green suite.

## Primary Flow

1. The operator runs the producer on a plan that mixes application code with non-code, meta, or non-deliverable work.
2. For each work item, the producer classifies the deliverable's nature against the catalog and records the markers the driver reads: a **Type** (`deliverable`, `verification`, or `spike`), a **Suggested implementation** (a skill or agent, plus `AFK` or `HITL`), a **Suggested review** (a skill, agent, or the literal `none` human read, plus `AFK` or `HITL`), and **Expected paths** (the files the item creates or modifies, or `None` when a verification produces no output). The item also carries a type-aware **Verification** field describing how it is checked — code test levels for code, read-the-file conformance and dry-run checks for docs and skills, result confirmation for a verification pass ([D6](artifacts/decision-log.md#d6-a-type-marker-distinguishes-deliverable-verification-and-spike-items), [D7](artifacts/decision-log.md#d7-the-templates-tests-field-becomes-a-type-aware-verification-field), [D9](artifacts/decision-log.md#d9-a-verification-item-may-declare-no-output-and-is-then-driven-without-a-commit)).
3. For a non-code change an agent can draft from the plan — a markdown edit, a config change, an edit to an existing skill or agent definition — the producer records the build as run by a **general-purpose agent, unattended**, using the canonical marker `` `general-purpose` agent, AFK ``, and links the applicable authoring guidance in the item's references so the build agent receives it ([D3](artifacts/decision-log.md#d3-agent-drafted-non-code-build-runs-through-the-general-purpose-agent), [D11](artifacts/decision-log.md#d11-the-type-marker-is-driver-validated-with-startup-refusals), [D15](artifacts/decision-log.md#d15-the-catalog-gains-classification-homes-for-verification-and-spike-and-links-guidance)).
4. The producer prints the breakdown and writes `work-items.md`, then tells the operator how many items run unattended and where a human is needed.
5. The operator runs the driver on the file. The driver validates every item's markers — including the new `Type`-coupled refusals — confirms a clean tree and green suite, and previews the run.
6. For each item in order, the driver asserts a clean working tree, then routes the build by its marker: an unattended build (a named skill, or a general-purpose agent for an agent-drafted non-code change) runs in a sub-agent; a human-in-the-loop or bare `none` build hands off to the operator. A verification item's build runs its named checks and, when the item declared `Expected paths: None`, is dispatched knowing that changing no files is the expected result ([D3](artifacts/decision-log.md#d3-agent-drafted-non-code-build-runs-through-the-general-purpose-agent), [D9](artifacts/decision-log.md#d9-a-verification-item-may-declare-no-output-and-is-then-driven-without-a-commit), [D13](artifacts/decision-log.md#d13-the-build-report-contract-gains-a-skill-less-and-no-output-shape)).
7. The driver verifies the build, then routes the review by its marker: an unattended review runs in a sub-agent; a human read, and every no-output item's result confirmation, is captured from the operator ([D8](artifacts/decision-log.md#d8-verification-and-spike-items-carry-result-confirming-reviews), [D12](artifacts/decision-log.md#d12-a-no-output-item-is-reviewed-by-a-human-confirmation)).
8. When the item clears, the driver commits the files it changed — or, when a verification item declared no output and changed nothing, records it complete as a distinct no-commit outcome rather than forcing an empty commit ([D9](artifacts/decision-log.md#d9-a-verification-item-may-declare-no-output-and-is-then-driven-without-a-commit), [D14](artifacts/decision-log.md#d14-a-no-commit-completion-is-labeled-tracked-and-idempotent)).
9. The driver repeats until every item is committed or recorded no-commit-complete, or it halts on the first item it cannot finish cleanly. The completion summary names each no-commit completion distinctly so the operator can audit it ([D14](artifacts/decision-log.md#d14-a-no-commit-completion-is-labeled-tracked-and-idempotent)).

## Startup Validation and Refusals

The no-output relaxation is safe only because the driver refuses, before it mutates the repository, any item whose markers could route a failed or no-op build onto the accept-nothing path. At validation the driver reads `Type` and enforces ([D11](artifacts/decision-log.md#d11-the-type-marker-is-driver-validated-with-startup-refusals), [D12](artifacts/decision-log.md#d12-a-no-output-item-is-reviewed-by-a-human-confirmation)):

- A missing `Type` is read as `deliverable`. A present `Type` outside `deliverable`, `verification`, `spike` is a startup refusal naming the offending value.
- `Expected paths: None` is legal only for a `verification` item. A `deliverable` or `spike` item declaring `None` is a startup refusal — this is what keeps a real deliverable off the no-output path.
- A `verification` item, and any item declaring `Expected paths: None`, must record a human review (`none` or `HITL`), never an `AFK` sub-agent review; an `AFK` review recorded on such an item is a startup refusal.
- A `` `none`, AFK `` build marker is a startup refusal: a bare `none` build is always a human-in-the-loop free-form build.

An interactive-skill spike's `AFK`-vs-`HITL` is producer-judged, not a refusal: run `AFK` such a spike produces its finding and returns, and an edge-case interactive gate fails recoverably rather than corrupting the run (see the Spike flow and [D19](artifacts/decision-log.md#d19-spike-autonomy-is-afk-capable-producer-judged-per-item)).

These refusals are enforced at two points. The producer applies them as it classifies and writes each item: because it authors from a well-formed catalog, the realistic way it reaches a refused combination is an operator override, so rather than write one it declines the specific override field(s) that create the refused combination and restores the item's catalog-derived classification, naming the declined override and the conflict in the breakdown — it does not transform the item to a different `Type` or output contract to make the override fit. The driver re-checks the refusals at startup as the last line, because a hand-edited file bypasses the producer ([D11](artifacts/decision-log.md#d11-the-type-marker-is-driver-validated-with-startup-refusals)).

## Alternate Flows and States

### Agent-drafted non-code build

- **Entry condition:** a work item's build is recorded as `` `general-purpose` agent, AFK `` (a non-code change an agent can draft from a detailed plan).
- **Sequence:** the driver dispatches a general-purpose agent with the item's description, references, and the committed plan, and asks it to make the change and report; because the change has no test harness, the report declares itself untestable rather than carrying test evidence, and it reports no skill gate because a general-purpose agent runs no skill ([D3](artifacts/decision-log.md#d3-agent-drafted-non-code-build-runs-through-the-general-purpose-agent), [D13](artifacts/decision-log.md#d13-the-build-report-contract-gains-a-skill-less-and-no-output-shape), [T1](artifacts/feature-technical-notes.md#t1-general-purpose-is-a-built-in-always-available-agent-type)).
- **Exit:** the driver verifies, then reviews. When the edited artifact is one the tooling loads (a skill, agent, or manifest), the review is a human read so a structurally-broken draft cannot ship; for genuinely non-executable prose an unattended prose review is allowed ([D16](artifacts/decision-log.md#d16-an-edit-to-an-executable-plugin-artifact-requires-a-human-read)).

### Editing an existing skill, agent, or plugin definition

- **Entry condition:** a work item modifies an existing skill, agent, or other plugin file rather than creating a new one.
- **Sequence:** the producer classifies it as a plugin-definition edit — an agent-drafted unattended build (per D3) with the plugin-authoring guidance linked in its references, reviewed by a human read — not as a new-skill or new-agent build and not as the reference-only guidance skill ([D4](artifacts/decision-log.md#d4-editing-an-existing-plugin-definition-is-its-own-classification), [D5](artifacts/decision-log.md#d5-guidance-is-reference-only-never-the-implementer), [D16](artifacts/decision-log.md#d16-an-edit-to-an-executable-plugin-artifact-requires-a-human-read)).
- **Exit:** the driver drafts the edit unattended and routes the human read to the operator.

### Verification pass

- **Entry condition:** a work item of `Type: verification` — a QA or conformance pass that runs checks and confirms a result.
- **Sequence:** the item's build runs its named checks (unattended when the checks are automatable, hand-run when they include manual dry-run scenarios); its review is the operator confirming the result is sound, not a review of a change. A verification that produces no artifact declares `Expected paths: None`; a verification that emits a report file declares that path and is committed like a deliverable ([D8](artifacts/decision-log.md#d8-verification-and-spike-items-carry-result-confirming-reviews), [D9](artifacts/decision-log.md#d9-a-verification-item-may-declare-no-output-and-is-then-driven-without-a-commit)).
- **Exit:** a no-output verification is recorded complete with no commit; a verification with a report commits it.

### Spike

- **Entry condition:** a work item of `Type: spike` — an investigation that proves whether something holds and records the outcome.
- **Sequence:** the item's build runs a probe routed by the question's shape — `han-coding:investigate` for a named symptom with a codebase root cause to trace, `han-core:research` for an open-ended question (options, prior art, how something works, or whether an approach holds), and a general-purpose agent for a quick empirical probe resolvable in a single read or command; the producer's default is `research` unless the question is a named symptom with a codebase root cause. A spike's build produces its finding unattended for the common case: `research` writes its report and returns (no blocking approval), and `investigate` writes its finding regardless of its fix-approval gate — so the producer marks an interactive-skill spike `AFK` when its question is well-formed, correctly routed, and single-thread, and `HITL` when it is inherently exploratory or likely to need clarification ([D19](artifacts/decision-log.md#d19-spike-autonomy-is-afk-capable-producer-judged-per-item)). A quick-probe general-purpose spike (one resolvable in a single read or command) is `AFK`, dispatched with the Expected path as its finding target; if such a probe turns out to need the operator, that is a signal it was misclassified, and it is re-routed to `investigate`/`research` rather than forced through. The interactive gates that would block an `AFK` interactive-skill spike are avoidable edge cases the producer controls — a mis-route, a too-vague clarify, a compound multi-thread question — plus a rare re-run overwrite; on any gate that fires today the build halts recoverably, nothing corrupted. A build-dispatch instruction that maps a routed skill's operator-gates to a `blocked` escalation, together with escalate-and-resume, upgrades those halts into clean mid-run escalations; both are out of scope and are enhancements, not prerequisites for `AFK` today ([D19](artifacts/decision-log.md#d19-spike-autonomy-is-afk-capable-producer-judged-per-item)). The foreground handoff for a `HITL` spike that names the Expected path, and the finding-soundness framing of a spike's review, are `plan-implementation` details. The probe records its finding as the deliverable (a root-cause document is a valid finding); its review confirms the finding is recorded, non-empty, and sound ([D8](artifacts/decision-log.md#d8-verification-and-spike-items-carry-result-confirming-reviews), [D17](artifacts/decision-log.md#d17-a-spikes-build-routes-by-question-type), [D15](artifacts/decision-log.md#d15-the-catalog-gains-classification-homes-for-verification-and-spike-and-links-guidance)).
- **Exit:** because a spike records a finding, it names the file it writes in Expected paths (never `None`) and the driver commits it like a deliverable.

**Note on the boundary with pre-work decisions.** The existing `Requires pre-work decisions` gate is kept, but its producer-side trigger narrows to a decidable, **ordered** rule (the criteria can co-apply, so precedence matters): a decision whose answer must be permanently recorded and referenced is modeled as an architectural decision record the dependent item depends on; else a decision that requires reading files, running code, or gathering external evidence is modeled as a spike it depends on; else a decision statable and actionable in a single sentence stays on the inline flag. A decision that both needs investigation and must be recorded is a spike whose finding an ADR records. This narrows the field's former "architectural decision or a design gate" trigger — a record-worthy architectural decision now routes to an ADR rather than the inline flag — in both the template's field definition and the catalog's classification step. Retiring the field itself is out of scope ([D18](artifacts/decision-log.md#d18-the-pre-work-decisions-field-is-kept-with-a-producer-routing-note)).

## Edge Cases and Failure Modes

| Condition | Required Behavior |
|-----------|-------------------|
| A `deliverable` or `spike` item declares `Expected paths: None`. | Startup refusal naming the item: only a `verification` may declare no output, so a real deliverable cannot reach the accept-nothing path ([D11](artifacts/decision-log.md#d11-the-type-marker-is-driver-validated-with-startup-refusals)). |
| A `verification` item declares `Expected paths: None` and changes no files. | The driver completes it: it accepts a build that produced no files for the declared no-output item, and records the item done as a distinct no-commit outcome rather than forcing an empty commit ([D9](artifacts/decision-log.md#d9-a-verification-item-may-declare-no-output-and-is-then-driven-without-a-commit), [D14](artifacts/decision-log.md#d14-a-no-commit-completion-is-labeled-tracked-and-idempotent)). |
| A no-output item's build leaves files in the working tree despite declaring `None`. | The unexpected change is surfaced as a scope finding in review for the operator to resolve, never silently no-committed; the driver asserts a clean tree before the next item so the stray files cannot contaminate the next item's scope window ([D9](artifacts/decision-log.md#d9-a-verification-item-may-declare-no-output-and-is-then-driven-without-a-commit), [D14](artifacts/decision-log.md#d14-a-no-commit-completion-is-labeled-tracked-and-idempotent)). |
| A verification item is recorded with an `AFK` review. | Startup refusal: a verification's review is a human result-confirmation, never an unattended change review, and over a no-output item an unattended review inspects nothing at all ([D8](artifacts/decision-log.md#d8-verification-and-spike-items-carry-result-confirming-reviews), [D12](artifacts/decision-log.md#d12-a-no-output-item-is-reviewed-by-a-human-confirmation)). |
| An agent-drafted edit reports success over a structurally-broken plugin artifact (bad frontmatter, dropped tool grant). | The required human read on an executable plugin artifact is the gate that catches it; the build's untestable declaration is never the sole gate over an artifact the tooling loads ([D16](artifacts/decision-log.md#d16-an-edit-to-an-executable-plugin-artifact-requires-a-human-read)). |
| A spike's finding file is empty. | The spike's soundness review treats an empty finding as a failed build — a spike records a finding, so an empty one is not a sound result ([D8](artifacts/decision-log.md#d8-verification-and-spike-items-carry-result-confirming-reviews)). |
| An existing `work-items.md` predates the `Type` and `Verification` fields. | The driver reads a missing `Type` as `deliverable` and drives the file unchanged; the `Verification` field (renamed from `Tests`) is one the driver does not parse, so an older file that still says `Tests` drives identically ([D10](artifacts/decision-log.md#d10-the-extended-format-is-backward-compatible)). |
| The operator overrides a non-code item's build or review. | Overrides work as they do today: the operator's named skill or declared autonomy wins, a mismatch against the item's nature is flagged, and an uninstalled override is kept as a recommendation — but an override cannot produce a marker combination the startup validation refuses (for example a `deliverable` with `None`) ([D3](artifacts/decision-log.md#d3-agent-drafted-non-code-build-runs-through-the-general-purpose-agent), [D11](artifacts/decision-log.md#d11-the-type-marker-is-driver-validated-with-startup-refusals)). |

## Coordinations

| Coordinating System | Direction | Interaction | Ordering / Consistency Requirement |
|---------------------|-----------|-------------|-----------------------------------|
| Producer → driver | outbound (producer writes, driver reads) | The producer records the per-item markers (`Type`, `Suggested implementation`, `Suggested review`, `Expected paths`) the driver validates and routes on. | The marker vocabulary is a shared contract: every value the producer can emit — including the canonical `` `general-purpose` agent `` build token and the three `Type` values — the driver must validate and route the same way, or an item silently falls through. The two skills must stay reconciled whenever either side's vocabulary changes ([D6](artifacts/decision-log.md#d6-a-type-marker-distinguishes-deliverable-verification-and-spike-items), [D11](artifacts/decision-log.md#d11-the-type-marker-is-driver-validated-with-startup-refusals)). |
| Producer → build/review agents | outbound | For an agent-drafted non-code build or an unattended review, the driver dispatches a general-purpose agent with the item's content and linked references. | The general-purpose agent is always available to the driver, so an agent-drafted build is never a not-installed halt; the item's references must carry the authoring guidance, because the driver passes only the item's references and the plan to the agent ([T1](artifacts/feature-technical-notes.md#t1-general-purpose-is-a-built-in-always-available-agent-type), [D15](artifacts/decision-log.md#d15-the-catalog-gains-classification-homes-for-verification-and-spike-and-links-guidance)). |
| Driver → build-report / review-verdict contracts | internal | The driver's build and review dispatch prompts must express the skill-less build, the no-output build, and the no-output review. | The build-report contract must accept a skill-less build (no skill gate) and a declared-no-output build (empty file set is the expected success), and the human-review capture must have a no-output branch (confirm the result, not review a change) ([D13](artifacts/decision-log.md#d13-the-build-report-contract-gains-a-skill-less-and-no-output-shape), [D12](artifacts/decision-log.md#d12-a-no-output-item-is-reviewed-by-a-human-confirmation)). |

## Out of Scope

- **Atomic co-land constraints (feedback F4).** Expressing that a set of items must ship in one commit is deferred (see Deferred).
- **The reference-artifact include/exclude boundary for technical notes (feedback F7).** Naming `feature-technical-notes.md` as an includable design reference is deferred (see Deferred).
- **The closing-summary framing (feedback F8) and the review-side catalog normalization.** Both already landed with the autonomous-driver HITL feature; this feature does not revisit them, beyond adding the no-commit outcome the summary must now name ([D1](artifacts/decision-log.md#d1-scope-is-roots-abc-f4-and-f7-are-deferred)).
- **The exact wording and field ordering of the catalog rows, template fields, and driver contract prompts.** The behaviors and the marker vocabulary are specified here; their precise phrasing and the position of the `Type` field in the template are implementation, owned by `plan-implementation`.
- **Reviewing the plugin edits this feature ships.** This spec defines behavior; it does not review the code that realizes it.
- **Retiring the `Requires pre-work decisions` field.** Kept — a spike absorbs the investigation-shaped decisions but not a pure judgment call, and retiring it would be a separate producer↔driver contract change ([D18](artifacts/decision-log.md#d18-the-pre-work-decisions-field-is-kept-with-a-producer-routing-note)).
- **Machinery to keep the producer and driver refusal vocabularies in sync.** The refusal set is one shared contract; a change to it must be applied to both skills in one commit. This feature relies on that as a maintenance convention and adds no cross-skill enforcement machinery ([D11](artifacts/decision-log.md#d11-the-type-marker-is-driver-validated-with-startup-refusals)).
- **The AFK-with-escalation enhancement for interactive-skill spikes.** Two driver capabilities this feature does not build would upgrade an `AFK` interactive-skill spike's recoverable edge-case halts into clean mid-run escalations: a build-report-contract instruction that converts a routed skill's operator-gates into a `blocked` escalation (today the skills say "ask the user" / "produce no report," which an unattended dispatch cannot honor), and escalate-and-resume so the driver hands off at the escalation and continues rather than halting. Neither is a prerequisite for running interactive-skill spikes `AFK` today — they are an enhancement that removes the residual edge-case halt ([D19](artifacts/decision-log.md#d19-spike-autonomy-is-afk-capable-producer-judged-per-item)).

## Deferred (YAGNI)

### Atomic co-land relationship between work items (feedback F4)
- **Why deferred:** evidence-test scope — the driving evidence is a single plan (`autonomous-driver-hitl-support`) that needed three units in one commit, and that run had a working fallback (one documented thick item). No second plan or measured recurrence yet justifies a new first-class relationship and the driver's per-item-commit change it would require.
- **Reopen when:** a second plan hits the same must-co-land constraint and the one-thick-item workaround demonstrably fails (an item too large to review cleanly, or an atomicity requirement the single-item collapse cannot express).
- **Source:** feedback F4; user scope decision this session ([D1](artifacts/decision-log.md#d1-scope-is-roots-abc-f4-and-f7-are-deferred)).

### Naming `feature-technical-notes.md` as an includable design reference (feedback F7)
- **Why deferred:** simpler-version scope — this is a one-line boundary clarification in the reference-artifact inventory, independent of the classification model this feature changes, and folding it in now would widen the feature for no shared benefit.
- **Reopen when:** an implementer is misled on a real run by the fuzzy `artifacts/` include boundary, or F7 is picked up as its own small change.
- **Source:** feedback F7; user scope decision this session ([D1](artifacts/decision-log.md#d1-scope-is-roots-abc-f4-and-f7-are-deferred)).

### Mechanical conformance gate for agent-drafted plugin edits
- **Why deferred:** simpler-version — a human read on an executable plugin artifact satisfies the current evidence; a driver-run mechanical gate (frontmatter parses, required fields present, the plugin still enumerates) is heavier (a new driver capability and a per-artifact-type check), and no incident yet shows the human read is insufficient.
- **Reopen when:** a structural breakage in a plugin artifact ships through the human-read gate, proving the read insufficient; or a reusable plugin-lint / frontmatter check exists that the driver could run cheaply.
- **Source:** on-call finding (D16); iterative-plan-review round 1 ([review-findings F9](artifacts/review-findings.md)).

## Summary

- **Outcome delivered:** non-code, meta-editing, and non-deliverable work items classify and drive end-to-end with no catalog override or template strain, and the no-output relaxations are guarded by startup validation rather than passed silently.
- **Primary actors:** the operator, the producer (`plan-work-items`), and the driver (`implement-work-items`).
- **Decisions settled by evidence:** 14 — see [artifacts/decision-log.md](artifacts/decision-log.md)
- **Decisions settled by user input:** 5 (scope, the general-purpose build marker, the three-value Type, the Verification rename, and the AFK-capable producer-judged spike autonomy) — see [artifacts/decision-log.md](artifacts/decision-log.md)
- **Sub-agents consulted:** `han-core:junior-developer`, `han-core:test-engineer`, `han-core:edge-case-explorer`, `han-core:on-call-engineer` (spec review); `han-core:research-analyst` and `han-core:junior-developer` (post-review iteration) — see [artifacts/team-findings.md](artifacts/team-findings.md)
