## Skill-authoring conventions (the shape of the deliverable)

- **`SKILL.md` frontmatter:** `name`, `description` (multiline block scalar; doubles as the harness trigger, <1024 chars), `allowed-tools` (comma list; Bash perms per-prefix, not wildcards). Optional: `arguments`, `argument-hint`.
- **Directory layout:** `{plugin}/skills/{name}/` = `SKILL.md` + `references/` (0-N `.md`, referenced inline via relative links, read lazily on demand) + optional `scripts/` (shell; referenced with `${CLAUDE_SKILL_DIR}` paths).
- **Reference-citation forms:** sibling `[references/x.md](./references/x.md)`; cross-plugin shared `[../../references/yagni-rule.md](../../references/yagni-rule.md)`.
- **Size precedent (SKILL.md line counts):** complex multi-round orchestration skills run **280-400 lines** (plan-implementation 287, tdd 277, code-review 398); a focused single-loop skill ~120 (plan-work-items 119). Progressive disclosure: keep SKILL.md at orchestration altitude, push detail (templates, formats, checklists) into `references/`.

## Sub-agent dispatch convention (load-bearing for this driver)

- **Established pattern:** launch agents via the `Agent` tool, **one call per agent in a single message** so they run concurrently; every skill carries the operating principle *"All sub-agents in this skill run on sonnet — pass `model: "sonnet"` on each Agent call"* (verbatim in plan-implementation, plan-work-items, plan-a-feature).
- `code-review` uses `run_in_background: true` and continues without waiting; `subagent_type: "han-core:{agent}"` names the agent type.
- **Novelty flag:** **no existing skill dispatches another *skill* as a sub-step** — all current dispatch is skill→agent. This driver would be the **first skill→skill orchestrator** in the suite (it invokes `tdd` and `code-review` as skills). No precedent to copy for the dispatch topology; the spec (F3/D11) states review runs as a main-loop skill so its panel fans out and only a condensed verdict returns. **How a skill invokes another skill unattended in a sub-agent, and how the review panel is made to fan out from within, is the central open implementation mechanic.**

## Dispatched skills — behavior the driver must honor

- **`tdd`** (`han-coding/skills/tdd/`, 277 lines): default implementation skill. Runs **unattended** (Step 1: "does not stop for confirmation"; exceptions: caller asks to review the test list, or the test command can't be resolved). **Does NOT commit** — writes prod+test files to the working tree, leaves the commit to the caller. **Final output is prose**, not a structured artifact (F1 in spec: this is why the driver must OWN the dispatch contract and name the exact compact return format, per D12).
- **`code-review`** (`han-coding/skills/code-review/`, 398 lines): the review stage. Fans out a **panel of han-core agents** — always `junior-developer` + `adversarial-security-analyst`, plus conditional `test-engineer, edge-case-explorer, structural-analyst, behavioral-analyst, concurrency-analyst, data-engineer, devops-engineer, on-call-engineer` by file signal — **in parallel** (`run_in_background: true`). Severity vocabulary: **Critical / Warning / Suggestion / YAGNI (advisory) / Security(SEC)**. Output: a full rendered report (`references/template.md`) with a Review Summary table + Review Recommendation (the verdict); no built-in count-based numeric gate today ("a Critical-severity security finding yields a do-not-merge recommendation"). The driver needs a **condensed verdict + durable full record** (D11/D12/D27) — `code-review` has no such mode today; producing it is a dispatch-contract/implementation concern.
  - **Sub-agent-nesting constraint (documented convention, cited as evidence on D11):** a sub-agent cannot dispatch further sub-agents. So review run *inside* a single sub-agent collapses to one reviewer. Full-panel fidelity requires review to run where it can fan out (main-loop skill invocation), with only the condensed verdict returning to the driver.
