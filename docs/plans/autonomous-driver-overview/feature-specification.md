# Feature Specification: Autonomous Work-Item Implementation Driver

A Han skill that takes a trusted set of work items and drives their implementation end to end, offloading the building and the reviewing to sub-agents and committing each finished item, pausing for the operator only on items that need a human up front or on blockers that cannot be resolved without changing the spec or architecture.

## Outcome

Given a trusted `work-items.md` and the committed spec or plan its items reference, the operator runs one skill and gets each work item built with its declared implementation skill (test-first by default), independently verified against the project's own checks where they exist (and scope-checked with the operator's confirmation where a project has none), reviewed at full specialist coverage ([D11](artifacts/decision-log.md#d11-full-review-fidelity-preserved)), fixed until it clears a quality gate, and committed (one commit per item) without hand-invoking `tdd` and `code-review` per item and sharply reducing the per-item context cost that otherwise forces session compaction (mid-run compaction can still occur and is guarded, [D1](artifacts/decision-log.md#d1-feature-scope-and-outcome), [D26](artifacts/decision-log.md#d26-the-re-grounding-routine)). The operator confirms the run plan once at the start, is then pulled in only when an item was marked as needing human involvement and when a sub-agent hits a blocker it cannot resolve, and can cleanly stop the run between items at any time.

## Actors and Triggers

- **Actors**
  - **Operator:** the solo or small-team engineer who has already planned the feature and broken it into trusted work items, and now wants the build driven for them.
  - **Implementer sub-agents:** disposable sub-agents the skill dispatches to build each item, running the item's declared implementation skill (by default `tdd`, the test-first builder).
  - **Reviewer sub-agents:** the self-contained review stage the skill dispatches to audit each item's changes at full specialist coverage (running `code-review`'s specialist panel). The stage returns a condensed verdict the skill gates on and persists a durable full record of its findings ([D27](artifacts/decision-log.md#d27-durable-review-record-condensed-verdict-gate-and-spot-check)). Unlike an implementer's output, which the skill independently re-verifies before trusting, the review verdict is a judgment the skill cannot re-run, so it is trusted as returned, bounded by the safeguards in the Review and Commit steps.
- **Triggers:** the operator invokes the skill, pointing it at a `work-items.md` file. Optional inputs let the operator set the review gate threshold, the fix-loop cap, the model the build and fix sub-agents run on, and the branch name.
- **Preconditions**
  - The work items are already produced and trusted (the operator ran the planning and work-item skills first; this skill does not produce or harden them).
  - The spec or plan the items reference is committed and readable, so each sub-agent can read it before building ([D1](artifacts/decision-log.md#d1-feature-scope-and-outcome)).
  - Each work item preferably carries the fields the driver uses to run it unattended: a human-involvement marker, an expected-paths declaration, and optionally an implementation skill. These are added by companion changes to the work-item producer; the driver checks for them up front and, rather than blocking when one is missing, applies a defined fallback (a missing marker is treated as unattended, and a missing expected-paths declaration falls back to a review-level scope check after asking the operator), so an absent field degrades the run rather than refusing it. The hard gates that do block the start are the clean tree, the green suite where a suite exists, and a well-formed dependency graph ([D6](artifacts/decision-log.md#d6-hitl-recognition-via-a-persisted-type-on-each-work-item), [D8](artifacts/decision-log.md#d8-independent-verification-before-commit), [D19](artifacts/decision-log.md#d19-input-validation-preconditions), [D21](artifacts/decision-log.md#d21-per-item-implementation-skill)).
  - The dependency graph across the items is well-formed: no cycles, no duplicate item identifiers, and every `Depends on` reference names an item present in the file ([D19](artifacts/decision-log.md#d19-input-validation-preconditions)).
  - The working tree is clean and the test suite is green before the run starts, so per-item commits stay clean and new breakage is distinguishable from pre-existing breakage. The run's own uncommitted planning artifacts (the spec, research, and plan the items reference, plus the work-items file itself) are the one exception: they do not block, because the preparation step commits them first ([D15](artifacts/decision-log.md#d15-start-preconditions-clean-tree-and-green-suite), [D22](artifacts/decision-log.md#d22-minimum-workspace-preparation)).
  - The operator runs the skill on a session model capable of the coordination role. The skill's own judgment runs on the operator's session model, so a weak session model degrades how it sequences items, reads sub-agent reports, and decides when to escalate ([D14](artifacts/decision-log.md#d14-model-selection-policy)).

## Primary Flow

1. **Prepare and validate (read-only).** The operator invokes the skill against a `work-items.md`. The skill first runs only read-only checks, so a refusal or a declined plan leaves the repository untouched ([D22](artifacts/decision-log.md#d22-minimum-workspace-preparation)): it determines the project's verification commands from the project's own configuration (the operator can confirm or override them) and checks the tooling they need is available (every required command resolves and can run); it confirms the working tree is clean apart from the run's own planning artifacts (the work-items file plus the spec, research, and plan files the items reference, the set it derives from those references and confirms with the operator before the first commit so nothing unrelated is folded in and nothing referenced is missed); where the project defines verification commands it confirms the suite is green, and a project with none takes the scope-check-only path it confirms with the operator instead of treating an absent suite as either vacuously green or a refusal ([D8](artifacts/decision-log.md#d8-independent-verification-before-commit), [D15](artifacts/decision-log.md#d15-start-preconditions-clean-tree-and-green-suite)); and it validates the items, a well-formed dependency graph, the required fields, and a valid implementation skill ([D19](artifacts/decision-log.md#d19-input-validation-preconditions)), building the run order from their stated dependencies. An empty file or one with no buildable items is a startup error, not an empty run. Any of these failing stops the run before anything is branched or committed.
2. **Confirm the plan, then set up.** The skill shows the operator the run plan (the effective run configuration the run will use (the review gate threshold, the fix-loop cap, the build/fix model, and the branch the per-item commits will land on, including an auto-derived branch name), followed by the items in dependency order, each marked as **unattended**, **needs a decision then runs unattended**, or **needs you to drive** (an interactive skill the operator steers in the foreground), and named with its implementation skill, with any item whose classification was defaulted because its marker was missing flagged as such, plus any items that will be skipped because a dependency is blocked) and waits for the operator to confirm, reorder (within the dependency order, which the skill enforces), mark items to skip (marking a skip re-renders the plan to show the dependents that skip now strands, before a fresh confirm, so the downstream cost is visible before the choice), or **decline** (which stops the run, having mutated nothing) before any work begins ([D25](artifacts/decision-log.md#d25-plan-preview-and-confirmation-before-the-run)). Only after the operator confirms does the skill mutate the repository: it creates the dedicated branch (or, on a resume, reads the run's branch from the ledger and continues on it rather than forking a new one, [D20](artifacts/decision-log.md#d20-item-to-commit-matching-and-resume-ledger-integrity)), commits the planning artifacts, and initializes the resume ledger as a marked bookkeeping commit (each of these preparation steps is idempotent on re-entry, so an already-created branch or an already-committed planning-artifact set left by a preparation a compaction interrupted before the marker was set is treated as already complete rather than as a "nothing to commit" failure), and only then sets the run-active marker the re-grounding routine reads, so a preparation failure never leaves a marker without a ledger ([D20](artifacts/decision-log.md#d20-item-to-commit-matching-and-resume-ledger-integrity), [D22](artifacts/decision-log.md#d22-minimum-workspace-preparation), [D26](artifacts/decision-log.md#d26-the-re-grounding-routine)); per-item commits never land on a shared mainline by default.
3. The skill processes items **one at a time** in dependency order ([D2](artifacts/decision-log.md#d2-serial-one-item-at-a-time-processing)). For each item that can run unattended, it drives a fixed per-item loop ([D3](artifacts/decision-log.md#d3-per-item-loop-shape)):
   1. **Build.** The skill dispatches an implementer sub-agent to build the item, handing it the work item, the spec and contract sections the item references, the project's conventions, an explicit instruction naming the item's declared implementation skill to run (defaulting to `tdd`; only non-interactive skills that produce code changes reach this step, [D21](artifacts/decision-log.md#d21-per-item-implementation-skill)), and the exact compact report format it must return ([D12](artifacts/decision-log.md#d12-driver-defined-dispatch-contract-and-compact-returns)). The sub-agent returns that compact report (status, files changed, the final gate result, any blocker, and the observed test-failure-then-pass evidence when the skill is `tdd`), short enough for the skill to decide from the report alone without reading the diff. A build that produces no file changes is escalated, not committed.
   2. **Verify.** The skill does not trust the sub-agent's "all green." It independently re-runs the project's own verification commands (tests, type-checking, any required code-generation or sync step, lint, build) and trusts those results over the sub-agent's self-report or editor diagnostics ([D8](artifacts/decision-log.md#d8-independent-verification-before-commit)). It also inspects the set of changed files against the item's declared expected paths, excluding files the project ignores, any code-generation or sync output the verification step itself produced, and the skill's own resume-ledger writes; a change to a file outside the declared paths is surfaced for the operator to accept (a legitimate cross-slice edit) or reject, and an acceptance holds for the rest of that item's loop so the operator is not asked again each fix round, recorded durably in the ledger so a re-grounding after a mid-item compaction restores it rather than resurfacing the already-approved change as a fresh scope escape ([D8](artifacts/decision-log.md#d8-independent-verification-before-commit), [D20](artifacts/decision-log.md#d20-item-to-commit-matching-and-resume-ledger-integrity), [D26](artifacts/decision-log.md#d26-the-re-grounding-routine)).
   3. **Review.** The skill runs a review of the item's changes as a self-contained stage, giving it the work item and the spec sections the item references so it can judge the change against what the item asked for. The review runs at the same specialist coverage a manual review would apply, checks both code quality and that the change does not go beyond what the item asked for, **persists a durable full record of its findings**, and returns a **condensed verdict** listing its findings by severity, complete at and above the gate threshold and attesting that the review ran at full coverage, rather than a full report ([D11](artifacts/decision-log.md#d11-full-review-fidelity-preserved), [D12](artifacts/decision-log.md#d12-driver-defined-dispatch-contract-and-compact-returns), [D27](artifacts/decision-log.md#d27-durable-review-record-condensed-verdict-gate-and-spot-check)). The skill evaluates the commit gate on that verdict and may spot-check the durable record against it; the spot-check is optional (it has no required trigger), but when it does run it makes a defined commitment rather than being a no-op: a spot-check that finds the record and the verdict disagree (a finding at or above the threshold present in the record but missing from the verdict) is treated as an untrustworthy verdict and escalated as a review failure, the same fail-closed handling as an unattestable verdict ([D27](artifacts/decision-log.md#d27-durable-review-record-condensed-verdict-gate-and-spot-check)). Because the spot-check may not run, the gate's bounded trust does not rest on it; this trust is deliberate, because unlike the build result, which the skill re-runs to verify, a review is a judgment the skill cannot re-run, so what bounds it is the verdict's required completeness, its coverage attestation, and the re-review each fix round ([D8](artifacts/decision-log.md#d8-independent-verification-before-commit), [D27](artifacts/decision-log.md#d27-durable-review-record-condensed-verdict-gate-and-spot-check)). A verdict the skill cannot trust as a clean pass, empty without a coverage attestation, reporting a partially-covered panel, or not evaluable against the threshold, is escalated as a review failure rather than treated as a clear gate ([D27](artifacts/decision-log.md#d27-durable-review-record-condensed-verdict-gate-and-spot-check), [D17](artifacts/decision-log.md#d17-no-return-and-stall-handling)).
   4. **Fix to the gate.** If the review reports any finding at or above the configured severity threshold (by default, any Critical or Warning finding ([D4](artifacts/decision-log.md#d4-completion-gate-severity-threshold))), the skill runs a bounded fix loop: it has the item fixed by a sub-agent that works from the original build context and the review's durable record (and can read the codebase for findings that reach beyond the change), re-verifies, and, only when re-verification passes, re-reviews, repeating until the gate clears or the configured cap is reached; a fix round whose re-verification fails counts as a not-cleared round and loops to the next fix without a review, so the panel never reviews known-broken code and the round's durable record reflects that verification did not pass and no review ran ([D5](artifacts/decision-log.md#d5-bounded-fix-loop-cap-then-escalate), [D13](artifacts/decision-log.md#d13-fix-round-context-preservation), [D27](artifacts/decision-log.md#d27-durable-review-record-condensed-verdict-gate-and-spot-check)).
   5. **Commit.** Once verification is green and the review reports no finding at or above the threshold, the skill commits the completed item as a single clean code commit following the project's commit convention, then records a separate marked bookkeeping commit marking the item done (with a reference to the code commit and the review-record location), and reports the commit's short reference to the operator ([D9](artifacts/decision-log.md#d9-one-commit-per-completed-item), [D20](artifacts/decision-log.md#d20-item-to-commit-matching-and-resume-ledger-integrity)). It then advances to the next item.
4. The skill repeats until every item is complete or stopped, then reports the completion summary: the branch name, each item's outcome (built and committed with its commit reference, committed over residual findings with a gate override flagged as such and pointing at its review record, skipped, escalated, or not started because a dependency was blocked), and the next action for the operator (review and push the branch, optionally running the offered cleanup that drops the marked bookkeeping commits to leave a clean per-item code history; the cleanup rewrites history and ends the ability to resume, and, because the override flags and review-record pointers ride on those marked bookkeeping commits, it also drops the on-branch record of which items shipped over residual findings, so the summary warns that running the cleanup erases that override audit trail (the durable review records themselves survive the cleanup, being kept independently of the dropped commits) and the operator preserves what they need before sharing; it is offered only once the run is fully complete, and a partial run's summary instead warns against dropping those commits by hand, since doing so forecloses the operator's own resume; sharing the branch is the operator's step). A fully complete run also clears the run-active marker, so the re-grounding trigger goes quiet ([D9](artifacts/decision-log.md#d9-one-commit-per-completed-item), [D20](artifacts/decision-log.md#d20-item-to-commit-matching-and-resume-ledger-integrity), [D26](artifacts/decision-log.md#d26-the-re-grounding-routine)).

## Alternate Flows and States

### Item needs a human before it starts

- **Entry condition:** the next item is marked as needing human involvement before work begins, or its declared implementation skill is interactive (it interviews or asks as it goes and so cannot run unattended in a sub-agent) ([D21](artifacts/decision-log.md#d21-per-item-implementation-skill)).
- **Decision gate (before any work):** the skill pauses when it reaches the item, presents it (naming the dependent items a skip would also strand, so the downstream cost is visible before the choice), and asks **proceed**, **defer** (not now: the run continues to the next independent item and this one is re-surfaced on a later resume, recorded durably like any defer so it is not silently re-attempted, [D24](artifacts/decision-log.md#d24-skip-and-defer-decisions-persist-across-resume)), or **skip** before any effort is invested, so a skip or defer never wastes work the operator has already done, and an external-prerequisite item whose prerequisite is not ready yet has a "come back to this one" path rather than only proceed-or-skip. On **skip**, the operator owns the item outside the skill; the skill records the choice durably and starts no item that depends on the skipped one ([D6](artifacts/decision-log.md#d6-hitl-recognition-via-a-persisted-type-on-each-work-item), [D24](artifacts/decision-log.md#d24-skip-and-defer-decisions-persist-across-resume)).
- **On proceed:**
  - For a **decision-needed or external-prerequisite item with a non-interactive skill**, the operator does whatever the item needs a human for and signals when it is done. If that produced a decision or an edit to record, the operator records it in the spec or the work item and the skill commits that edit as a marked planning commit so it is durable (a resume will not discard it) and is not flagged as the item's scope escape; if there is nothing to record (an external setup, a design review the operator just absorbs), the skill proceeds on the operator's signal with no planning commit ([D6](artifacts/decision-log.md#d6-hitl-recognition-via-a-persisted-type-on-each-work-item)). It then re-grounds its own context (see the context guard below) and builds the item through the full per-item loop (build with any recorded decision as context, verify, review, fix, commit).
  - For an **interactive-skill item**, the skill runs that skill **in the foreground**: the orchestrator invokes the interactive implementation skill in the operator's session, signals that the operator is now steering and the run is paused until they confirm, and the operator steers the interview through it to produce the work ([D21](artifacts/decision-log.md#d21-per-item-implementation-skill)). If that item also carried a decision to record (it was both marked human-required and interactive), the operator records the decision and the skill commits it as a marked planning commit before the interview's work is finalized, so a decision made during an interactive item is durable exactly as on the non-interactive proceed path rather than being lost on a resume ([D6](artifacts/decision-log.md#d6-hitl-recognition-via-a-persisted-type-on-each-work-item)). When the work is done, the skill asks the operator to **confirm the work is complete and choose how to proceed**: *finish the item autonomously* (re-ground, then run verify, review, fix, and commit unattended, where a gate-blocking finding is fixed by a sub-agent that may alter the hand-built work to clear the gate), or *pause after each review* (run verify and review, then pause on the verdict so the operator can steer before each fix round and the commit, pausing every round until the gate clears or the cap is reached, each pause offering to keep steering (the operator makes manual changes and sends a message, which runs the next verify-and-review cycle), finish autonomously, **defer or skip this item** (the run continues to the next independent item), or **stop the run** (everything halts), the same defer-versus-stop-the-run split the blocker menu uses, so "stop" is never ambiguous between abandoning the item and halting the run). Review always runs; there is no commit-without-review path. The skill records the chosen mode in the durable ledger before it re-grounds, then resumes the item at verify without dispatching a build, working any fix round from the work item, the review record, the diff, and the codebase rather than an implementer's build report ([D13](artifacts/decision-log.md#d13-fix-round-context-preservation), [D26](artifacts/decision-log.md#d26-the-re-grounding-routine), [D27](artifacts/decision-log.md#d27-durable-review-record-condensed-verdict-gate-and-spot-check)). At the commit step, if the interactive skill committed its own work (whether as one commit or several), the skill reviews the cumulative diff of all the item's commits (not only the last, so no self-committed change escapes review), treats them as the item's code commits, and records the commit range, or, after any fix round, the final commit produced for the item, in the done marker rather than a single original reference or an empty commit ([D9](artifacts/decision-log.md#d9-one-commit-per-completed-item)). If the operator reports the work is not done (or the tree is unexpectedly unchanged), the skill keeps the item paused or skips it at the operator's direction rather than committing nothing.
- **Context guard:** handling a human-required item inline erodes the orchestrator's context, and the orchestrator itself conducts the item's verify, review, fix, and commit stages, so it runs its **re-grounding** routine **at the resume point, before conducting those stages**, not only at the next-item boundary. This is the same routine it runs after an automatic compaction or a resume after a pause: it records the item's handling in the durable ledger and re-grounds (re-reading the ledger, reloading its own instructions, and re-establishing the run's state); it recommends the operator run a manual compaction before and after a human-required item ([D26](artifacts/decision-log.md#d26-the-re-grounding-routine)).

### A blocker is raised

- **Entry condition:** a sub-agent escalates a blocker it cannot resolve (the spec contradicts the item, the acceptance criteria are unsatisfiable or mutually contradictory, or the item cannot be built as written), or the skill detects one itself (the fix loop hit its cap, a change looks like it escaped the item's slice, the build produced no changes, or a later item's verification fails because of a regression in an already-committed earlier item).
- **Sequence:** the skill stops advancing and presents the blocker using the consistent escalation frame (the status line, the one-sentence reason, and the labeled options first), with the supporting evidence (which sub-agent raised it, the relevant spec or acceptance criteria, and the raw verification output or residual findings) placed after the options rather than between the reason and the choice, so a returning operator sees what to decide before scrolling through a wall of output. For a suspected cross-item regression the evidence names which tests were green at the earlier item's commit and are now failing; identifying the specific earlier item that regressed is a triage or operator step, not a fact the whole-suite verify alone establishes. It offers an optional deeper triage pass, naming what triage does (it characterizes the blocker against the spec and architecture and proposes options) so the operator can decide whether to run it; triage runs only when chosen, not automatically on every item ([D7](artifacts/decision-log.md#d7-blocker-detection-escalate-on-signals-plus-on-demand-triage)).
- **Exit:** the operator chooses from the options applicable to the blocker that fired (the menu is filtered to those, rather than presenting every option on every blocker), grouped by consequence. *Continue* is split by how weighty it is: **override the gate** (commit despite residual findings at or above the threshold, the heavy choice, surfaced as such and recorded so the commit is flagged as an override in the ledger and the completion summary and points at its review record) versus **accept a flagged change** as intentional and commit (the benign cross-slice case). *Modify and retry* amends the spec, changes the item, or runs more fix rounds. *Repair upstream* fixes the already-committed earlier item in the current working context and commits the fix, separately or folded in with the current item, the whole-suite verify still gating it; when the fix is folded in, the review of that commit is given both the current item's and the repaired item's work-item and spec context so the upstream fix is reviewed against its own acceptance criteria and not only the current item's scope, and the repaired item's done marker is annotated to note its fix landed in the current commit so the ledger does not misrepresent it as untouched; to attribute the fix to the earlier item in history the skill offers `git commit --fixup` plus `rebase --autosquash` as part of the end-of-run cleanup rather than mid-run, since a mid-run history rewrite would invalidate the commit references the resume ledger records ([D7](artifacts/decision-log.md#d7-blocker-detection-escalate-on-signals-plus-on-demand-triage), [D20](artifacts/decision-log.md#d20-item-to-commit-matching-and-resume-ledger-integrity)). And the operator can *defer this item* (the run continues to the next independent item, after the skill returns the working tree to the last clean committed baseline, inspecting and confirming before discarding and never discarding an interactive item's hand-built work, so the deferred item's uncommitted work is not folded into the next item and the deferred item is rebuilt from scratch when re-surfaced, [D10](artifacts/decision-log.md#d10-resume-discard-partial-work-and-rebuild)) or *stop the run* entirely. The skill records the decision durably ([D24](artifacts/decision-log.md#d24-skip-and-defer-decisions-persist-across-resume)) and either resumes or halts.

### Operator stops the run cleanly

- **Entry condition:** the operator sends a stop request at any point during the run. The skill acknowledges the stop on receipt and records it durably, so a compaction during the drain window does not drop the pending stop and let the run continue past the point the operator asked it to halt, and it checks for a pending stop request before each sub-agent dispatch (the next build, fix round, or review), not only at item boundaries, so the stop takes effect at the next safe point rather than waiting out a whole item ([D18](artifacts/decision-log.md#d18-clean-stop-affordance)).
- **Sequence:** the skill finishes the in-progress item to its gate, committing it if it passes or escalating it if it does not. A stop pending before the item's review does not skip review: review runs, the gate is evaluated, and only then does the stop take effect, so no item is committed or escalated on a review that did not run. If the stop arrives mid-fix-loop, it completes the current fix round, evaluates the gate once, and then commits or escalates rather than starting another round. It then halts instead of starting the next item.
- **Exit:** the skill emits the completion summary; the repository is left in a known state on the run's branch with the completed items committed, and the summary states the two forward actions available: resume by re-invoking the skill on the same work-items file (the marker is deliberately left set for this), or abandon the run, an explicit end choice that clears the run-active marker and records the run as abandoned in the ledger so the re-grounding trigger goes quiet, without forcing the operator to complete the run or hand-edit configuration to silence it. The run-active marker stays set on a plain clean stop, so a later resume still re-grounds; a fully complete run or an explicit abandon clears it ([D26](artifacts/decision-log.md#d26-the-re-grounding-routine)).

### Resuming a partially complete run

- **Entry condition:** the operator re-invokes the skill on a `work-items.md` whose items are partly done.
- **Sequence:** the skill reads the committed resume ledger (its record of done, skipped, and deferred items), honors previously skipped or deferred items rather than silently re-attempting them (re-surfacing them for the operator when their blocking reason may have changed), and resumes at the first item that is neither complete nor deliberately skipped ([D10](artifacts/decision-log.md#d10-resume-discard-partial-work-and-rebuild), [D20](artifacts/decision-log.md#d20-item-to-commit-matching-and-resume-ledger-integrity), [D24](artifacts/decision-log.md#d24-skip-and-defer-decisions-persist-across-resume)). It shows a resume summary (done, skipped, deferred, remaining, and the effective run configuration and branch it restores from the ledger, so the operator sees the gate, cap, model, and branch the resumed items will run under) rather than replaying the full plan preview, so the remaining items are gated exactly as the committed ones ([D25](artifacts/decision-log.md#d25-plan-preview-and-confirmation-before-the-run), [D20](artifacts/decision-log.md#d20-item-to-commit-matching-and-resume-ledger-integrity)). If the recorded branch is missing, the checkout lacks the run's prior commits, or a done entry's recorded commit reference no longer resolves in history (an out-of-band reset, cherry-pick, or rebase), it surfaces that and asks the operator rather than continuing on the wrong base or reporting an item done whose commit is gone ([D20](artifacts/decision-log.md#d20-item-to-commit-matching-and-resume-ledger-integrity)). An item left with uncommitted, in-progress work has the skill inspect that work and its in-progress commits and decide whether it is complete, gate-passed work to resume from or partial, unverified work to drop, confirming with the operator (and surfacing what it found) before discarding anything; a foreign or out-of-band commit in the in-progress window is inspected, not blindly trusted as the item's completion, and the operator is asked when the call is not clean. The inspection distinguishes states the discard default would otherwise flatten: a complete, verified build whose review had not yet run is kept and re-reviewed, mirroring the review-stall handling ([D17](artifacts/decision-log.md#d17-no-return-and-stall-handling)), rather than discarded as if unverified, with the re-review's durable-record location committed to the ledger before any fix round so a compaction in that window does not strand the fix without the findings it must address ([D26](artifacts/decision-log.md#d26-the-re-grounding-routine)); and an item whose recorded-decision planning commit landed but whose build never started is resumed at build with that decision kept rather than mistaken for partial work. Genuinely partial work (an interrupted build, or a build plus a partial fix) is discarded and the item rebuilt, but an interactive item's hand-built work is never discarded without the operator's explicit agreement. This partial-work inspection and any discard complete before the skill re-establishes the green-suite baseline ([D15](artifacts/decision-log.md#d15-start-preconditions-clean-tree-and-green-suite)), so leftover partial work cannot redden the baseline and be misread as a regression ([D10](artifacts/decision-log.md#d10-resume-discard-partial-work-and-rebuild), [D20](artifacts/decision-log.md#d20-item-to-commit-matching-and-resume-ledger-integrity)).
- **Exit:** the run continues from the first incomplete item; already-complete and deliberately-skipped items are not rebuilt.

## Edge Cases and Failure Modes

| Condition | Required Behavior |
|-----------|-------------------|
| Working tree is dirty at start with changes unrelated to the run's planning artifacts | The skill refuses to start and asks the operator to commit or stash first; the unrelated-change check runs before the planning-artifact commit so nothing extra is folded in. The run's own spec, research, plan, and work-items file are committed as the first commit instead of blocking ([D15](artifacts/decision-log.md#d15-start-preconditions-clean-tree-and-green-suite), [D22](artifacts/decision-log.md#d22-minimum-workspace-preparation)). |
| Test suite is already red at start | The skill refuses to start, because it cannot tell newly introduced breakage from pre-existing breakage, and the refusal names the remedy (get the suite green, or narrow the configured verification command to exclude the known-failing tests, then re-invoke) rather than only the reason ([D15](artifacts/decision-log.md#d15-start-preconditions-clean-tree-and-green-suite)). |
| Dependency graph is malformed, or an item declares an invalid implementation skill | The skill refuses to start and names the offending items: a cycle, duplicate identifiers, a `Depends on` to a missing item, or a declared skill that is not a code-producing implementation skill ([D19](artifacts/decision-log.md#d19-input-validation-preconditions)). |
| The work-items file is empty or contains no buildable items | The skill reports a startup error and stops before any branch or commit, rather than showing an empty preview, committing an empty ledger, and reporting zero items done ([D19](artifacts/decision-log.md#d19-input-validation-preconditions)). |
| A required field is missing (the human-involvement marker or the expected-paths declaration) | The skill does not refuse; it applies the defined fallback and proceeds with a surfaced warning, treating a missing marker as unattended and falling back to a review-level-only scope check (after asking the operator) for a missing expected-paths declaration ([D19](artifacts/decision-log.md#d19-input-validation-preconditions), [D6](artifacts/decision-log.md#d6-hitl-recognition-via-a-persisted-type-on-each-work-item), [D8](artifacts/decision-log.md#d8-independent-verification-before-commit)). |
| The operator edits the committed spec or work-items file mid-run (recording a decision or amending the spec) | The skill commits that edit as a marked planning commit so it is durable and is excluded from the item's scope check; it is never left uncommitted to be discarded by a resume or flagged as a scope escape ([D6](artifacts/decision-log.md#d6-hitl-recognition-via-a-persisted-type-on-each-work-item), [D8](artifacts/decision-log.md#d8-independent-verification-before-commit), [D10](artifacts/decision-log.md#d10-resume-discard-partial-work-and-rebuild)). |
| A preparation step fails: the branch cannot be created, a required verification command will not run, the planning-artifact commit is rejected (for example by a pre-commit hook), or a git operation does not return | The skill reports exactly what failed and stops before processing any item, rather than proceeding without a branch, without working tooling, or without the planning commit ([D22](artifacts/decision-log.md#d22-minimum-workspace-preparation), [D17](artifacts/decision-log.md#d17-no-return-and-stall-handling)). |
| Some required tooling is available and some is not (for example tests run but the type-checker is missing) | The skill treats any missing required command as "tooling unavailable" and stops, naming every missing command, rather than silently running a weakened gate ([D22](artifacts/decision-log.md#d22-minimum-workspace-preparation)). |
| No verification commands are configured for the project at all | Distinct from missing tooling: the skill surfaces this as a configuration choice and asks the operator to confirm before proceeding with a scope-check-only run ([D8](artifacts/decision-log.md#d8-independent-verification-before-commit)). |
| A verification command fails to execute mid-run (the tool is missing or removed, a required service is down, the disk is full) | The skill treats this as a tooling or environment problem, surfacing it the way the start-time tooling check would, rather than feeding it into the fix loop as if the code were at fault ([D8](artifacts/decision-log.md#d8-independent-verification-before-commit), [D22](artifacts/decision-log.md#d22-minimum-workspace-preparation)). |
| Implementer reports green but independent verification fails | The skill does not commit; it treats the failure as a fix-loop round and, if unresolved within the cap, escalates, trusting the project's own checks over the self-report ([D8](artifacts/decision-log.md#d8-independent-verification-before-commit)). |
| A later item's verification fails because of a regression in an already-committed earlier item | The skill escalates with evidence showing which tests were green at the earlier item's commit and are now failing, and offers to repair the earlier item in the current working context (committing the fix separately or folded in, the whole-suite verify gating it, with an optional `commit --fixup` plus `rebase --autosquash` for history) rather than churning the current item's fix loop against a cause it cannot fix ([D7](artifacts/decision-log.md#d7-blocker-detection-escalate-on-signals-plus-on-demand-triage)). |
| A dispatched build or fix sub-agent, the self-contained review stage, or a verification command does not return within a reasonable bound | The skill does not wait indefinitely; it surfaces the stall, names the cause where identifiable (a turn-budget exhaustion versus an operational hang, acknowledging a stall deep inside the review stage may be reportable only as "review did not return"), describes the relevant state (the working tree for a build, fix, or verification stall; for a review stall, what the stage could report, since review does not change the tree), and offers to retry, skip the item, or stop the run, leaving the repository in a known state; the stronger-model retry helps the build and fix path, not the review panel, whose models are `code-review`'s ([D17](artifacts/decision-log.md#d17-no-return-and-stall-handling), [D14](artifacts/decision-log.md#d14-model-selection-policy)). |
| A dispatched build or fix sub-agent, or the review stage, returns an error or an unusable non-report rather than hanging (a model or API outage, a rate-limit, a network partition) | The skill classifies this as a tooling or environment problem, on the same footing as a verification command that fails to execute, and surfaces it with retry, skip, or stop, rather than feeding it into the fix loop or misreading a missing report as "the build produced no changes" ([D17](artifacts/decision-log.md#d17-no-return-and-stall-handling), [D8](artifacts/decision-log.md#d8-independent-verification-before-commit), [D21](artifacts/decision-log.md#d21-per-item-implementation-skill)). |
| The review stage returns but its verdict cannot be trusted as a clean pass: empty with no coverage attestation, reporting that only part of the specialist panel ran, or not evaluable against the severity threshold | The skill does not treat it as a cleared gate; it escalates it as a review failure (retry the review, skip the item, or stop the run), the same fail-closed handling as a review that never returns, and never commits unreviewed or partially-reviewed work ([D27](artifacts/decision-log.md#d27-durable-review-record-condensed-verdict-gate-and-spot-check), [D17](artifacts/decision-log.md#d17-no-return-and-stall-handling)). |
| Code-generation or sync output, lock files, or ignored files change during verification | These are not treated as out-of-slice changes; the changed-file inspection excludes files the project ignores, any generation or sync output the verification step itself produced, and the skill's own resume-ledger writes ([D8](artifacts/decision-log.md#d8-independent-verification-before-commit)). |
| An item's change legitimately touches another item's files, or renames or moves a file | The skill surfaces the cross-slice or out-of-declared-path change for confirmation and offers to accept it as intentional and commit; a deleted declared path counts as in-scope, and a created path outside the declared set is surfaced with its rename context rather than treated as a blind escape ([D8](artifacts/decision-log.md#d8-independent-verification-before-commit), [D7](artifacts/decision-log.md#d7-blocker-detection-escalate-on-signals-plus-on-demand-triage)). |
| A change looks unrelated to the item, or a sub-agent left a stray file behind | The skill does not commit; it surfaces the suspected scope escape for the operator to accept or reject ([D8](artifacts/decision-log.md#d8-independent-verification-before-commit)). |
| Build can never reach a passing test | The skill stops the item, surfaces it as a blocker, and offers triage rather than looping forever ([D7](artifacts/decision-log.md#d7-blocker-detection-escalate-on-signals-plus-on-demand-triage)). |
| An interactive-skill item's tree is unexpectedly unchanged after the operator confirms the work is complete | The skill surfaces the unchanged tree to the operator and follows their direction (re-run the interactive skill, skip the item, or treat it as a blocker), consistent with the human-needed flow, rather than committing nothing ([D21](artifacts/decision-log.md#d21-per-item-implementation-skill), [D6](artifacts/decision-log.md#d6-hitl-recognition-via-a-persisted-type-on-each-work-item)). |
| Verification keeps failing because of an intermittent test, not the item's change | The escalation includes the raw verification output so the operator can recognize flakiness; a cap-reached escalation is reported as "gate not cleared," reserving "unsatisfiable" for the build-never-passes case ([D5](artifacts/decision-log.md#d5-bounded-fix-loop-cap-then-escalate), [D17](artifacts/decision-log.md#d17-no-return-and-stall-handling)). |
| Fix loop reaches its cap without clearing the gate | The skill stops the item and escalates with the residual findings listed, and the escalation offers running more fix rounds as one option ([D5](artifacts/decision-log.md#d5-bounded-fix-loop-cap-then-escalate)). |
| The operator defers (or otherwise continues the run past) an item that has uncommitted work in the tree (a fix-loop-cap escalation, a suspected scope escape, an unbuildable item) | Before the run continues to the next independent item, the skill returns the working tree to the last clean committed baseline, inspecting and confirming before discarding and never discarding an interactive item's hand-built work, so the deferred item's uncommitted work is not folded into the next item's commit; the deferred item is rebuilt from scratch when re-surfaced ([D7](artifacts/decision-log.md#d7-blocker-detection-escalate-on-signals-plus-on-demand-triage), [D10](artifacts/decision-log.md#d10-resume-discard-partial-work-and-rebuild), [D24](artifacts/decision-log.md#d24-skip-and-defer-decisions-persist-across-resume)). |
| An item depends on an item that is blocked or skipped | The skill does not start the dependent item; it emits a note naming the blocked item and the skipped dependents, then continues autonomously to the next independent item that can still run ([D2](artifacts/decision-log.md#d2-serial-one-item-at-a-time-processing)). |
| Every remaining item is blocked by a skipped or blocked dependency (including the degenerate case of zero items committed) | The skill stops and the completion summary states the run as partially complete, naming how many items were committed and how many were not started and why, rather than ending silently ([D2](artifacts/decision-log.md#d2-serial-one-item-at-a-time-processing)). |
| Review surfaces few or no findings on a tiny slice because of its size calibration | The gate is evaluated against the findings the review actually surfaces at the size it assigns the slice; the skill does not invent findings or force a larger review ([D4](artifacts/decision-log.md#d4-completion-gate-severity-threshold)). |
| Operator interrupts, or a build or fix sub-agent stalls, mid-item (including during a fix round) | The item's uncommitted work is unverified (during a fix round it is the original build plus a partial fix); the skill inspects it and, for genuinely partial work, discards it after confirming with the operator and rebuilds rather than committing a half-finished or mixed-state change, while not blindly discarding work that inspection shows is complete and gated, nor an interactive item's hand-built work without explicit agreement. A stall during *review* is the exception: the build is already verified and review writes nothing to the tree, so the retry re-runs review only and keeps the verified build ([D10](artifacts/decision-log.md#d10-resume-discard-partial-work-and-rebuild), [D17](artifacts/decision-log.md#d17-no-return-and-stall-handling)). |
| A code commit, or a marked bookkeeping commit (a done marker, a skip, or a defer), is rejected or fails mid-run (a pre-commit hook, a lock, a full disk) | The skill does not advance and does not discard the verified, reviewed work; it surfaces the failure and its remedy and halts fail-closed. If the code commit itself failed, the work is still in the tree; if the code committed but its done marker failed, the code is already in git and the missing marker is reconciled on resume by inspection rather than by re-applying the change. Same class as a rejected preparation commit ([D20](artifacts/decision-log.md#d20-item-to-commit-matching-and-resume-ledger-integrity), [D22](artifacts/decision-log.md#d22-minimum-workspace-preparation)). |
| On resume the committed ledger cannot be parsed (merge-conflict markers, truncation, corruption) | The skill treats it as a fatal resume error: it surfaces the raw ledger content and offers abort-to-reconcile rather than guessing, because committed items may already exist on the branch ([D20](artifacts/decision-log.md#d20-item-to-commit-matching-and-resume-ledger-integrity)). |
| On resume a done entry's recorded commit reference no longer resolves (an out-of-band reset, cherry-pick, or history rewrite moved or dropped the commit) | The skill does not accept the item as done on the strength of the marker alone; it surfaces the unresolved reference and asks the operator to reconcile, the same class as a missing branch or a checkout lacking the run's prior commits ([D20](artifacts/decision-log.md#d20-item-to-commit-matching-and-resume-ledger-integrity)). |
| A builder sub-agent writes or modifies the resume ledger file | The ledger's exclusion from the scope check covers only the skill's own bookkeeping writes; a builder's write to it is surfaced as a scope escape for the operator to accept or reject, like any other out-of-path change ([D8](artifacts/decision-log.md#d8-independent-verification-before-commit), [D20](artifacts/decision-log.md#d20-item-to-commit-matching-and-resume-ledger-integrity)). |
| The session auto-compacts mid-run, between or within an item, possibly truncating the skill's own instructions | The orchestrator does not trust its post-compaction recollection of run state; its re-grounding routine fires (triggered durably from outside the skill body, since compaction can truncate the skill), re-reads the committed ledger, and reloads its instructions before the next dispatch, so it never rebuilds a committed item or skips an unbuilt one. When it fires mid-item and finds uncommitted in-progress work for the current item, it routes that work through the same inspect-decide-ask / discard-and-rebuild handling the resume flow uses ([D10](artifacts/decision-log.md#d10-resume-discard-partial-work-and-rebuild)) rather than committing a mixed build-plus-partial-fix tree. If that re-read or reload cannot complete (an unparseable or unreachable ledger, or the skill cannot reload), it halts fail-closed and surfaces the state rather than proceeding on guessed state, the same fail-closed handling as an unparseable ledger on resume ([D26](artifacts/decision-log.md#d26-the-re-grounding-routine), [D20](artifacts/decision-log.md#d20-item-to-commit-matching-and-resume-ledger-integrity)). |
| The session auto-compacts during preparation, before the run-active marker is set | The re-grounding trigger cannot fire yet (no marker present), so on re-invoke the skill re-enters preparation idempotently: an already-created branch and an already-committed planning-artifact set are treated as already complete rather than as a "nothing to commit" preparation failure, and it proceeds to ledger-init and marker-set on the already-prepared branch ([D22](artifacts/decision-log.md#d22-minimum-workspace-preparation), [D26](artifacts/decision-log.md#d26-the-re-grounding-routine)). |
| The operator pauses the run and resumes it later by sending a new message (no compaction) | The orchestrator recognizes it is continuing an in-progress run rather than starting cold: it runs the re-grounding routine, announces where it is, and interprets the new message in that resumed context ([D26](artifacts/decision-log.md#d26-the-re-grounding-routine)). |
| The session auto-compacts while a foreground interactive item is mid-interview | The interview state is not in the ledger, so re-grounding cannot reconstruct it; the skill surfaces the interrupted interactive item and offers to re-invoke the interactive skill or, if the operator confirms the hand-built work is already complete, treat it as confirmed and resume at verify, keeping the item in progress rather than dropping it or silently restarting it ([D26](artifacts/decision-log.md#d26-the-re-grounding-routine), [D21](artifacts/decision-log.md#d21-per-item-implementation-skill), [D10](artifacts/decision-log.md#d10-resume-discard-partial-work-and-rebuild)). |
| On resume, the committed resume ledger and the work-items file disagree: an item recorded in the ledger is no longer present in the file, or the operator edited or renumbered items between runs | The skill does not silently skip or rebuild; it surfaces the mismatch with the unmatched ledger entries and items and offers a clear option set, each option stating its consequence for the already-committed items and ledger (so "restart the run from the beginning" names what it does to the existing commits rather than leaving it to be inferred): proceed from the first unmatched item, restart the run from the beginning, or abort so the operator can reconcile manually ([D20](artifacts/decision-log.md#d20-item-to-commit-matching-and-resume-ledger-integrity)). |
| On resume, a different work-items file drives a branch that already carries a prior run's ledger (a total, zero-shared-identifier mismatch) | The skill treats this as distinct from an edited-items mismatch: rather than offering "proceed from the first unmatched item" (which would build the new file's items atop the old file's unrelated commits and report the old items as done), it surfaces a **start a fresh run on this branch** option (initializing a new ledger) alongside switch-branch and abort ([D20](artifacts/decision-log.md#d20-item-to-commit-matching-and-resume-ledger-integrity)). |

## User Interactions

- **Affordances:** the operator invokes the skill with a work-items file and optional inputs: the review gate threshold, the fix-loop cap, a model override for the build and fix sub-agents, and the branch name. The skill otherwise sets the build/fix model explicitly for what those sub-agents do rather than letting them inherit the operator's session model; the models used inside review are governed by the `code-review` skill ([D14](artifacts/decision-log.md#d14-model-selection-policy)). After the plan preview ([D25](artifacts/decision-log.md#d25-plan-preview-and-confirmation-before-the-run)) the operator confirms, reorders, or marks items to skip. During a run the operator can send a stop request that the skill acknowledges on receipt, telling the operator the in-flight stage will finish to the item's gate before the stop takes effect (so continued output is expected, not a sign the stop was missed), and applies at the next safe point, before the next sub-agent dispatch ([D18](artifacts/decision-log.md#d18-clean-stop-affordance)). At each escalation the operator can accept or decline the offered triage pass, accept a flagged change and commit it, choose how to resolve a blocker or resume mismatch, decide proceed, defer, or skip on a human-required item before doing the work, confirm that an interactive item's work is complete and choose how the skill resumes it (finish autonomously, or pause after each review), retry a stall (including on a stronger model), mark a not-yet-reached item to skip, and abandon a stopped run to clear its re-grounding marker. Around a human-required item the skill recommends a manual compaction so the inline work does not crowd its context, and re-grounds itself from its progress ledger before it resumes conducting the item ([D26](artifacts/decision-log.md#d26-the-re-grounding-routine)).
- **Feedback:** the skill keeps an unattended run legible. It narrates the preparation steps as they happen, shows a per-item status header (the item, its position in the run order, and the phase beginning) and a dispatch notification when each sub-agent it dispatches starts, streams each such sub-agent's compact report (the review stage runs self-contained, so the skill surfaces its dispatch and its returned verdict rather than its inner panel member by member), reports each commit's short reference at commit time, emits a one-line run summary at each item boundary (done, remaining, blocked), notes whenever items are skipped because a dependency is blocked, and ends with the completion summary. Because a healthy sub-agent is silent between its dispatch notification and its compact report, the skill also keeps the run's current state legible at a glance (working, or awaiting the operator) and emits an active attention signal when the run transitions to awaiting operator input, so an operator who stepped away during an unattended stretch is drawn back at a decision point rather than discovering the wait later.
- **Escalation frame:** every pause uses a consistent shape so the operator can re-orient quickly: a status line (which item and phase, and its position in the run order with a done/remaining/blocked recap, the same run position the per-item header carries, so an operator weighing a run-wide option like stopping the run has that context without scrolling back), a one-sentence reason, an expectedness marker (a routine, preview-anticipated pause such as a human-required item, versus an unexpected one such as a blocker or a stall), and an explicit labeled list of options grouped by consequence, with any raw supporting evidence (verification output, residual findings) placed after the options rather than between the reason and the choice so the actionable element is not buried under a wall of output. Every such pause is recorded durably the moment the run transitions to awaiting the operator (the item, the pause kind, the evidence pointer, and the option set presented), so a compaction during the wait lets re-grounding re-present the same pending decision rather than lose the question the operator's reply answers; a pending escalation is thus not run state re-grounding must reconstruct from scratch (the one state it still cannot reconstruct is an interrupted foreground interview, [D26](artifacts/decision-log.md#d26-the-re-grounding-routine)).
- **Error states:** precondition and preparation failures are reported as a refusal to start that names both the reason and the remedy; stalls are surfaced with the working-tree state and the operator's options; blockers are presented with their evidence and the operator's options; a review failure or a review-gated escalation points to the durable review record so the operator can read the full findings.

## Out of Scope

- **Producing or hardening the work items.** Breaking a plan into work items and stress-testing it belong to the planning and work-item skills; this skill consumes a trusted result.
- **Specifying or planning the feature.** Deciding what to build is the job of the feature-spec and implementation-plan skills.
- **Pushing commits or opening pull requests.** The skill commits locally on the run's branch and names that branch in the summary; sharing the result with a remote stays with the operator.
- **Cross-repository orchestration.** A work-items file is single-repository by design; the driver does not coordinate work across repositories.

## Deferred (YAGNI)

### Adaptive, automatically-routed per-task model-selection policy

- **Why deferred:** the skill sets the build and fix sub-agents' model explicitly by role and lets the operator override ([D14](artifacts/decision-log.md#d14-model-selection-policy)); a fully automatic router that scores each task and routes it to a model is a further step. The superpowers research found automatic routing is research-stage with no adopted standard, and that superpowers deliberately keeps the model-selection judgment with the controller rather than automating it. No measured reliability or quality gap justifies building a router now.
- **Reopen when:** the per-role selection plus operator override produces a measured reliability problem that an automatic router would demonstrably fix.
- **Source:** issue #96 design direction; the superpowers research ([`research/superpowers-patterns.md`](research/superpowers-patterns.md)).

### Proactive per-item model override

- **Why deferred:** the operator can set the model for the whole run, and the reactive need (an item turns out to need a stronger model) is met by the stall recovery's retry-on-a-stronger-model option ([D17](artifacts/decision-log.md#d17-no-return-and-stall-handling)). A declared per-item model field would be a fourth companion change to the work-item producer for a need the whole-run override and the stall retry already cover.
- **Reopen when:** operators routinely need to pre-assign a stronger model to specific items and the stall-retry path is too late to be useful.
- **Source:** iterative review (user-experience-designer; operator chose to descope).

### Parallel execution across items

- **Why deferred:** the work items share one working tree and the build skill does not commit, so running items in parallel would corrupt each other's changes; isolating them is unbuilt and serial latency is not yet a measured bottleneck.
- **Reopen when:** per-item isolation exists and serial run time is a measured constraint on real features.
- **Source:** operator's manual-run feedback ("serial-vs-parallel given a shared working tree").

### Pre-flight triage on every item

- **Why deferred:** running a triage analysis on every item before building it pays a cost on items that never block; on-demand triage offered at escalation satisfies the same need at far lower cost.
- **Reopen when:** escalations routinely arrive too late to act on cheaply, so up-front triage would pay for itself.
- **Source:** operator's answer refining blocker detection to on-demand triage.

### Re-deriving the human-involvement marker for older work-item files

- **Why deferred:** the companion change that records the marker ships with this skill, so files without it are essentially none and can be regenerated by re-running the work-item producer; building a re-derivation heuristic now serves a population that does not exist yet, and the heuristic's criteria would be unspecified.
- **Reopen when:** an operator needs to drive a `work-items.md` that predates the marker and cannot regenerate it.
- **Source:** review finding (junior-developer YAGNI candidate).

### Global run-cost cap

- **Why deferred:** the per-item fix-loop cap plus the clean-stop affordance already bound run cost and give the operator a way to intervene; a separate numeric run-wide cap adds a knob with no measured need.
- **Reopen when:** unattended runs measurably overspend before the operator can intervene with a clean stop.
- **Source:** review finding (on-call-engineer).

### Up-front conflict scan across all work items

- **Why deferred:** the superpowers research borrows a batched plan-conflict scan run before any item is built. Here the up-front graph and field validation already catch structural conflicts, and a content contradiction between items surfaces as a blocker when the dependent item is reached, with on-demand triage offered. A separate content scan of every item up front pays analysis cost before any build and overlaps both existing mechanisms, with no evidence contradictions arrive too late to act on cheaply.
- **Reopen when:** content contradictions between items routinely surface only deep into a run, where an up-front scan would have saved wasted builds.
- **Source:** superpowers research ([`research/superpowers-patterns.md`](research/superpowers-patterns.md)); iterative review (junior-developer).

### Final whole-run review across all committed items

- **Why deferred:** the superpowers research borrows a final whole-branch review after all items complete. Here every item is already reviewed at full specialist coverage before it commits, and cross-item issues surface through the per-item review of later items that build on earlier ones (and through the cross-item-regression escalation). A separate final pass adds a second full review of the whole run with no evidence of a defect class the per-item reviews miss.
- **Reopen when:** cross-item integration defects are found after a run that the per-item reviews could not have caught.
- **Source:** superpowers research ([`research/superpowers-patterns.md`](research/superpowers-patterns.md)); iterative review (junior-developer, on-call-engineer).

### Full workspace isolation and provisioning

- **Why deferred:** the skill does the minimum preparation (branch, tooling check, planning-artifact commit) and otherwise runs in the existing checkout ([D22](artifacts/decision-log.md#d22-minimum-workspace-preparation)). Creating a worktree, installing dependencies, bringing up dev services, and choosing main-checkout-versus-worktree are a heavier, reusable concern better factored into a dedicated workspace-preparation skill that other skills (for example `plan-a-feature` at the start of a feature) could also call, rather than coupled into this driver.
- **Reopen when:** a dedicated workspace-preparation skill exists for this driver to call, or operators need this driver to isolate and provision a worktree itself before such a skill is available.
- **Source:** operator direction during review.

### Non-convergence detection across review iterations

- **Why deferred:** an internal alert skill (`cls-grafana-server-alert`) diffs consecutive review-iteration records to catch a finding that survives a claimed fix, but it has no cap on its review loop, so it needs that detector to terminate. This driver's fix loop is already bounded by a configurable cap ([D5](artifacts/decision-log.md#d5-bounded-fix-loop-cap-then-escalate)) that terminates the loop and escalates with the residual findings, so a non-convergence detector would only escalate a few rounds earlier. With the durable review record now persisted per fix round, the detector is cheap to add later, but no measured need justifies it now.
- **Reopen when:** fix loops routinely burn their full cap on a single finding that an earlier non-convergence signal would have escalated sooner, at a cost worth the added logic.
- **Source:** R7 review (the `cls-grafana-server-alert` precedent); operator chose to defer.

### Continuing the original build sub-agent for fix rounds

- **Why deferred:** handing a fix back to the same build sub-agent with its context intact (rather than dispatching a fresh fix sub-agent with curated context) would save re-priming, but the platform primitive it needs (`SendMessage`-based sub-agent resume) is experimental, disabled by default behind the `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` flag, and reported broken for the plain-sub-agent case; the fresh-agent path passes the same context by file and diff and works on the default platform ([D13](artifacts/decision-log.md#d13-fix-round-context-preservation)).
- **Reopen when:** sub-agent resume is generally available (off the experimental flag) and reliable for plain sub-agents, and a measured re-priming cost makes continuing the builder worth the dependency.
- **Source:** R11 hands-on verification ([`research/sendmessage-subagent-resume.md`](research/sendmessage-subagent-resume.md)); operator chose to defer.

### Guard against a concurrent second invocation on the same working tree

- **Why deferred:** the in-progress marker cannot tell a run that is actively building now from one that crashed mid-build, so a second invocation against a live run could take the discard-and-rebuild path on the active run's in-flight work. Concurrent runs against one working tree are an unusual pattern for a solo or small-team engineer, and the durable ledger plus the resume inspect-and-ask flow ([D10](artifacts/decision-log.md#d10-resume-discard-partial-work-and-rebuild), [D20](artifacts/decision-log.md#d20-item-to-commit-matching-and-resume-ledger-integrity)) already require operator confirmation before any discard, which blunts the worst case. A dedicated liveness guard (a lock or heartbeat) is unbuilt and unjustified by a measured need.
- **Reopen when:** operators run concurrent invocations against a shared tree often enough that the inspect-and-ask confirmation is not protection enough.
- **Source:** R12 review-worker panel (P12); operator chose to defer.

### Aggregate diagnosis of a systematic review-stage failure

- **Why deferred:** if the review stage fails across many items (the panel cannot fan out, review is broken, a model outage), each item escalates on its own and the completion summary can read N mechanism failures as N code-quality failures. A run-wide "systematic failure" diagnosis would name the common cause once, but the per-item escalations already surface each failure with its evidence, and no measured run has produced the misleading aggregate. Adding cross-item failure correlation now is speculative.
- **Reopen when:** systematic review-stage failures occur in practice and the per-item escalations prove too noisy to diagnose the common cause.
- **Source:** R12 review-worker panel (P14); operator chose to defer.

### Operator-confirmed path for a legitimately-red test baseline

- **Why deferred:** the start precondition refuses on an already-red suite because it cannot distinguish new breakage from pre-existing breakage ([D15](artifacts/decision-log.md#d15-start-preconditions-clean-tree-and-green-suite)); the refusal now names a remedy (get the suite green, or narrow the configured verification command to exclude the known-failing tests). A dedicated operator-confirmed red-baseline path (snapshot the red baseline and gate only on new failures, mirroring the no-verification-commands scope-check escape) would serve a project whose suite is red by design, but no operator has hit that wall yet and the narrow-the-command remedy already gives such a project a way forward, so building a second confirmation path now serves a population that has not appeared.
- **Reopen when:** operators routinely need to drive features on a repository whose test baseline is red by design and cannot narrow the configured command to a green subset.
- **Source:** R15 review (user-experience-designer, F156); operator chose remedy-text-only.
