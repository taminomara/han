## Full decisions

### D1: Feature scope and outcome

- **Question:** What does the skill do, for whom, and what does a successful run produce?
- **Decision:** The skill takes a trusted `work-items.md` plus the committed spec or plan its items reference, and drives implementation end to end (building each item test-first, verifying it, reviewing it, fixing it to a gate, and committing it), offloading the build and the review to sub-agents and pausing only for human-required items and unresolvable blockers.
- **Rationale:** The operator already plans features and breaks them into work items, then implements each item by hand-invoking `tdd` and `code-review`. That per-item loop is tedious on long, well-specified features and burns enough context to force session compaction every few items. A driver that offloads the heavy work to sub-agents removes the manual tedium and sharply reduces the context cost (it does not eliminate it, mid-run compaction can still fire and is guarded, D26).
- **Evidence:** Issue #96 summary, motivation, and "design direction"; the operator's manual-run feedback (a 7-item feature driven this way in 6 commits). The `tdd` skill builds and tests but does not commit (`han-coding/skills/tdd/SKILL.md`); `code-review` audits changes (`han-coding/skills/code-review/SKILL.md`); `plan-work-items` produces the items (`han-planning/skills/plan-work-items/SKILL.md`).
- **Rejected alternatives:**
  - Ship only a how-to doc pointing at an external loop runner (e.g., a Ralph loop), rejected because the operator wants a first-party Han skill and external runners raised cost and human-in-the-loop concerns in the issue discussion.
  - Build the loop into `tdd` or `code-review` themselves, rejected because those skills are clean single-stage building blocks; the conductor is a separate concern that composes them.
- **Linked technical notes:** (none)
- **Driven by findings:** compaction-cost claim scoped from "removes" to "sharply reduces" in R12 (review-findings.md F98)
- **Dependent decisions:** D2, D3, D6, D9, D11
- **Referenced in spec:** Outcome; Actors and Triggers; Coordinations

### D2: Serial, one-item-at-a-time processing

- **Question:** Does the skill build items one at a time or several in parallel?
- **Decision:** Items are processed serially in dependency order, one at a time; a dependent item is not started while an item it depends on is blocked or skipped.
- **Rationale:** The work items share a single working tree and the build skill does not commit its changes, so two items built concurrently would overwrite each other's uncommitted work. Serial processing with a commit between items keeps each item's changes isolated and the tree clean.
- **Evidence:** `tdd` leaves changes uncommitted in the working tree (`han-coding/skills/tdd/SKILL.md`); `work-items.md` orders items by a `Depends on` field and is single-file, single-repository (`han-planning/skills/plan-work-items/references/work-items-file-format.md`); the operator's feedback names "serial-vs-parallel given a shared working tree" as a real judgment point.
- **Rejected alternatives:**
  - Parallel execution across independent items, rejected because the shared working tree makes it unsafe without per-item isolation, which does not exist yet (deferred under YAGNI).
- **Linked technical notes:** (none)
- **Driven by findings:** (none)
- **Dependent decisions:** D9
- **Referenced in spec:** Primary Flow; Edge Cases and Failure Modes

### D3: Per-item loop shape

- **Question:** What is the fixed sequence the skill runs for each item?
- **Decision:** Build (test-first via `tdd`) → independently verify → review (via `code-review`) → bounded fix loop until the gate clears → commit.
- **Rationale:** The operator's manual runs converged on exactly this loop, and identified it as roughly 80% of the conducting work the two skills do not provide. Encoding it as the skill's core makes the conductor first-party.
- **Evidence:** Operator feedback: "for each slice: tdd → review → (while findings ≥ Warning and rounds < 3) fix → re-review → verify green → commit"; `tdd` and `code-review` skill contracts.
- **Rejected alternatives:**
  - Build-then-commit with review as an optional afterthought, rejected because the operator's whole motivation is keeping review in the gate; review caught real latent bugs in the manual runs.
- **Linked technical notes:** (none)
- **Driven by findings:** (none)
- **Dependent decisions:** D4, D5, D8, D9, D12, D13
- **Referenced in spec:** Primary Flow

### D4: Completion gate severity threshold

- **Question:** What review result lets an item be considered done, given `code-review`'s severity scale?
- **Decision:** An item clears the review gate when the review reports no finding at or above a configurable severity threshold; the default threshold is Warning, so any Critical or Warning finding blocks the commit and Suggestions do not. Because the gate reads only the condensed verdict the review returns, its soundness depends on that verdict being complete at and above the threshold and attesting full coverage; the durable record and the fail-closed handling of an untrustworthy verdict secure that (D27).
- **Rationale:** The issue asked for "no findings at severity medium or above," but `code-review` has no "medium"; its levels are Critical, Warning, Suggestion. Warning is the natural mapping of "medium-and-above," and making the threshold configurable lets a project gate more strictly (Critical only) or more loosely (include Suggestions). The gate is evaluated against whatever findings the review surfaces at the size it assigns the slice, since `code-review` calibrates which severities it escalates by change size.
- **Evidence:** `han-coding/skills/code-review/SKILL.md` severity levels (Critical / Warning / Suggestion) and size-calibration table; issue #96 ("severity threshold should probably be configurable"); user input selecting "Warning+, configurable."
- **Rejected alternatives:**
  - Block on Critical only, rejected because it would silently ship Warning-level bugs the operator wanted a gate on.
  - Block on Critical or Warning with no knob, rejected because projects legitimately want a stricter or looser bar.
- **Linked technical notes:** (none)
- **Driven by findings:** gate-completeness dependency on the condensed verdict noted in R7 (review-findings.md F47, F48)
- **Dependent decisions:** D5, D27
- **Referenced in spec:** Primary Flow; Edge Cases and Failure Modes

### D5: Bounded fix-loop cap, then escalate

- **Question:** What happens when a review keeps finding gate-blocking issues?
- **Decision:** The skill runs a bounded fix loop (fix, re-verify, re-review) up to a configurable cap (default 3 rounds); if the gate has not cleared at the cap, the skill stops the item and escalates with the residual findings listed. A cap of zero is valid and means escalate on the first gate-blocking finding with no fix attempt; an unbounded, never-escalate loop is not a supported value.
- **Rationale:** An unbounded loop can thrash forever on an item the sub-agents cannot resolve. A small cap with escalation bounds the cost and hands a genuinely hard item to the operator with evidence.
- **Evidence:** Operator feedback ("rounds < 3", "iteration cap"); issue #96 failure-handling direction ("run a tdd → code-review → tdd loop with a hard cap on the iteration count").
- **Rejected alternatives:**
  - Escalate immediately on the first round of findings, rejected because most findings are routine and fixable without the operator; immediate escalation defeats the autonomy goal.
  - Unbounded retry, rejected because it can spin indefinitely and burn cost on an unsatisfiable item.
- **Linked technical notes:** (none)
- **Driven by findings:** cap-zero semantics named (escalate on the first finding, no unbounded value) in R14 (review-findings.md F133); re-review scoped to run only when re-verification passes within a fix round in R15 (review-findings.md F160)
- **Dependent decisions:** (none)
- **Referenced in spec:** Primary Flow; Edge Cases and Failure Modes

### D6: HITL recognition via a persisted type on each work item

- **Question:** How does the skill know which items need human involvement before work begins, given the AFK/HITL classification is not currently written into `work-items.md`, and what does the skill do once a human-required item is reached?
- **Decision:** The human-involvement marker is persisted on each work item by the work-item producer (a companion change to `plan-work-items` and its template that must ship before this skill can rely on it) and the driver reads it. An item also counts as human-required when its declared implementation skill is interactive (D21), since such a skill cannot be offloaded to a disposable sub-agent. When a human-required item is reached the skill makes the **proceed-or-skip decision before any work is invested**: it pauses, presents the item, and asks **proceed** or **skip**. On **skip** the operator owns the item outside the skill, the skill records the choice durably (D24), and it starts no item that depends on it. On **proceed**, a decision-needed or external-prerequisite item with a non-interactive skill has the operator do the human step and signal when it is done; if that produced a decision or an edit to record, the operator records it and the skill commits that edit to the spec or work item as a marked planning commit before building (so the recorded decision is durable, is not discarded by a later resume, and is not flagged as the item's own scope escape; this planning commit carries a marker distinct from the droppable run-bookkeeping commits, so the end-of-run cleanup keeps it, D20), and if there is nothing to record (an external setup, a design review the operator absorbs) the skill proceeds on the operator's signal with no planning commit; it then builds the item through the normal loop. An interactive-skill item is run in the foreground (the orchestrator invokes that skill in the operator's session and the operator steers it through the interview), after which the skill asks the operator to **confirm the work is complete and choose how to proceed**: finish the item autonomously (where a gate-blocking finding is fixed by a sub-agent that may alter the hand-built work to clear the gate), or pause after each review (so the operator can steer before each fix round and before the commit). The skill records the chosen mode in the durable ledger before it re-grounds (D24, D26), so a re-grounded orchestrator conducts the item in the mode the operator chose. The item is then resumed at verify, and review always runs: there is no commit-without-review path, because committing unreviewed code would break the gate that is the feature's headline value (D27). The surrounding context handling (re-grounding after the item, recommending compaction) is governed by D26. Re-deriving the marker for older files that lack it is deferred under YAGNI rather than built now.
- **Rationale:** `plan-work-items` already classifies each item as AFK or HITL during its breakdown, but only prints it in the in-channel report and final count: the `work-item-template.md` has no type field, so a downstream reader has nothing to key off. Persisting the existing classification is deterministic and reuses work already done, rather than asking the driver to re-guess. "Proceed" and "skip" must be distinguished because they lead to opposite behavior (one builds the item, the other treats it as operator-owned), and a dependent item must not run on a precondition the operator chose to handle elsewhere. The proceed-or-skip decision is made before any work because the earlier flow had the operator run the interactive skill and only then asked proceed-or-skip, so a skip wasted the work already done; deciding first makes a skip meaningful. The interactive-skill path then adds a confirm-the-work-is-complete checkpoint so the operator explicitly signals their manual work is ready before the automated gates run on it.
- **Evidence:** `han-planning/skills/plan-work-items/SKILL.md` Step 5 (classifies AFK/HITL) and Step 7 (prints it) versus `references/work-item-template.md` (no type field); user input selecting "Persist Type in work items"; review findings on the undefined "resolve" semantics and the transient nature of the legacy fallback.
- **Rejected alternatives:**
  - Re-derive AFK/HITL in the driver at run time as the primary path, rejected because a fresh guess can disagree with what `plan-work-items` decided; the legacy-file case is deferred under YAGNI instead.
  - Drop the up-front marker and rely solely on runtime blocker-detection, rejected because it loses the "a human must look at this before we start" signal the operator wants.
- **Linked technical notes:** (none)
- **Driven by findings:** F7, F12, F26 (team-findings.md); HITL proceed-path split and durable skip recording added in R4 (review-findings.md F19, F20); decision-before-work and confirm-done restructure added in R5 (review-findings.md F43, F44); proceed-mode choice added in R8 (review-findings.md F62); continue-without-review mode removed, pause-after-each-review clarified, and the chosen mode recorded durably in R9 (review-findings.md F64, F73, F74); mid-run recorded decisions committed durably as marked planning commits in R10 (review-findings.md F80); proceed path generalized to external-prerequisite items with nothing to record, and the finish-autonomously consent that a sub-agent may alter hand-built work, in R14 (review-findings.md F121, F126); defer added to the human-required decision gate and the interactive pause menu, and the marked-and-interactive decision-recording precedence, in R15 (review-findings.md F155, F159)
- **Dependent decisions:** D7, D21, D24, D26
- **Referenced in spec:** Actors and Triggers (Preconditions); Alternate Flows and States; Coordinations; Deferred (YAGNI)

### D7: Blocker detection: escalate on signals plus on-demand triage

- **Question:** How does the skill detect and handle a blocker that needs the operator's explicit decision?
- **Decision:** The skill escalates to the operator on a set of signals: the item is marked human-required, a sub-agent escalates an unresolvable blocker (spec contradicts the item, acceptance criteria unsatisfiable or contradictory, item unbuildable as written), the fix loop hits its cap, or changed files escape the slice. On any escalation it offers the operator an optional deeper triage pass that characterizes the blocker and proposes options; triage is run only when the operator chooses it, not automatically on every item. When a blocker requires fixing an **already-committed earlier item** (the cross-item-regression exit), the skill does not re-open and re-run that item through a rebase-and-reapply dance, which is rarely worth the complexity. The fix is made in the current working context as part of resolving the blocker, and committed: separately if it cleanly stands alone, or folded into a bulkier commit with the current item's work when the two cannot be cleanly separated (the gate invariant still holds, the skill only commits when verification and review are green, D8). Because the per-item verification re-runs the whole suite, a regression the fix introduces in any dependent surfaces before commit without a separate downstream sweep. For an operator who wants the fix attributed to the earlier item in history, the skill offers `git commit --fixup` against that item's commit plus `git rebase --autosquash` **as part of the end-of-run cleanup rather than mid-run**, because a mid-run history rewrite would change the commit hashes the resume ledger's done markers record and leave them dangling (D20); mid-run the fix stays a normal commit, and it does not promise more than that. The escalation surfaces only the options applicable to the blocker that fired (rather than every option on every blocker), keeps the gate-override choice surfaced as the weighty one and records it so its commit is flagged as an override in the ledger and the completion summary and points at its review record, and lists defer-this-item (the run continues to the next independent item) separately from stop-the-run.
- **Rationale:** Pure hard-failure detection misses the most valuable escalations: the operator's manual runs surfaced two spec/acceptance contradictions that a human had to decide. A structured escalation channel from sub-agents plus signal-based detection catches those. Running triage on every item up front pays cost on items that never block, so triage is offered on demand instead.
- **Evidence:** Operator's manual-run feedback (two plan inconsistencies escalated as clean human decisions; escalation channel "surfaced the right things"); issue #96 ("how a blocker requiring an explicit decision is detected" is "genuinely open"); user input selecting escalate-on-signals combined with on-demand triage.
- **Rejected alternatives:**
  - Escalate only on hard failures (build can't pass, fix-loop cap), rejected because it misses spec-contradiction blockers, the highest-value escalations.
  - Run pre-flight triage automatically on every item, rejected because it pays analysis cost on items that never block (deferred under YAGNI).
- **Linked technical notes:** (none)
- **Driven by findings:** R4 added the cross-item-regression recovery option, grouped the blocker options by consequence, and named what triage does (review-findings.md F24, F33, F39); the repair-upstream lifecycle specified and the D20-mismatch mis-reference corrected in R10 (review-findings.md F81); the repair-upstream rebuild dance dropped for in-context fix plus optional fixup/autosquash in R12 (review-findings.md F87); the blocker continue option split into gate-override versus benign-accept in R12 (review-findings.md F102); the mid-run fixup/autosquash deferred to end-of-run cleanup to protect the ledger's commit references, the escalation menu filtered to the applicable options, the gate-override recorded as a flagged commit, and defer-this-item split from stop-the-run, in R14 (review-findings.md F107, F135, F124, F136); repair-upstream fold reviews both items' work-item/spec context and annotates the upstream done marker, defer returns the tree to the clean baseline before continuing, blocker evidence placed after the options, and cross-item-regression culprit attribution named a triage/operator step, in R15 (review-findings.md F148, F149, F141, F157, F158)
- **Dependent decisions:** (none)
- **Referenced in spec:** Alternate Flows and States; Edge Cases and Failure Modes

### D8: Independent verification before commit

- **Question:** Can the skill trust a sub-agent's "all gates green" before it commits, and what does the changed-file check measure against?
- **Decision:** The skill verifies independently. Before committing, it re-runs the project's own verification commands (tests, type-checking, any required code-generation or sync step, lint, and build), determined from the project's own configuration with the operator able to confirm or override the set, and trusts those results over the sub-agent's self-report or raw editor diagnostics. The green-suite start precondition (D15) applies only where the project defines such commands; a project with none takes the scope-check-only path below rather than treating an absent suite as vacuously green or as a reason to refuse. It also inspects the changed-file set for changes that look outside what the item should touch, **excluding files the project ignores and any generation or sync output the verification step itself produced**. A change that looks unrelated to the item is surfaced for the operator to accept or reject rather than hard-blocked; a change that legitimately crosses into another item's files can be **accepted and committed** as intentional. When no verification commands can be found, the skill asks the operator to confirm before proceeding with a scope-check-only run rather than treating an empty check as a pass. A verification command that **fails to execute** mid-run (the tool is missing or removed, a required service is down, the disk is full) is distinguished from one that runs and reports failures: the former is surfaced as a tooling or environment problem, the way the start-time tooling check would (D22), not fed into the fix loop as if the code were at fault. Scope is policed two ways. At review time the review flags work that goes beyond what the item asked for (the borrowed "nothing extra" spec-compliance check); because the reviewing judgment now runs a stage removed from the driver (D11), the work-item scope context that check depends on must reach that judgment however the review stage is dispatched. And the changed-file inspection compares the changed files against an **expected-paths declaration the work-item producer records on each item** (a companion change), excluding files the project ignores and any generation or sync output the verification step itself produced; a change to a file outside the item's declared paths is surfaced for the operator to accept (a legitimate cross-slice edit) or reject, and an acceptance is recorded durably in the ledger so it holds for the rest of the item's loop and survives a mid-item re-grounding rather than resurfacing as a fresh scope escape (D20, D26). The review-level check alone catches over-building; the expected-paths declaration additionally catches correct behavior written in the *wrong files*, the gap a review-only gate cannot close. The skill's own resume-ledger writes are likewise excluded from this inspection as its bookkeeping (D20), but only the skill's own writes: a builder sub-agent that writes the ledger file is surfaced as a scope escape, not excluded.
- **Rationale:** In the manual runs, sub-agents repeatedly over-claimed green while real issues remained, and raw editor diagnostics were stale until a code-generation/sync step ran, so only an independent re-run of the project's own checks could tell stale-diagnostic from real-breakage. Sub-agents also occasionally reached past their slice or left temp files behind, so the changed-file set is worth inspecting. But a strict block on any out-of-slice change would misfire on every item in a project with mandatory code generation or lock files, and would block legitimately-correct cross-slice edits, so the check excludes generated and ignored files and offers an accept-and-commit path instead of an unconditional block. The superpowers research confirmed a working implementation polices scope purely through review (a diff-first review budget plus a "nothing extra" spec-compliance verdict) with no declared file-scope field, and that this approach has a structural blind spot for correct-code-in-the-wrong-file. The operator chose to close that blind spot with a declared expected-paths field rather than accept the gap, accepting the cost of a second companion change to the work-item producer (the first being the human-involvement marker, D6).
- **Evidence:** Operator feedback ("Sub-agents over-claimed 'all gates green'... verify-before-trust was mandatory"; stale pre-sync diagnostics; "verify the changed-file set matches the slice"; an implementer reached past its slice and one left a temp file); `tdd` runs the project's test/lint/build and shows output rather than asserting it (`han-coding/skills/tdd/SKILL.md`); the work-item template has no scope field (`han-planning/skills/plan-work-items/references/work-item-template.md`); the superpowers research [`../research/superpowers-patterns.md`](../research/superpowers-patterns.md) (review-level scope budget and "nothing extra" check S9/S10; the wrong-files blind spot, validation V10); user input selecting "Add an expected-paths field" to close the wrong-files gap; review findings on generated-file scope escapes, legitimate cross-slice changes, and missing verification commands.
- **Rejected alternatives:**
  - Trust the sub-agent's reported gate result, rejected because it demonstrably shipped false greens and stale-diagnostic confusion in the manual runs.
  - Hard-block any change to a file outside a strict declared slice, rejected because it would fire on every commit in a code-generation or lock-file project and block correct cross-slice edits; the check excludes generated/ignored files and offers accept-and-commit instead.
- **Linked technical notes:** (none)
- **Driven by findings:** F4, F5, F10, F11 (team-findings.md); extended in iterative review (review-findings.md F3, F13); R4 added the expected-paths match rule and rename handling (F27), the missing-field fallback (F28), the tooling-vs-no-commands distinction (F30), and cross-slice acceptance persistence (F37); review-scope-context reach noted in R7 (review-findings.md F55); the ledger scope-check exclusion scoped to the skill's own writes in R9 (review-findings.md F68); a command that fails to execute distinguished from one that reports failures in R12 (review-findings.md F96); verification-command source named (project configuration, operator can override), the green-suite gate scoped to projects that have a suite, and cross-slice acceptances persisted in the ledger to survive a mid-item compaction, in R14 (review-findings.md F119, F120, F117); an errored or unusable dispatch return classified as an environment problem, re-review gated on re-verification passing, and a cross-slice acceptance committed immediately (not deferred to the done marker), in R15 (review-findings.md F146, F160, F143)
- **Dependent decisions:** D19
- **Referenced in spec:** Actors and Triggers (Preconditions); Primary Flow; Edge Cases and Failure Modes; Coordinations

### D9: One commit per completed item

- **Question:** When and how does the skill commit, given the build skill does not commit?
- **Decision:** The skill commits each completed item as a single commit, following the project's commit convention, once verification is green and the review gate has cleared. One commit per item is the **normal target, not a strict invariant**: an abnormal situation, a blocker fix folded in with the current item (D7) or an interactive skill that commits its own work (D6), can legitimately produce a different mapping, which the skill accepts rather than forcing a single commit; when an interactive skill has already committed its work, the driver treats that commit as the item's code commit, reviews that commit's diff, and records its reference in the done marker rather than making an empty commit. Beyond the per-item code commits, the skill also makes separate marked bookkeeping commits for all run state (in-progress and done markers, skips, defers, run configuration), so "one commit per completed item" describes the clean code history, recoverable by dropping the marked commits, not a ban on the interleaved bookkeeping commits (D20, D24); a done marker additionally flags when its item was committed over residual findings by a gate override and points at the item's review record (D7).
- **Rationale:** `tdd` deliberately leaves changes in the working tree and does not commit, so the conductor owns the commit. One commit per item gives a clean, revertible history and a natural record of progress.
- **Evidence:** `tdd` does no commits (`han-coding/skills/tdd/SKILL.md`); operator's manual run produced "7 work items in 6 commits, each built test-first, panel-reviewed, fixed where needed, and committed green."
- **Rejected alternatives:**
  - Make all changes and commit once at the end, rejected because it loses per-item revertibility and the progress record that drives resume.
  - Leave committing to the operator, rejected because per-item commits are the completion ledger the skill needs to resume.
- **Linked technical notes:** (none)
- **Driven by findings:** ledger-only bookkeeping commits noted as an exception in R9 (review-findings.md F67); one-commit-per-item reframed as a target not an invariant in R12 (review-findings.md F89); interactive self-commit mapping and the gate-override-flagged done marker specified in R14 (review-findings.md F110, F124); interactive multi-commit reviewed as the cumulative diff with the done marker recording the commit range (or the final fix commit) in R15 (review-findings.md F147)
- **Dependent decisions:** D10
- **Referenced in spec:** Primary Flow; Coordinations

### D10: Resume: discard partial work and rebuild

- **Question:** What happens when the operator re-invokes the skill on a partly finished run, and what becomes of an item that was interrupted mid-build?
- **Decision:** The skill reads the run's committed ledger (D20) and resumes at the first incomplete item without rebuilding finished ones. For an item left with uncommitted, in-progress work in the tree, the skill does not blindly discard: it **inspects that partial work and the in-progress commits, judges whether they are complete, gate-passed work to resume from or partial, unverified work to drop**, and confirms with the operator, surfacing what it found, before discarding anything. The inspection distinguishes two states a plain complete-or-discard split would flatten: a complete, verified build whose review had not yet run is kept and re-reviewed, mirroring the review-stall handling (D17), not discarded as unverified; and an item whose recorded-decision planning commit (D6) landed but whose build never started is resumed at build with that decision kept, not mistaken for partial work. The default for genuinely partial work (an interrupted build, or a build plus a partial fix, all uncommitted and unverified) is to discard and rebuild, because committing it would skip a verify or review stage; but the skill does not reflexively throw away work that inspection shows is complete and gated, and it especially does not discard an interactive item's **hand-built work** (D6) without the operator's explicit, informed agreement, since that work is not a context-free rebuild the skill can reproduce. Once that inspection and any discard are complete, and before continuing the resumed run, the skill re-establishes the green-suite baseline by re-running the suite, the same precondition it checks at a fresh start (D15); ordering the discard first keeps leftover partial work from reddening the baseline and being misread as a regression, and a baseline that drifted red between sessions is surfaced rather than misattributed to the resumed item.
- **Rationale:** The motivating problem is long features whose runs span context-compaction boundaries; the operator must be able to stop and resume. Per-item commits make completion observable, so resume is cheap. Discarding the interrupted item's partial work resolves the contradiction with the clean-tree precondition (D15) and guarantees no item is committed having skipped a verify or review stage, which a "continue mid-loop" path could not guarantee. The partial work was uncommitted and unverified, so rebuilding loses nothing trustworthy, but that holds for the skill's own partial build, which it can reproduce; it does not hold for an operator's hand-built interactive work, which is why the skill inspects and asks rather than discarding by default (R12).
- **Evidence:** Issue #96 motivation (long features, repeated compaction); D9 (one commit per item gives the completion record); user input selecting "Discard & rebuild"; review findings on the clean-tree-versus-resume contradiction and the verify-bypass ambiguity in "re-runs that item."
- **Rejected alternatives:**
  - Preserve the partial work and continue the item from where it stopped, rejected because it risks committing work that skipped a verify or review stage and collides with the clean-tree precondition.
  - Refuse on a dirty tree and make the operator clean up manually every resume, rejected because it pushes routine cleanup onto the operator on a path the skill can handle.
  - Always restart from the first item, rejected because it rebuilds finished work and wastes cost.
- **Linked technical notes:** (none)

### D11: Full review fidelity preserved

- **Question:** Does autonomous review run at the same specialist coverage as a manual `code-review`, or a reduced version?
- **Decision:** Autonomous review applies the same specialist coverage a manual `code-review` would, and runs as a **self-contained stage** rather than from the driver's main loop: the operator's headline value (the panel's self-reconciliation) is preserved rather than degraded to a single reviewer, the panel's deliberation stays out of the driver's context, and the review is isolated from the builder-output bias the driver's context carries. The stage returns a condensed verdict to the driver and persists a durable full record of its findings ([D12](#d12-driver-defined-dispatch-contract-and-compact-returns), [D27](#d27-durable-review-record-condensed-verdict-gate-and-spot-check)).
- **Rationale:** `code-review`'s value in the manual runs came specifically from its specialist panel out-performing a single reviewer and reconciling competing claims with runtime evidence. A driver that dropped that coverage to save dispatch complexity would lose the thing that made review worth gating on, so the panel is preserved. Two forces decide WHERE it runs. First, context economy: if review ran from the driver's main loop, every panel agent's output would land in the driver's context, the per-item cost the skill exists to avoid; running review in a self-contained stage that fans out the panel and returns only a condensed verdict keeps that deliberation out of the driver entirely. Second, bias isolation: the driver's context holds the builder's output and reasoning, so dispatching the review panel from the driver would expose the reviewers to that builder bias, whereas a self-contained review stage with fresh context judges the change on its merits. The clean mechanism is therefore a self-contained review stage that fans out `code-review`'s specialist panel and returns only a condensed verdict (D12) plus a durable full record ([D27](#d27-durable-review-record-condensed-verdict-gate-and-spot-check)). This depends on the platform allowing a dispatched reviewer to fan out its own panel; the suite targets current Claude Code, and the exact dispatch topology together with any platform capability or depth constraint is confirmed against the live documentation at `plan-implementation` rather than asserted here. No pre-nesting fallback is carried: the platform auto-updates aggressively and the population on a version that cannot nest is negligible, so designing a degraded main-loop fallback would cost more than it is worth.
- **Evidence:** Operator feedback ("code-review's specialist panel repeatedly out-performed a single reviewer... that self-reconciliation is the headline value"); `code-review` dispatches a specialist panel via sub-agents (`han-coding/skills/code-review/SKILL.md`); current Claude Code permits a dispatched agent to fan out its own sub-agents (the exact capability and any depth or version constraint to be confirmed against the live Claude Code sub-agents documentation at implementation time, rather than asserted as a settled version fact here); the preload-skills mechanism (a `skills:` list on a worker-agent definition injects an existing skill's content into the dispatched sub-agent at startup, without modifying that skill, controllable at dispatch via the agent definition or `--agents` JSON) as the way to run `tdd` and `code-review` in disposable workers; review findings that the fidelity commitment needed a feasible mechanism named (R4 F3), that the platform constraint had changed (R6 F46), and that the earlier write overclaimed a no-longer-needed fallback and asserted a single-sourced platform state (R7 F54).
- **Rejected alternatives:**
  - Run review as a single reduced reviewer inside one sub-agent, rejected because it discards the panel coverage that made review valuable.
  - Load the full review report into the driver's context to keep the panel, rejected because it reintroduces the per-item context cost the skill exists to avoid; only the condensed verdict returns instead.
  - Dispatch the review panel from the driver's own main loop, rejected because it would put the panel's full deliberation back in the driver's context (losing context economy) and expose the reviewers to the builder bias the driver's context carries (losing bias isolation).
  - Carry a pre-nesting fallback for a Claude Code old enough that a dispatched agent cannot fan out a panel, rejected because that population is negligible on an aggressively auto-updating platform and the degraded fallback would cost more to design and maintain than it is worth.
  - Make `code-review` (or `tdd`) fork via `context: fork` in its own SKILL.md, rejected because it would modify those shared skills and force every invocation of them to fork, including a human running `tdd` manually; preloading the skill into a disposable worker agent keeps the skills unmodified.
- **Linked technical notes:** (none)
- **Driven by findings:** F3 (team-findings.md); platform-constraint update and dispatch mechanism clarified in R6 (review-findings.md F46); bias-isolation rationale added, fallback removed, and platform claim reframed in R7 (review-findings.md F54)
- **Dependent decisions:** D12, D27
- **Referenced in spec:** Outcome; Primary Flow; Coordinations

### D12: Driver-defined dispatch contract and compact returns

- **Question:** What do the sub-agents return to the skill, and how does the skill get a structured return and the right skill invoked, given `tdd` emits prose and `code-review` emits a long report by default?
- **Decision:** The **driver defines the contract in every dispatch it makes**: it explicitly names the skill the sub-agent must run (the item's declared implementation skill, defaulting to `tdd`, for building, per D21; `code-review` for reviewing) and specifies the exact compact report the sub-agent must return, kept to roughly 300 words, short enough for the skill to decide accept/fix/commit/escalate from the report alone without reading the diff. The fields common to every implementation skill are status, files changed, the final gate result, and any escalation; the observed failure-then-pass evidence is required for a `tdd` **build** (where a new behavior is driven test-first), and is not applicable for other skills or for a `tdd` fix round that addresses a review finding without adding new behavior (a rename or extraction introduces no new failing test) (D21). The review likewise returns a condensed verdict (findings by severity, complete at and above the gate threshold, with a full-coverage attestation) rather than its full report, and that verdict references the durable full record the review persists ([D27](#d27-durable-review-record-condensed-verdict-gate-and-spot-check)); the roughly-300-word budget bounds the verdict's prose precisely because completeness lives in the record, not in the verdict. The structured contract is enforced by the driver's dispatch instruction, not by the building blocks' default output. The contract the driver imposes governs the dispatches the driver itself makes; any further fan-out inside a dispatched stage (the review panel) is that stage's own concern, not the driver's.
- **Rationale:** The manual runs found two things were needed for reliability: the sub-agents had to be told explicitly which skill to invoke, or they would not run `tdd`/`code-review`; and each had to return a ~300-word structured report so the orchestrator could conduct many items in one context without reading diffs. `tdd`'s default Step 5 output is a human narrative and `code-review`'s default is a long markdown report, so neither yields a machine-consumable return on its own; the driver must impose the contract in the dispatch. The ~300-word budget is the behavioral constraint, not just a description: without an upper bound the reports balloon and the context saving evaporates. The driver imposes the contract by instruction today; a more robust path, if the platform's schema-enforced structured output proves available for skill-dispatched sub-agents (it is generally available for the main session and workflows, but unconfirmed for this dispatch path as of R8), is to give the building-block skills a declared structured-output mode so the contract is validated rather than merely requested. That is an implementation-planning option, not a behavioral change.
- **Evidence:** Operator feedback ("I had to explicitly pass the skill names to the sub-agents, otherwise they wouldn't invoke tdd / code-review"; "Structured, machine-consumed return contracts made the orchestration context-cheap"; "STATUS / FILES / RED→GREEN / FINAL GATE / ESCALATION (~300 words)"; "code-review's natural output is a long review document... a composing skill should pass the concise-contract by default"); `tdd` Step 5 emits a narrative (`han-coding/skills/tdd/SKILL.md`); `code-review` emits a full markdown report by default (`han-coding/skills/code-review/references/template.md`); review findings on the prose-versus-structured contract, the missing compact mode, the unencoded skill-name requirement, and the budget left as evidence only.
- **Rejected alternatives:**
  - Rely on `tdd`/`code-review` default output and parse it, rejected because the defaults are prose and a long report, with no structured escalation field; the driver imposing the contract is what made the manual flow work.
  - List the report fields without a length bound, rejected because an unbounded "structured" report still overflows the conductor's context.
- **Linked technical notes:** (none)
- **Driven by findings:** F1, F2, F13 (team-findings.md); report contract generalized for non-`tdd` skills in R4 (review-findings.md F26); review verdict tied to the durable record and the contract scoped to the driver's own dispatches in R7 (review-findings.md F47, F56); structured-output mode recorded as an implementation option in R8 (review-findings.md F60); the failure-then-pass field scoped to a tdd build, not every fix round, in R12 (review-findings.md F99)
- **Dependent decisions:** D21, D27
- **Referenced in spec:** Primary Flow; Coordinations

### D13: Fix-round context preservation

- **Question:** When the review finds issues, how is the fix applied so it does not lose the original build context?
- **Decision:** A fix round is delegated to a sub-agent and is **informed by the original build context** (what was built and why) rather than starting from a cold, context-free re-read of the files; the fixed item is re-verified and re-reviewed through the full gate. Because the review now returns only a condensed verdict and persists its findings in a durable record ([D27](#d27-durable-review-record-condensed-verdict-gate-and-spot-check)), the fix carries the findings from that record, so it targets the specific findings that blocked the gate rather than re-deriving them from a verdict that, by design, only summarizes them. The behavioral requirement is context-informed, test-backed fixes; the mechanism is a **fresh fix sub-agent given curated context** (the build report, the diff, and the review record), which is all durable and works across every boundary the run can cross, including a compaction or a resume in a later session. Handing the fix back to the *same* build sub-agent with its context intact was considered as an optimization but is **deferred** (see Deferred (YAGNI)): the platform primitive it needs (`SendMessage`-based sub-agent resume) is experimental, disabled by default behind an env flag, and reported broken for the plain-sub-agent case, so the driver does not lean on it and passes context by file and diff instead. A review finding that needs broader codebase context than the fix can assemble (a cross-cutting pattern conflict, for instance) is not silently dropped: if the fix loop cannot clear it within the cap, it escalates to the operator like any other unresolved finding (D5, D7).
- **Rationale:** In the manual runs there was no way to continue a finished sub-agent, so fix rounds either fell back to the conductor making surgical edits itself or spawned a fresh agent that re-read the file from scratch and lost the implementer's context. A composing skill needs the fix to carry that context so it does not regress or re-litigate decisions already made; what is rejected is a *context-free* fresh agent, not a particular dispatch shape. A continue-the-same-sub-agent primitive briefly looked like the obvious mechanism after R8 doc-research reported it generally available, but a hands-on R11 verification found that claim wrong: the primitive (`SendMessage`) belongs to the experimental, off-by-default Agent Teams feature and is reported broken for plain sub-agents. So the durable, boundary-proof context the run already persists (the build report, the diff, and the review record) is the mechanism, and continuing the builder is deferred until the resume primitive is stable. This also avoids depending on a sub-agent handle that, even if resume worked, does not survive the compaction and session boundaries this feature targets (D1, D26).
- **Evidence:** Operator feedback ("No way to continue a finished sub-agent... the original implementer's context was lost"; fix rounds fell back to the conductor editing directly or a cold fresh agent); the superpowers research [`../research/superpowers-patterns.md`](../research/superpowers-patterns.md) (the fix round dispatches a fresh fix sub-agent with the report and diff as curated context; validation V1 corrected an earlier misread that a single implementer is kept alive); the R11 hands-on verification [`../research/sendmessage-subagent-resume.md`](../research/sendmessage-subagent-resume.md) that sub-agent resume via `SendMessage` is experimental (gated behind `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`, off by default) and reported broken for plain sub-agents (GitHub issues #35240, #42737, #37051, #48160), which corrected and supersedes the R8 doc-research claim that it was generally available; R9 review and the R9 compaction-behavior verification that a sub-agent handle does not survive a compaction or resume regardless.
- **Rejected alternatives:**
  - Spawn a fresh, context-free agent for each fix, rejected because it loses the build context and risks regressing prior decisions.
  - Have the conductor make the surgical edits itself with no sub-agent, rejected because it loads editing judgment and file context into the conductor's already-strained context and bypasses the build skill's test-first discipline.
  - Lean on continuing the original build sub-agent (resume its context for the fix), rejected for now because the resume primitive is experimental, flag-gated, and reported broken for plain sub-agents, and a sub-agent handle would not survive the compaction and resume boundaries the feature targets anyway; deferred until the primitive is stable.
- **Linked technical notes:** (none)
- **Driven by findings:** F14 (team-findings.md); sharpened in iterative review (review-findings.md F2); HITL-proceed interactive-item fix context added in R4 (review-findings.md F19); review-record reference added to the fix dispatch in R7 (review-findings.md F51); continue-the-builder mechanism adopted after the platform gained a continue-a-subagent primitive in R8 (review-findings.md F59); reframed to fresh-agent-standard with continue-the-builder as an optional within-session optimization in R9 (review-findings.md F65); continue-the-builder deferred after a hands-on check found the resume primitive experimental and broken in R11 (review-findings.md F86)

### D14: Model selection policy

- **Question:** How does the skill choose the model for the sub-agents it dispatches, and what model does its own coordination run on?
- **Decision:** The skill dispatches its build and fix sub-agents on an explicit model chosen for what those sub-agents do (structured, test-first code implementation), following Han's convention of choosing a sub-agent's model by what the task demands, not by price. It does not let those sub-agents inherit the operator's session model. The operator can override this model for the whole run; a proactive per-item override is deferred (the reactive need, an item that turns out to require a stronger model, is met by the stall recovery's retry-on-a-stronger-model option, D17). The explicit-model rule covers every sub-agent the driver itself dispatches, including the agent that hosts the self-contained review stage (D11), so none of them silently inherits the session's most-expensive tier, the very failure this decision exists to prevent; only the models of the specialist reviewers inside `code-review`'s own panel are governed by the `code-review` skill and are not chosen here. Because the skill runs as a coordinating skill in the operator's session (D11), its own coordination judgment runs on the operator's session model; the skill therefore requires the operator to run it on a session model capable of the coordination role, recorded as an operator-responsibility precondition (the skill may not be able to check the session model the way it checks a clean tree or a green suite, so this one rests on the operator), because a weak session model degrades the conductor's judgment. An adaptive, automatically-routed per-task model policy remains deferred under YAGNI.
- **Rationale:** This supersedes the earlier provisional "inherit the operator's session model by default" and the briefly-considered per-item complexity tiering. Three forces shape it. First, the superpowers research (validated adversarially) found an unnamed sub-agent model silently resolves to the session's most expensive model (one real run put all 26 of its reviewers on the top tier), so the model must be set explicitly rather than inherited. Second, Han's own model-selection standard requires choosing by what the task demands, not by cost, so the selection is framed by the role's cognitive demand, not by a cheap/expensive tier; this also matches Han's existing per-role agent-model convention. A per-item-complexity rubric was rejected because the work-item format carries no complexity signal and an item's true complexity is not reliably known before it is built (mechanical-looking items expand, design-heavy items collapse), so a per-item guess would be circular; per-role selection with an operator override for a known-unusual item achieves the same goal more simply. Third, review models are not the driver's to choose: the driver delegates review to the `code-review` skill, which owns its panel and its models. The conductor is the operator's session (D11), so "capable conductor" cannot be a value the skill sets; it is an operator precondition, because superpowers found a cheap-model controller collapses on implicit quality-versus-plan conflicts and the driver's coordination is exactly that controller role.
- **Evidence:** Research report [`../research/superpowers-patterns.md`](../research/superpowers-patterns.md) (the explicit-model lesson and 26-reviewer cost regression S2/S4; the cheap-controller-collapse finding S5; Anthropic's tiered guidance W2/W3; validation V5 recast for Han's named-agent architecture); Han's model-selection standard "choose based on what the task demands, not price" in `han-plugin-builder/skills/guidance/references/agent-building-guidelines/agent-model-selection.md`; the work-item template has no complexity field (`han-planning/skills/plan-work-items/references/work-item-template.md`); issue #96 and the operator's manual need for explicit model control; iterative-review convergence (junior-developer, adversarial-validator, on-call-engineer) that per-item cost tiering violated the standard, rested on an undefined signal, and made an unenforceable conductor commitment.
- **Rejected alternatives:**
  - Default sub-agents to inherit the operator's session model, rejected because an unnamed model silently resolves to the most expensive tier (the original provisional decision, superseded).
  - Choose the sub-agent model per item from a guessed complexity, rejected because the work-item format has no complexity signal and complexity is not reliably known before building; per-role selection with an operator override is simpler and matches Han's convention.
  - Frame the selection by cost tier (cheap / standard / most-capable), rejected because Han's standard forbids cost as a model-selection criterion.
  - Assert "the conductor runs on a capable model" as a skill behavior, rejected because the conductor is the operator's session and the skill cannot set the session model; it is recorded as an operator precondition instead.
  - Build an adaptive automatic router now, deferred under YAGNI (research-stage, no standard).
- **Linked technical notes:** (none)
- **Driven by findings:** F15, F16 (team-findings.md); recast and the per-item override descoped in iterative review (review-findings.md F1, F4, F36); explicit-model rule extended to cover the review stage's own dispatched agent in R7 (review-findings.md F52)
- **Dependent decisions:** (none)
- **Referenced in spec:** Actors and Triggers (Preconditions); User Interactions; Deferred (YAGNI)

### D15: Start preconditions: clean tree and green suite

- **Question:** What must be true before the skill begins a run?
- **Decision:** The skill refuses to start unless the working tree is clean and, where the project defines verification commands, the test suite is green; otherwise it reports the reason and stops. A project with no verification commands has no suite to confirm and takes the scope-check-only path rather than being refused on the green-suite gate (D8). The one exception to "clean" is the run's own uncommitted planning artifacts (the spec, research, and plan the items reference): these do not block, because the workspace-preparation step commits them as the first commit (D22). Uncommitted changes unrelated to those artifacts still block.
- **Rationale:** Per-item commits must not fold in unrelated uncommitted work, and the skill cannot tell newly introduced breakage from pre-existing breakage if the suite is already red. Both are cheap to check up front and prevent corrupt commits and false escalations. The clean-tree precondition applies to a fresh start; on a resume, an interrupted item legitimately leaves uncommitted partial work, which the resume flow discards rather than treating as a precondition violation (D10), so the two do not conflict.
- **Evidence:** Operator feedback (manual `git status` after every item to keep commits clean; verify-before-trust depends on a known-green baseline); D9 (one clean commit per item); review findings on the clean-tree-versus-resume contradiction.
- **Rejected alternatives:**
  - Auto-stash a dirty tree and proceed, rejected because it silently hides the operator's in-flight work and risks losing or mixing it; a refusal with a clear reason is safer.
  - Start on a red suite and proceed, rejected because new breakage becomes indistinguishable from pre-existing breakage, making verification meaningless.
- **Linked technical notes:** (none)
- **Driven by findings:** F8 (team-findings.md); planning-artifact definition and ordering refined in R4 (review-findings.md F21); green-suite gate scoped to projects that define verification commands in R14 (review-findings.md F120)

### D17: No-return and stall handling

- **Question:** What does the skill do when a dispatched sub-agent or a verification command never returns?
- **Decision:** The skill is not an open-ended wait. When any operation it dispatches or runs, a build or fix sub-agent, the self-contained review stage (which fans out its own panel, D11), or a verification command, does not return within a reasonable bound, the skill surfaces the stall to the operator, describes the relevant state, and offers to retry, skip the item, or stop the run, leaving the repository in a known state. The state it describes is the working tree for a build, fix, or verification stall; for a review stall the tree does not reflect anything (review writes nothing), so it instead reports what the review stage could surface, such as which reviewers ran or whether any partial record exists. The retry includes retrying on a stronger model where that is the lever that helps, which is the build and fix path rather than the review path, since the review panel's own models are `code-review`'s to choose (D14); for a review stall the retry re-runs the review stage. Where the cause is identifiable (for example a sub-agent that exhausted a turn budget rather than an operational hang) the skill names it, while acknowledging that a stall deep inside the review stage may be reportable only as "review did not return." A review that returns but cannot be trusted as a clean pass, an empty verdict with no coverage attestation, a partially-covered panel, or a verdict the gate cannot evaluate, is handled on this same escalation path rather than as a clean gate result (D27): review fails closed, never open. On a retry of a stall during build, verify, or a fix round, the item's in-progress partial work is discarded and the item rebuilt rather than continued, the same handling as any interrupted item (D10). A stall during review is different: the build is complete and already verified and review writes nothing to the tree, so the retry re-runs the review stage only and the verified build is kept, never discarded. The spec commits to the recovery path, not to a wall-clock duration. Relatedly, an escalation caused by repeated verification failure carries the raw verification output so the operator can recognize an intermittent test, and a cap-reached escalation is reported as "gate not cleared" rather than "unsatisfiable."
- **Rationale:** The whole point of the skill is unattended operation on long features. The two heaviest operations (a sub-agent running `tdd` on a real codebase and the independent verification re-run) are exactly where an interactive prompt, a deadlocked test, or a network-bound step can hang forever. Without a committed recovery path the operator returns to a session that made no progress, with no idea of the tree's state. A flaky suite that trips the fix-loop cap on otherwise-correct work would also mislead the operator unless the escalation shows the raw output and avoids "unsatisfiable" language reserved for the build-never-passes case. Bounding and detecting a non-return is implementable with the platform's means for timing or background-monitoring a dispatched operation and scheduling a check on it; the exact mechanism is plan-implementation. A complementary, cheaper guard is to have the dispatched sub-agents run their own commands under explicit timeouts, so a hung verification or build command aborts and surfaces inside the sub-agent rather than silently hanging it; this is worth folding into the implementation skills (for example `tdd`) as a companion change. The orchestrator's own outer non-return bound remains the load-bearing guard, so a sub-agent that ships without command-level timeouts only means slower detection, never an unguarded hang.
- **Evidence:** Review findings (on-call-engineer: no timeout or non-return commitment for sub-agent dispatch or skill-owned verification; flaky-suite escalation misleads; edge-case-explorer: flaky suite, no verification commands); the skill's unattended design intent (D1, Outcome); current Claude Code provides bounded and background-monitored dispatch, command timeouts, and scheduled wake-ups as the means to track a non-return (verified in R8), plus the operator's R8 direction to run sub-agent commands under explicit timeouts.
- **Rejected alternatives:**
  - Wait indefinitely for the sub-agent or command to return, rejected because it strands an unattended run with no recovery and no visibility.
  - Auto-kill and silently move on, rejected because it can discard partial work and hide a systemic problem; the operator gets a decision instead.
  - Degrade in place when the review stage is down, committing the item with review deferred and flagged, rejected because committing unreviewed code defeats the gate that is the feature's headline value; a review outage escalates to retry, skip, or stop, it does not lower the bar (D27).
- **Linked technical notes:** (none)
- **Driven by findings:** F17, F18, F20 (team-findings.md); stall-cause clause added in iterative review (review-findings.md F10); review-call stall added in R4 (review-findings.md F23); review-domain stall levers fixed, fail-closed verdict handling tied in, and degrade-in-place rejected in R7 (review-findings.md F53); stall-tracking feasibility, in-progress-on-retry handling, and the explicit-command-timeout companion added in R8 (review-findings.md F58); review-stall-keeps-the-verified-build clarified and the command-timeout companion marked non-load-bearing in R9 (review-findings.md F72, F76); an errored or unusable dispatch return (outage, rate-limit, partition) classified as an environment problem alongside the no-return case in R15 (review-findings.md F146)
- **Dependent decisions:** (none)
- **Referenced in spec:** Edge Cases and Failure Modes; User Interactions

### D18: Clean-stop affordance

- **Question:** Can the operator stop a run cleanly without waiting for a blocker to surface?
- **Decision:** Yes. At any point the operator can send a stop request; the skill **acknowledges it on receipt** (so the operator knows it registered, telling them the in-flight stage will finish to the item's gate before the stop takes effect, so continued output is expected and not a sign the stop was missed, and they do not fall back to a raw interrupt) and checks for a pending request **before each sub-agent dispatch** (the build, each fix round, and the review), not only at item boundaries, so the stop takes effect at the next safe point rather than waiting out a whole item. When one is pending it finishes the in-flight stage to the item's gate, committing the item if it passes or escalating it if it does not, then halts instead of starting the next stage or item, leaving the repository in a known state and emitting the final summary. A stop pending before the item's review does not skip review: review runs and the gate is evaluated before the stop takes effect, so no item is committed or escalated on a review that did not run (D27). If the stop arrives mid-fix-loop, finishing to the gate means it completes the current fix round, evaluates the gate once, and commits or escalates, rather than starting another round.
- **Rationale:** On a long feature the operator may decide to stop for many reasons (the direction changed, they want to inspect the committed items, they found a problem in an earlier item) that are not blockers. Without a graceful-drain path, the only option is a raw interruption that lands in the mid-item resume case. Scoping the stop to "after the current item" keeps the working tree in a clean, known state and avoids the partial-work problems of an abrupt halt. This affordance also bounds run cost, which is why a separate global cost cap is deferred.
- **Evidence:** Review finding (on-call-engineer: no clean-stop affordance at non-escalation points; the only run-level abort is via a blocker escalation); the skill's autonomous, long-run design intent (D1).
- **Rejected alternatives:**
  - Rely on raw interruption only, rejected because it leaves an item mid-loop and forces the discard-and-rebuild path for work that could have finished cleanly.
  - Stop immediately, abandoning the in-progress item, rejected because it leaves uncommitted partial work and a less predictable tree state than finishing the current item.
- **Linked technical notes:** (none)
- **Driven by findings:** F19 (team-findings.md); signal mechanism and mid-fix semantics added in R4 (review-findings.md F25, F38); stop checked before each dispatch and acknowledged on receipt in R12 (review-findings.md F91, F97); the acknowledgement told to state the in-flight stage drains first, a stop pending before review confirmed not to skip review, and the clean-stop alternate-flow text brought into line with the before-each-dispatch granularity, in R14 (review-findings.md F128, F127, F108); a received-but-unapplied stop recorded durably so a compaction in the drain window does not drop it, and a positive stopped-run hand-off with an explicit abandon, in R15 (review-findings.md F143, F152)
- **Dependent decisions:** (none)
- **Referenced in spec:** Alternate Flows and States; User Interactions

### D19: Input-validation preconditions

- **Question:** What input does the skill validate up front, and what does it do when validation fails?
- **Decision:** Before starting the first item, the skill validates the work-item input. It **refuses to start** (naming the offending items) on a structural error it cannot safely proceed past: a dependency-graph malformation (a cycle, duplicate item identifiers, or a `Depends on` reference to an item not present in the file), a declared implementation skill that is not a code-producing implementation skill (D21), or a file with no buildable items at all (empty, or every item filtered out), which is a startup error rather than an empty run. A **missing required field** is handled differently: rather than refusing, the skill **applies the defined fallback and proceeds** with a surfaced warning, a missing human-involvement marker is treated as unattended (D6), and a missing expected-paths declaration falls back to a review-level-only scope check after asking the operator (D8). Structural errors are caught up front, in the same class as a dirty tree or a red suite; a missing field is a proceed-with-fallback, not a refusal.
- **Rationale:** The skill builds a serial run order from the dependency graph. A cycle has no valid order and would wedge the run or cause silent mutual skipping; duplicate identifiers make dependency resolution and the commit ledger ambiguous; a dangling reference can never be satisfied and would silently skip the dependent and everything below it. Each of these fails silently or wedges if not caught, and a final summary claiming "all items committed" would mislead. Up-front validation turns all three into a clear refusal.
- **Evidence:** Review findings (edge-case-explorer: dependency cycle, duplicate IDs, dangling dependency reference, all High; junior-developer: circular dependency unaddressed); `Depends on` is the sole ordering field and items are single-file (`han-planning/skills/plan-work-items/references/work-items-file-format.md`).
- **Rejected alternatives:**
  - Discover the malformation mid-run, rejected because by then items may be partly built and the failure is harder to diagnose; up-front validation is cheap and clear.
- **Linked technical notes:** (none)
- **Driven by findings:** F21 (team-findings.md); field-presence and skill validation added in R4 (review-findings.md F22, F28); the missing-field path reconciled to apply-the-fallback rather than refuse in R10 (review-findings.md F79); empty or zero-buildable-item file added as a start-time refusal in R14 (review-findings.md F132)

### D20: Item-to-commit matching and resume-ledger integrity

- **Question:** How does the skill match commits to items so resume is unambiguous, and what happens when the history and the file disagree?
- **Decision:** The skill keeps a **resume ledger as a tracked file**, and all run bookkeeping lands as **separate commits carrying a specific marker** (a commit-message convention), interleaved with the clean per-item *code* commits, which carry no ledger changes. The bookkeeping commits record the run configuration (the gate threshold, the fix-loop cap, the model, and the branch), an **in-progress marker** before each item's work and a **done marker** after its code commit (the done marker records the real reference of the code commit it finalizes and the item's durable review-record location, D27), any skip or defer choice, any operator-accepted cross-slice scope escapes for an item (so a re-grounding restores them rather than resurfacing an approved change as a fresh escape, D8), and a flag on a done marker when its item was committed over residual findings by a gate override (D7). Because bookkeeping and code are separate commits, the operator can keep a clean code history: a `git rebase` that drops the marked bookkeeping commits leaves one clean commit per item, and the ledger file disappears with them. The skill offers this cleanup **only when the run is fully complete, never on a partial run**, since it rewrites history and dropping the ledger forecloses resume; for the same reason any history rewrite that would change an item's code-commit hash, including the optional repair-upstream `--fixup`/`--autosquash` attribution (D7), is offered only at completion, because a mid-run rewrite would leave the done markers' recorded commit references dangling. The bookkeeping marker is **distinct from the marker on a mid-run planning commit** (an operator's recorded decision, D6), which is real history the cleanup does not drop. On resume the skill reads the ledger and the in-progress/done markers to orient, but it does not mechanically trust a marker-plus-commit pattern: for any item whose state is not cleanly *done*, it **inspects the actual in-progress commits and working-tree changes** and judges whether they are complete, gate-passed work for that item (resume from there) or partial or untrustworthy work (drop and rebuild, D10); when that judgment is not clean it **asks the operator** rather than guessing. This is why the reconciliation is a judgment, not a rule: a foreign or out-of-band commit, or a contract-violating builder commit, landing between the in-progress and done markers is not blindly accepted as the item's completion, it is inspected and, if unclear, surfaced to the operator. The run configuration and branch are read from the ledger on resume, so a resumed run gates the remaining items exactly as the committed ones and continues on the same branch rather than forking a new one. The ledger file is the skill's own bookkeeping, so the skill's own writes to it are excluded from the per-item changed-file and expected-paths checks (D8); a builder sub-agent writing the ledger is *not* excluded and is surfaced as a scope escape. If a commit the skill makes (a code commit or a marked bookkeeping commit) is rejected or fails (a pre-commit hook, a lock, a full disk), the skill does not advance and does not discard the verified work; it surfaces the failure and halts fail-closed, in the same class as a rejected preparation commit (D22, D17). When the ledger and the work-items file disagree (an item recorded in the ledger is no longer present in the file, or the operator edited or renumbered items between runs), the skill surfaces the mismatch and offers a clear option set: proceed from the first unmatched item, restart from the beginning, or abort so the operator can reconcile manually. A committed ledger that cannot be parsed on resume (merge-conflict markers, truncation, corruption) is a fatal resume error: the skill surfaces the raw content and offers abort-to-reconcile rather than guessing, since committed items may already exist on the branch. Likewise, if the branch the ledger records is missing (deleted), or the resume runs from a checkout that lacks the run's prior commits, or a done entry's recorded commit reference no longer resolves in history (an out-of-band reset, cherry-pick, or rebase moved or dropped it), the skill surfaces that and asks the operator to reconcile rather than continuing on the wrong base or treating an item as done whose commit is gone.
- **Rationale:** A completion ledger only works if it survives the things that happen to a long run across multiple sessions: out-of-band commits, work-item edits, squashes, and rebases. Reconstructing completion by parsing a machine-readable item id out of each commit message is fragile, because a project's commit convention does not generally encode a parseable id, and a rebase or squash that rewrites the messages corrupts the match silently. An explicit ledger file the skill commits as it goes is simpler and more robust: it is explicit committed state whose content is preserved even when history is rewritten, so resume reads it directly instead of reconstructing it. Keeping a single ledger that records completions, skips, and defers together (rather than completions in commit messages and skips in a separate record) unifies the resume anchor (D24). A confirm-on-mismatch behavior keeps it trustworthy without forbidding the operator from touching the repository or the work-items file. The R9 review hardened this against the failure modes a committed ledger introduces: a rejected per-item or ledger-only commit halts fail-closed rather than discarding verified work or advancing into a mixed tree; a skip or defer is committed immediately so it is never lost across a stop; the scope-check exclusion is scoped to the skill's own writes so a stray builder write to the ledger is still caught; and an unparseable ledger fails to a reconcile prompt rather than a silent restart. The R10 review refined the commit shape further. Folding the ledger update into each item's code commit kept the two atomic but polluted every code commit with bookkeeping and made a clean history hard to recover. Landing all bookkeeping as separate, marked commits instead keeps the code history clean and lets the operator drop the bookkeeping with a single rebase when the run is done, at the cost of a reconcilable window between an item's code commit and its done marker. That window is handled by inspection on resume, not a blind rule: the skill verifies that a code commit found without its done marker is genuinely the item's own gate-passed work before treating it as complete, and asks the operator when that is unclear, so a foreign or out-of-band commit in the window cannot silently mark an unbuilt item done. Separating the commits also dissolves the self-referential-hash problem, since the done marker is a later commit and can record the real reference of the code commit it finalizes. The same ledger now also carries the run configuration and branch, so a resume restores the exact gate and branch the committed items were produced under.
- **Evidence:** Review findings (junior-developer: completion ledger requires a parseable commit format; on-call-engineer: out-of-band commits and rebases corrupt the ledger; edge-case-explorer: commit format does not anchor resume, items edited/renumbered/rebased between runs); D9 (one commit per item); D10 (resume reads the progress record); the operator's R8 direction to commit updates to a resume ledger marking items done, as the simpler and rebase-robust alternative to a machine-readable per-commit reference.
- **Rejected alternatives:**
  - Embed a machine-readable item reference in each commit and reconstruct completion by parsing it on resume, rejected as more complex and less robust than a committed ledger file: a squash or rebase that rewrites commit messages corrupts the parse, whereas a committed file's content survives.
  - Match items to commits by message text or position only, rejected because it breaks on out-of-band commits, edits, and rebases, silently skipping or re-running work.
  - Proceed silently on a mismatch with a best-guess, rejected because a wrong guess re-runs committed work or skips unbuilt work with no surfaced error.
- **Linked technical notes:** (none)
- **Driven by findings:** F8, F22 (team-findings.md); mismatch option set added in R4 (review-findings.md F35); recast to a committed resume ledger in R8 (review-findings.md F57); per-item and ledger-only commit-failure handling, immediate skip/defer commits, the scoped exclusion, unparseable-ledger handling, and the stable-commit-reference wording added in R9 (review-findings.md F66, F67, F68, F69, F70); recast to separate marked, droppable bookkeeping commits with in-progress/done bracketing and persisted run config and branch in R10 (review-findings.md F82); resume reconciliation made judgment-based (inspect, decide, ask if unclear) rather than trusting a marker-plus-commit pattern in R12 (review-findings.md F88); cleanup scoped to full completion with a distinct planning marker, and the missing-branch resume case added, in R12 (review-findings.md F92, F93, F101); mid-run history rewrite (including the repair-upstream fixup/autosquash) deferred to completion to protect the done markers' commit references, an unresolvable done-marker reference added to the resume reconciliation, and accepted scope escapes plus gate-override flags added to the ledger record, in R14 (review-findings.md F107, F109, F117, F124, F139); a zero-overlap ledger/file mismatch given a start-fresh-run option, restart-option consequences disclosed, the effective config surfaced on resume, mid-item transient state committed immediately, and the cleanup's erasure of the override audit trail surfaced, in R15 (review-findings.md F150, F162, F153, F143, F142)
- **Dependent decisions:** D24
- **Referenced in spec:** Primary Flow; Alternate Flows and States; Edge Cases and Failure Modes; Coordinations

### D21: Per-item implementation skill

- **Question:** Does every item build with `tdd`, or can a work item name a different implementation skill?
- **Decision:** Each work item may declare an optional implementation skill, defaulting to `tdd`. The declared skill must be a **code-producing implementation skill**; a skill that does not produce code changes (for example `code-review`) is rejected by the up-front validation (D19), and a build that produces no file changes is escalated as a blocker rather than committed, so an item is never marked done with no work behind it. The driver auto-drives only **non-interactive (AFK) skills** by dispatching them to a sub-agent and naming the declared skill in the dispatch (generalizing D12's hard-coded `tdd`). A work item whose declared skill is **interactive** (it interviews or asks questions as it goes, such as `skill-builder`, `agent-builder`, or `refactor` when it asks) cannot be offloaded to a disposable sub-agent, so its item is treated as a human-involvement item: the driver pauses and invokes that skill in the foreground, guiding the operator through it, reusing the existing pause flow (D6). If a compaction interrupts the foreground interview, the interview state is not in the ledger and re-grounding cannot reconstruct it, so on re-entry the skill surfaces the interrupted interactive item and offers to re-invoke the skill or, on the operator's confirmation that the hand-built work is complete, resume at verify, rather than dropping the item or silently restarting it (D26).
- **Rationale:** A long feature's work items are not all "build new behavior test-first": some restructure existing code (`refactor`), some author a new skill or agent (`skill-builder`, `agent-builder`). The driver should be able to run the right tool per item rather than forcing everything through `tdd`. But a disposable sub-agent runs once and returns and cannot conduct an interview, so an interactive skill genuinely cannot be driven autonomously; its item is inherently HITL. Tying the item's skill to its human-involvement classification reuses the D6 pause path instead of inventing a new one, and keeps the autonomous path strictly for skills that can run unattended.
- **Evidence:** `tdd` runs autonomously with no gate (`han-coding/skills/tdd/SKILL.md`); `refactor` is gated and can ask as it goes (`han-coding/skills/refactor/SKILL.md`); `skill-builder` and `agent-builder` are interview-driven (`han-plugin-builder/skills/`); user-described need to drive items that are not test-first builds; D6 (human-involvement marker) and D12 (the driver names the skill in the dispatch).
- **Rejected alternatives:**
  - Keep the driver `tdd`-only, rejected because it cannot drive a refactor item or an authoring item, which the operator will have in real features.
  - Run interactive skills inside a dispatched sub-agent, rejected because a sub-agent returns once and cannot conduct the interview those skills require.
- **Linked technical notes:** (none)
- **Driven by findings:** review-findings.md F16; code-producing-skill requirement and zero-change escalation added in R4 (F22); foreground invocation of interactive-skill items clarified in R8 (review-findings.md F63); compaction-mid-interview recovery for a foreground interactive item added in R14 (review-findings.md F111)

### D22: Minimum workspace preparation

- **Question:** What does the skill set up before the per-item loop begins?
- **Decision:** The skill does a minimal preparation before processing items, and orders it so the **read-only checks and the operator's plan confirmation precede any repository mutation**, so a refusal or a declined plan leaves the repo untouched. First, read-only: it checks the tooling the run needs is available (treating any one missing required command as "tooling unavailable" and stopping), confirms the working tree is clean apart from the run's own planning artifacts (the set it derives from the items' references plus the work-items file, confirmed with the operator before it is committed so nothing unrelated is folded in and nothing referenced is missed), confirms the suite is green where the project defines verification commands, and validates the items (D19). Then, only after the operator confirms the plan (D25), it mutates the repository: it creates the **dedicated branch** (named by the operator, the project's convention, or a feature-derived default, unless already on a suitable one), so per-item commits never land on a shared mainline by default; commits the planning artifacts as the first commit; **initializes the resume ledger as a separate marked bookkeeping commit** recording the run configuration and branch, so the ledger exists before any item is reached, including a run whose first reached item is skipped (D20, D24); and only then, last in the sequence, sets the run-active marker the re-grounding trigger reads, so a preparation failure never leaves a marker without a ledger (D26). A preparation failure (the branch cannot be created, a required command will not run, the planning-artifact commit is rejected by a hook, or a git operation hangs) is reported and stops the run, and because the mutations come last a failure or a declined plan leaves no stray branch or commits. Full workspace isolation, creating a worktree, installing dependencies, bringing up dev services, and choosing main-checkout-versus-worktree, is **not** built into this skill; it is deferred as a candidate for a separate, reusable workspace-preparation skill that other skills (for example `plan-a-feature` at the start of a feature) could also call.
- **Rationale:** The run needs a branch to commit onto and working tooling to verify against, and it should not refuse over the planning documents the operator just produced (the common case where the spec, research, and plan are still uncommitted). But full worktree provisioning, dependency installation, and service bringup are a heavier, general concern that other planning skills would also want; folding them into this driver would couple a reusable capability into one consumer and duplicate it later. Keeping this skill's preparation minimal, and letting a dedicated skill own isolation, is the simpler split the operator chose.
- **Evidence:** User direction (defer full worktree resolution to a separate skill usable from `plan-a-feature` as well; do branch, tooling check, and spec commit as the minimum); the superpowers research factors isolation into a separate `using-git-worktrees` skill and end-of-run handling into `finishing-a-development-branch` ([`../research/superpowers-patterns.md`](../research/superpowers-patterns.md)); D15 (start preconditions); D9 (per-item commits need a branch).
- **Rejected alternatives:**
  - Build the full setup phase (worktree, dependency install, service bringup, checkout-versus-worktree resolution) into this skill, rejected because it couples a reusable isolation concern into the driver; the operator prefers a separate workspace-preparation skill.
  - Do no preparation and run in the existing checkout as-is, rejected because the run needs a branch and working tooling, and must not block on the operator's uncommitted planning artifacts.
- **Linked technical notes:** (none)
- **Driven by findings:** review-findings.md F17; extended in R4 (F21 planning-artifact definition and ordering, F29 dedicated branch, F30 tooling distinction); ledger initialization added in R9 (review-findings.md F67); ledger init recast to a separate marked bookkeeping commit recording run config and branch in R10 (review-findings.md F82); preparation reordered so read-only checks and the confirm precede repo mutation in R12 (review-findings.md F95); planning-artifact set derived from the items' references and confirmed before commit, and the run-active marker set last in the mutation sequence, in R14 (review-findings.md F130, F113); preparation steps made idempotent on re-entry after a mid-preparation compaction in R15 (review-findings.md F145)
- **Dependent decisions:** D15
- **Referenced in spec:** Primary Flow; Actors and Triggers (Preconditions); Edge Cases and Failure Modes; Deferred (YAGNI)

### D24: Skip and defer decisions persist across resume

- **Question:** How are skip and defer decisions remembered so a resume does not silently re-attempt or re-skip them?
- **Decision:** The skill records skip and defer choices durably in the committed resume ledger (D20), alongside completions, rather than inferring progress from commit messages. A skip or defer is committed immediately as a marked bookkeeping commit, so the choice is durable the moment it is made and is never lost if the run stops before the next item (D20). On resume it honors them: a previously skipped or deferred item is not silently rebuilt. A deferred item that was *blocked* is re-surfaced for the operator when the reason that blocked it may have changed; a *self-owned skip* (the operator chose to own the item outside the skill) is honored without re-surfacing on every resume, since it has no blocking reason that could change, though the operator can still re-introduce it deliberately. The same ledger is the re-grounding anchor the skill re-reads after handling a human-required item inline, not only the cross-session resume anchor (D26). Alongside each item's done, skip, or defer status and its commit, the ledger also records the location of that item's durable review record (D27), any operator-accepted cross-slice scope escapes for the item and whether the item was committed over residual findings by a gate override (D8, D7), and the run configuration and branch (D20), so a spot-check or an escalation can reach the full review, a re-grounding restores the item's accepted escapes, and a resume restores the exact gate and branch the committed items were produced under. The ledger lives in version control as separate marked, droppable bookkeeping commits (D20), so it survives across sessions and history rewrites; its exact layout is left to implementation.
- **Rationale:** The resume ledger (D20) matches completed items by their commit reference, but a skipped or deferred item never receives a commit, so on a commit-only ledger it is indistinguishable from an item never started, and a resume would re-attempt it, contradicting the skip semantics (D6). A durable record of skip and defer choices closes that gap. Re-surfacing rather than silently honoring lets an operator who resolved a blocker off-cycle drive the dependent items on a later run.
- **Evidence:** Review findings (adversarial-validator: skip choices lost across a session boundary; junior-developer: skipped dependents have no unblock path on resume); D6 (skip semantics); D20 (commit-based ledger); the superpowers durable progress ledger ([`../research/superpowers-patterns.md`](../research/superpowers-patterns.md), S14).
- **Rejected alternatives:**
  - Rely on the commit ledger alone, rejected because skips have no commit and would be re-attempted on resume.
  - Skip a deferred item forever, rejected because an operator who resolves its blocker off-cycle could never drive it or its dependents through the skill.
- **Linked technical notes:** (none)
- **Driven by findings:** review-findings.md F20; dual-purpose re-grounding anchor added in R5 (F45); per-item review-record location added to the ledger in R7 (review-findings.md F47, F49); unified with the committed resume ledger in R8 (review-findings.md F57); immediate ledger-only commits for skips and defers added in R9 (review-findings.md F67); ledger model recast to separate marked bookkeeping commits carrying run config and branch in R10 (review-findings.md F82); self-owned skip distinguished from a blocked-defer on resume in R12 (review-findings.md F103); accepted scope escapes and the gate-override flag added to the recorded ledger state in R14 (review-findings.md F117, F124); defer offered at the human-required decision gate and the deferred item's uncommitted work returned to the clean baseline before the next item, in R15 (review-findings.md F155, F141)

### D25: Plan preview and confirmation before the run

- **Question:** Does the run start immediately after preconditions, or does the operator see and confirm the plan first?
- **Decision:** After preparation and validation, the skill shows the operator the run plan (the items in dependency order, each marked unattended or human-required and named with its implementation skill, plus any items that will be skipped because a dependency is blocked) and waits for the operator to confirm, reorder, mark items to skip, or **decline** (which stops the run before any repository mutation, D22) before the first item is dispatched. A reorder must preserve the dependency order: the skill rejects, or re-sorts and re-presents, an order that would run a dependent before something it depends on, rather than honoring an order that violates the validated graph (D19). A skip marked at the preview is recorded durably at once, the same as any skip (D24), so it survives a stop before the first item. On a **resume** the skill does not replay the full preview; it shows a resume summary (what is done, skipped, deferred, and what remains) and continues, so the one-time confirmation is not re-demanded mid-run.
- **Rationale:** The run is unattended and can be long; without a preview the operator cannot see which items are human-required, and so cannot decide whether to stay or step away, until those pauses surface mid-run. A one-time confirmation at the start surfaces the run's shape and its human-required items and gives the operator a place to skip an item they already know is problematic, without breaking the autonomous-after-start model.
- **Evidence:** Review findings (user-experience-designer: no plan preview before the run; no proactive skip affordance); user input selecting "Add preview + confirm."
- **Rejected alternatives:**
  - Start immediately with no preview, rejected because the operator cannot plan their attention or surface human-required items up front.
  - Show a preview but auto-proceed without confirmation, rejected by the operator in favor of an explicit confirmation.

- **Driven by findings:** review-findings.md F32; reorder constrained to the dependency order, and preview-skip durability and the resume summary clarified in R10 (review-findings.md F78, F85); decline option added and mutation deferred until after confirm in R12 (review-findings.md F95); the effective run configuration surfaced at the confirm gate and the resume summary, and a preview-time skip re-rendering the stranded-dependent cascade, in R15 (review-findings.md F153, F154)

### D26: The re-grounding routine

- **Question:** The orchestrator can re-enter a run with stale or erased context: after an automatic compaction (which can fire mid-run and even truncate the skill's own instructions), after the operator pauses and resumes the run later, or after handling a human-required item inline. How does it re-establish its working context reliably, and only when a run is actually in progress?
- **Decision:** The skill runs a single named routine, **re-grounding**, whenever it re-enters a run with possibly-stale context, and **only when a run is actually in progress**. Re-grounding fires on three triggers: an **automatic compaction** (which can fire mid-run between items and can even truncate the skill's own re-injected instructions); a **resume after a pause or a time gap**, where the operator sends a new message and the orchestrator must recognize it is continuing an in-progress run rather than starting cold; and the **inline handling of a human-required item** (a recorded decision, or an interactive skill run in the foreground), which erodes context the same way. The routine is the same in all three: the orchestrator re-reads the committed ledger (its source of truth for run state, D20, D24), reloads its own instructions if they were truncated, re-establishes the run's state, **announces where it is** (which item, what is done and what remains), and only then interprets the operator's message in that resumed context rather than as a cold start. If re-grounding cannot re-read the ledger or reload its instructions (an unparseable or unreachable ledger, or the skill cannot reload), it halts fail-closed and surfaces the state rather than proceeding on guessed state, the same fail-closed handling D20 commits to on resume, since this trigger can fire mid-run and not only at a fresh resume. The one run state re-grounding cannot reconstruct is an interview interrupted mid-foreground for an interactive item, which the ledger does not hold; there the skill surfaces the interrupted item and offers to re-invoke the skill or confirm the work complete and resume at verify, rather than guessing (D21). For a human-required item specifically, the re-ground happens **at the resume point, before the orchestrator conducts the item's own verify, review, fix, and commit stages**, not only at the next-item boundary, because those stages run right after the inline work erodes context; the operator's chosen proceed-mode is recorded in the ledger before re-grounding (D6) so the re-grounded orchestrator reads the mode rather than defaulting.
  The routine's reliability turns on a trigger that survives a compaction which erased the skill's own re-ground instruction, and that stays silent when no run is active. The skill's own body cannot be that trigger (a compaction re-injects a skill only truncated and may drop it entirely), so the durable trigger lives outside it: a **run-active marker kept in version-control configuration rather than in the working tree or commit history**, so it is durable across sessions and compaction without polluting the tree or the history and needs no cleanup commit, scoped to the run's branch; plus a **conditional startup hook** that reads that marker and injects a short re-ground pointer (the ledger location and an instruction to reload the skill) only when the marker is present. The skill sets the marker once the ledger is initialized (last in the preparation sequence, so a preparation failure never leaves a marker without a ledger, D22) and clears it when the run is fully complete or the operator explicitly abandons the run (an end choice distinct from a clean stop, which records the run abandoned in the ledger and clears the marker so the trigger goes quiet without forcing completion or hand-editing config); a plain clean stop leaves it set, so a later resume still re-grounds, and a marker left set by an abnormally-ended run is recoverable: when re-entry finds the marker but the ledger shows no run in progress (complete, or absent), the skill reconciles and clears it rather than re-grounding into a dead run forever. The hook is a small bundled companion, portable across the suite's targets, which share the same lifecycle-hook model. The exact marker key and hook are left to `plan-implementation`; the behavioral commitment is that re-grounding is reliable even through a compaction that truncated the skill, and never fires when no run is in progress. The skill also recommends the operator run a manual compaction before and after a human-required item, so the heavy inline work does not crowd the orchestrator's window, and signals the start of an interactive skill's foreground hand-off; re-grounding from the ledger keeps the skill correct whether or not the operator compacts.
- **Rationale:** The orchestrator's value depends on holding the run's state and its own instructions; when context is eroded, by inline human work, by a mid-run auto-compaction, or by a long pause, it can mis-conduct the rest of the run (mis-sequence items, mis-read reports, skip a gate) or, on a resume, misread the operator's new message as a cold start. Naming one routine and triggering it at every such boundary makes the recovery uniform and recognizable, so the agent is never unsure what a re-entry means. The hard part is the bootstrap: the instruction to re-ground cannot live only in the skill body, because the very compaction it must survive re-injects skills only truncated (and can drop them), as the R13 research verified on both target platforms. So the durable state stays in the committed ledger, the full procedure stays in the (reloadable) skill, and the durable *trigger* lives where it survives compaction and stays conditional: a branch-scoped marker in version-control config (durable on disk, invisible to the tree and history, needing no cleanup) plus a hook that fires only when the marker is set. That keeps the trigger from ever injecting noise when no run is active, the failure the operator flagged, and it is portable because both targets share the same hook model and plain git config.
- **Evidence:** Operator direction (the proceed/skip decision before the work; a confirm-the-work-is-done gate; ledger guards around HITL items; suggest manual compaction; name the resume pattern; keep the trigger conditional and out of the tree and history, the branch-config-marker idea); the R13 research ([`../research/re-grounding-after-compaction.md`](../research/re-grounding-after-compaction.md)) that neither Claude Code nor Codex has a compaction-surviving session-local memory, that skills re-inject only truncated, that lifecycle hooks (SessionStart/PreCompact/PostCompact) are generally available on both targets, and that git config holds a branch-scoped value durably outside the tree and history; the superpowers durable-ledger pattern, which after compaction trusts the ledger and `git log` over the orchestrator's own recollection ([`../research/superpowers-patterns.md`](../research/superpowers-patterns.md), S14); issue #96 motivation (per-item context cost forcing session compaction).
- **Rejected alternatives:**
  - Keep the re-ground instruction only in the skill body, rejected because a compaction re-injects skills only truncated and may drop the skill entirely, so the instruction to recover is itself lost by the event it must survive.
  - Carry the run-active marker as a working-tree file, rejected because uncommitted it is unreliable (discarded with partial work) and committed it adds history noise that needs a cleanup commit; a branch-scoped version-control-config value is durable without either cost.
  - Inject the re-ground note unconditionally from a hook, rejected because it would surface irrelevant content whenever no run is active; the marker makes the hook conditional.
  - Continue to the next item, or read a resumed message as a fresh task, without re-grounding, rejected because the orchestrator's eroded or stale context mis-conducts the run.
  - Force a compaction automatically at each human-required item, rejected because compaction is the operator's call; the skill recommends it and re-grounds from the ledger regardless.

### D27: Durable review record, condensed verdict gate, and spot-check

- **Question:** Now that review runs as a self-contained stage and only a short verdict returns to the driver, how does the driver gate on review without the verdict silently dropping a gate-blocking finding, and how do a later fix round or an escalation recover the full review?
- **Decision:** The review stage produces a **durable, complete record** of its reconciled findings and returns only a **condensed verdict** to the driver. The verdict is the gate input: it lists findings by severity, **complete at and above the configured threshold** (the brevity budget compresses prose, never the count of gate-blocking findings), and **attests that the review ran at full specialist coverage**. The driver evaluates the commit gate on the verdict and may **spot-check** the durable record (or the changes themselves) against it; the spot-check has no required trigger, so it is not a load-bearing safeguard and the bounded trust rests on the verdict's required completeness and full-coverage attestation and the per-fix re-review, not on it. But when a spot-check does run and finds the record and the verdict disagree (a finding at or above the threshold present in the record but missing from the verdict), the driver treats the verdict as untrustworthy and escalates it as a review failure rather than committing, so the spot-check makes a defined commitment when exercised rather than being a no-op. A verdict that cannot be evaluated against the threshold, reports incomplete coverage, or is empty with no positive clean-coverage attestation is treated as a **review failure** and escalated like a stall (retry, skip, or stop), never as a clean pass: review fails closed, not open ([D17](#d17-no-return-and-stall-handling)). The full record is the input the fix stage reads ([D13](#d13-fix-round-context-preservation)) and the artifact an escalation points the operator to; its per-item location is recorded in the durable progress ledger alongside the commit reference ([D20](#d20-item-to-commit-matching-and-resume-ledger-integrity), [D24](#d24-skip-and-defer-decisions-persist-across-resume)). The record's format and location are left to implementation.
- **Rationale:** Offloading review to a self-contained stage ([D11](#d11-full-review-fidelity-preserved)) means the driver can no longer see the panel's reasoning; it sees only what comes back. If that return is also the only place the findings exist, the brevity that keeps the driver's context cheap ([D12](#d12-driver-defined-dispatch-contract-and-compact-returns)) competes directly with the completeness the commit gate ([D4](#d4-completion-gate-severity-threshold)) depends on: on a slice with many findings, a short verdict cannot enumerate them all, and any dropped or down-severitied blocking finding lets a defective item commit through a gate that reports "clear." Splitting the return into a durable full record plus a condensed verdict dissolves that competition: completeness lives in the record (outside the driver's context), and the verdict stays cheap because it no longer has to BE the record, only to summarize it gate-decidably and point to it. Build output is distrusted and independently re-verified ([D8](#d8-independent-verification-before-commit)) because tests can be re-run; a review verdict is a judgment that cannot be re-run, so it is trusted as returned. That trust is bounded rather than blind: the completeness-at-threshold requirement and the full-coverage attestation constrain what a clean verdict can hide, the fix loop re-reviews each round, and an unattestable or non-evaluable verdict fails closed to an escalation instead of passing; the spot-check is an optional best-effort aid on top of these, not one of the relied-upon safeguards.
- **Evidence:** The review restructuring ([D11](#d11-full-review-fidelity-preserved), [D12](#d12-driver-defined-dispatch-contract-and-compact-returns)); the commit gate ([D4](#d4-completion-gate-severity-threshold)); independent build verification and its verify-before-trust rationale ([D8](#d8-independent-verification-before-commit)); the durable ledger ([D20](#d20-item-to-commit-matching-and-resume-ledger-integrity), [D24](#d24-skip-and-defer-decisions-persist-across-resume)); the documentation-track and ledger precedent in an existing internal skill that persists a full per-item review document (a current-iteration review file plus retained per-iteration history) and threads only that document's path and an open-gate status back through a durable state file, keeping the orchestrating context small while the full review stays on disk; review findings (R7) that the gate trusted an unguaranteed verdict (F47), that an empty, partial, or non-evaluable verdict was indistinguishable from a clean pass (F48), that the build-distrusted / review-trusted asymmetry was unstated (F49), and that the fix stage was not given the review's findings (F51).
- **Rejected alternatives:**
  - Cram completeness into the condensed verdict by requiring it to list every finding, rejected because it collides with the brevity budget on a heavy slice and reintroduces the per-item context cost the skill exists to avoid; the durable record holds completeness instead.
  - Independently re-run the review the way build is re-verified, rejected because a review is a judgment, not a re-runnable command; the spot-check is the available partial cross-check, not an equivalent.
  - Treat an empty or unparseable verdict as a clean pass, rejected because it lets an item commit on a review that never ran or never completed; the verdict fails closed to an escalation instead.
  - Commit an item with review deferred when the review stage is down, rejected because committing unreviewed code defeats the gate that is the feature's headline value; a review outage escalates (retry, skip, or stop), it does not lower the bar.
