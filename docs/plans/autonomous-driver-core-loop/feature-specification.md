# Feature Specification: Autonomous Driver — Core Loop

A Han skill that takes a trusted set of work items and drives their implementation end to end, dispatching the building and the reviewing to sub-agents and committing each finished item, running fully unattended and halting the whole run on any item it cannot complete on its own. This is the first, deliberately narrow slice of the larger autonomous-implementation-driver design ([reference plan](../autonomous-implementation-driver/feature-specification.md)); the human-in-the-loop path, clean-stop, resume, compaction recovery, and the rich blocker menu are all deferred to follow-on features ([D1](artifacts/decision-log.md#d1-core-scope-and-outcome)).

## Outcome

Given a trusted `work-items.md` and the committed spec or plan its items reference, the operator runs one skill and gets each work item built with `tdd` (test-first), independently verified against the project's own checks (or scope-checked with the operator's confirmation where a project defines none), reviewed at full specialist coverage ([D9](artifacts/decision-log.md#d9-self-contained-full-coverage-review-with-a-condensed-verdict-gate)), fixed until it clears a quality gate, and committed (one commit per item) on a dedicated branch, without the operator hand-invoking `tdd` and `code-review` per item. The operator confirms the run plan once at the start and is not asked anything else: the run either completes every item or halts on the first item it cannot finish cleanly, leaving the items completed so far committed and reporting exactly where and why it stopped ([D6](artifacts/decision-log.md#d6-halt-the-whole-run-on-any-unresolvable-item)).

## Actors and Triggers

- **Actors**
  - **Operator:** the solo or small-team engineer who has already planned the feature and broken it into trusted work items, and now wants the build driven for them unattended.
  - **Implementer sub-agents:** disposable sub-agents the skill dispatches to build each item with `tdd`, the non-interactive build skill ([D16](artifacts/decision-log.md#d16-per-item-implementation-skill)).
  - **Reviewer sub-agents:** the self-contained review stage the skill dispatches to audit each item's changes at full specialist coverage (running `code-review`'s specialist panel). The stage returns a condensed verdict the skill gates on and persists a durable full record of its findings ([D9](artifacts/decision-log.md#d9-self-contained-full-coverage-review-with-a-condensed-verdict-gate)).
- **Triggers:** the operator invokes the skill, pointing it at a `work-items.md` file. Optional inputs let the operator set the review gate threshold, the fix-loop cap, the model the build and fix sub-agents run on, the branch name, and an override for the auto-detected verification commands.
- **Preconditions**
  - The work items are already produced and trusted (the operator ran the planning and work-item skills first; this skill does not produce or harden them).
  - Every work item is typed **`AFK`**: no item needs a human before it starts. Items typed `HITL` are out of scope for this core and are caught by up-front validation of the `Type` marker ([D13](artifacts/decision-log.md#d13-input-validation-preconditions)).
  - The spec or plan the items reference is committed and readable, so each sub-agent can read it before building ([D1](artifacts/decision-log.md#d1-core-scope-and-outcome)).
  - Each work item carries an `expected-paths` declaration (a best-effort list the producer derives from the plan's named touch points and Step-3 codebase exploration, which the operator confirms; when the plan gives no file-level detail the producer flags the item's paths as low-confidence rather than inventing them) and a `Type` marker (`AFK` or `HITL`); both fields are added by companion changes to the work-item producer that ship with this core ([D19](artifacts/decision-log.md#d19-companion-changes-to-the-work-item-producer)).
  - The dependency graph across the items is well-formed: no cycles, no duplicate item identifiers, and every `Depends on` reference names an item present in the file ([D13](artifacts/decision-log.md#d13-input-validation-preconditions)).
  - The working tree is clean and, where the project defines verification commands, the test suite is green before the run starts, so per-item commits stay clean and new breakage is distinguishable from pre-existing breakage. The run's own uncommitted planning artifacts (the spec, research, and plan the items reference, plus the work-items file itself) are the one exception: they do not block, because the preparation step commits them first ([D14](artifacts/decision-log.md#d14-start-preconditions-clean-tree-and-green-suite), [D15](artifacts/decision-log.md#d15-minimum-workspace-preparation)).
  - The operator runs the skill on a session model capable of the coordination role. The skill's own judgment runs on the operator's session model, so a weak session model degrades how it sequences items, reads sub-agent reports, and decides when to halt ([D12](artifacts/decision-log.md#d12-model-selection-policy)).

## Primary Flow

1. **Prepare and validate (read-only).** The operator invokes the skill against a `work-items.md`. The skill first runs only read-only checks, so a refusal or a declined plan leaves the repository untouched ([D15](artifacts/decision-log.md#d15-minimum-workspace-preparation)): it determines the project's verification commands from the project's own configuration (the resolved set, or scope-check-only mode where the project defines none, is surfaced for the operator to confirm or override at the plan preview, not as a separate prompt, [D17](artifacts/decision-log.md#d17-plan-preview-and-confirmation-before-the-run)) and checks the tooling they need is available; it confirms the working tree is clean apart from the run's own planning artifacts (the work-items file the operator passed plus the spec, research, and plan files that file names as its context; source files the items target do not count as planning artifacts); where the project defines verification commands it confirms the suite is green, and a project with none takes the scope-check-only path confirmed at the plan preview ([D7](artifacts/decision-log.md#d7-independent-verification-and-scope-check-before-commit), [D14](artifacts/decision-log.md#d14-start-preconditions-clean-tree-and-green-suite)); it confirms the target branch does not already carry a prior run's planning-artifacts commit ([D14](artifacts/decision-log.md#d14-start-preconditions-clean-tree-and-green-suite)); and it validates the items, a well-formed dependency graph, the presence of the `expected-paths` and `Type` fields, and that no item is typed `HITL` ([D13](artifacts/decision-log.md#d13-input-validation-preconditions)), building the run order from their stated dependencies. An empty file, one with no buildable items, or one containing any `HITL`-typed item is a startup refusal, not a partial run. Any of these failing stops the run before anything is branched or committed.
2. **Confirm the plan, then set up.** The skill shows the operator the run plan (the effective run configuration the run will use — the review gate threshold, the fix-loop cap, the build/fix model, the branch the per-item commits will land on including an auto-derived branch name, the verification configuration the run will use (the resolved verification commands, or scope-check-only mode where the project defines none), and the planning-artifact set that will be committed first — followed by the items in dependency order, each named with its build skill (`tdd`)) and waits for the operator to **confirm** or **decline** (which stops the run, having mutated nothing) before any work begins ([D17](artifacts/decision-log.md#d17-plan-preview-and-confirmation-before-the-run)). Only after the operator confirms does the skill mutate the repository: it creates the dedicated branch, commits the planning artifacts as the first commit, and initializes the uncommitted work-state file ([D15](artifacts/decision-log.md#d15-minimum-workspace-preparation), [D18](artifacts/decision-log.md#d18-uncommitted-single-pass-work-state)); per-item commits never land on a shared mainline by default.
3. The skill processes items **one at a time** in dependency order ([D2](artifacts/decision-log.md#d2-serial-one-item-at-a-time-processing)). For each item it drives a fixed per-item loop ([D3](artifacts/decision-log.md#d3-per-item-loop-shape)):
   1. **Build.** The skill dispatches an implementer sub-agent to build the item, handing it the work item, the spec and contract sections the item references, the project's conventions, an explicit instruction to run `tdd` ([D16](artifacts/decision-log.md#d16-per-item-implementation-skill)), and the exact compact report format it must return ([D10](artifacts/decision-log.md#d10-driver-defined-dispatch-contract)). The sub-agent returns that compact report (status, files changed, the final gate result, any blocker, and the observed test-failure-then-pass evidence when the skill is `tdd`), short enough for the skill to decide from the report alone without reading the diff. A build that produces no file changes — or whose only changes are to files the scope check excludes (files the project ignores, code-generation or sync output, and the driver's own artifacts) — halts the run, so a semantically empty commit is never made ([D6](artifacts/decision-log.md#d6-halt-the-whole-run-on-any-unresolvable-item)). A `tdd` build report missing the required test-failure-then-pass evidence is treated as an untrustworthy report and halts the run rather than proceeding as if the item had been built test-first ([D6](artifacts/decision-log.md#d6-halt-the-whole-run-on-any-unresolvable-item), [D10](artifacts/decision-log.md#d10-driver-defined-dispatch-contract)).
   2. **Verify.** The skill does not trust the sub-agent's "all green." Verify is two independent checks. First, it re-runs the project's own verification commands (tests, type-checking, any required code-generation or sync step, lint, build) and trusts those results over the sub-agent's self-report or editor diagnostics ([D7](artifacts/decision-log.md#d7-independent-verification-and-scope-check-before-commit)). A command that runs and reports failures is handled by the fix loop (below); a command that fails to execute (a missing or removed tool, a required service down, a full disk) is instead surfaced as a tooling or environment problem and halts the run, rather than being fed into the fix loop as if the code were at fault ([D6](artifacts/decision-log.md#d6-halt-the-whole-run-on-any-unresolvable-item), [D7](artifacts/decision-log.md#d7-independent-verification-and-scope-check-before-commit)). Second, it inspects the set of changed files against the item's declared expected paths, treating each added, modified, or deleted path against those paths (so an item that renames a file — a delete plus an add — must declare both the old and new paths) and excluding files the project ignores, any code-generation or sync output produced by any step in the per-item loop (the build or the verification step), and the driver's own artifacts (the work-state file and the durable review record). A change to a file outside the declared paths halts the run rather than being silently committed ([D6](artifacts/decision-log.md#d6-halt-the-whole-run-on-any-unresolvable-item), [D7](artifacts/decision-log.md#d7-independent-verification-and-scope-check-before-commit)).
   3. **Review.** The skill runs a review of the item's changes as a self-contained stage, giving it the work item and the spec sections the item references so it can judge the change against what the item asked for. The review runs at the same specialist coverage a manual review would apply, checks both code quality and that the change does not go beyond what the item asked for, **persists a durable full record of its findings** (a driver artifact kept out of commits, readable by the fix sub-agent during the run and retained after a halt so the operator can read the full findings, [D9](artifacts/decision-log.md#d9-self-contained-full-coverage-review-with-a-condensed-verdict-gate), [D18](artifacts/decision-log.md#d18-uncommitted-single-pass-work-state)), and returns a **condensed verdict** listing its findings by severity, complete at and above the gate threshold and attesting that the review ran at full coverage ([D9](artifacts/decision-log.md#d9-self-contained-full-coverage-review-with-a-condensed-verdict-gate), [D10](artifacts/decision-log.md#d10-driver-defined-dispatch-contract)). A verdict the skill cannot trust as a clean pass — empty without a coverage attestation, reporting a partially-covered panel, or not evaluable against the threshold — halts the run rather than being treated as a clear gate ([D6](artifacts/decision-log.md#d6-halt-the-whole-run-on-any-unresolvable-item), [D9](artifacts/decision-log.md#d9-self-contained-full-coverage-review-with-a-condensed-verdict-gate)).
   4. **Fix to the gate.** The bounded fix loop is entered either when verify's commands report failures or when the review reports any finding at or above the configured severity threshold (by default, any Critical or Warning finding ([D4](artifacts/decision-log.md#d4-completion-gate-severity-threshold))). Each round has the item fixed by a fresh sub-agent that works from the original build context, the review's durable record, and the current cumulative diff (the working tree against the item's base commit at the start of this item), then re-verifies ([D5](artifacts/decision-log.md#d5-bounded-fix-loop-cap-then-halt), [D11](artifacts/decision-log.md#d11-fresh-fix-sub-agent-with-curated-context)). Re-verify has four outcomes: verification commands that report failures make it a **not-cleared round** that loops to the next fix without a review, so the panel never reviews known-broken code; a verification command that **fails to execute** halts the run as an environment problem; an **out-of-path change** halts the run immediately, naming the file rather than reporting "gate not cleared"; and a **pass** advances to re-review. Re-review likewise has three outcomes: a clean verdict commits the item; gate-blocking findings make it a not-cleared round that loops to the next fix; and an untrustworthy verdict halts the run immediately (the same fail-closed handling as the initial review), never counted as a not-cleared round. The loop repeats until the gate clears or the configured cap is reached; a cap of zero enters no fix round and halts on the first gate-blocking finding. If the cap is reached with the gate still not clear, the run halts with the residual findings listed and reported as "gate not cleared" ([D5](artifacts/decision-log.md#d5-bounded-fix-loop-cap-then-halt), [D6](artifacts/decision-log.md#d6-halt-the-whole-run-on-any-unresolvable-item)).
   5. **Commit.** Once verification is green and the review reports no finding at or above the threshold, the skill commits the completed item as a single clean code commit following the project's commit convention, staging only the item's own code changes (and any project-tracked generation output) and never the driver's own artifacts — the uncommitted work-state file and the durable review record are kept out of every code commit ([D8](artifacts/decision-log.md#d8-one-commit-per-completed-item), [D18](artifacts/decision-log.md#d18-uncommitted-single-pass-work-state)). It then records the item done in the work-state file (with the code commit's reference and the review-record location), reports the commit's short reference to the operator, and advances to the next item.
4. The skill repeats until every item is complete or the run halts, then reports the completion summary: the branch name, each item's outcome (built and committed with its commit reference, or the one item that halted the run and why), the items not reached, and the next action for the operator (review and push the branch; sharing the branch is the operator's step) ([D8](artifacts/decision-log.md#d8-one-commit-per-completed-item)).

## Alternate Flows and States

### The run halts on an item it cannot complete

- **Entry condition:** during a per-item loop the skill hits a state it cannot resolve unattended: a sub-agent escalates a blocker it cannot resolve (the spec contradicts the item, the acceptance criteria are unsatisfiable, or the item cannot be built as written); the build produces no file changes (or only excluded ones), or its `tdd` report is missing the required test-failure-then-pass evidence; a verification command fails to execute; a changed file escapes the item's declared paths; the fix loop reaches its cap without clearing the gate; the review verdict cannot be trusted as a clean pass; or a commit is rejected ([D6](artifacts/decision-log.md#d6-halt-the-whole-run-on-any-unresolvable-item)).
- **Sequence:** the skill stops advancing. It does not attempt any of the operator-interactive recovery paths (triage, accept-a-flagged-change, gate override, repair-upstream, defer, skip) that the larger design offers — those are deferred. It presents the halt using a consistent frame with five named parts: a **status line** (which item and phase, and its position in the run order); a **one-sentence reason**; a **tree-state disclosure** (the uncommitted files belonging to the halting item, and a statement that the items completed before the halt remain committed on the branch); the **supporting evidence** (which sub-agent raised it, the relevant spec or acceptance criteria, and the raw verification output or residual findings), and, when the halt is review-gated, a pointer to the durable review record; and a **what-to-do-next** part.
- **What to do next:** because the run does not resume, re-invoking the skill starts a fresh run from the first item ([D18](artifacts/decision-log.md#d18-uncommitted-single-pass-work-state)). So the what-to-do-next part tells the operator to resolve the halting item's cause (amend the spec, fix the item, or build it by hand), names a resolution suited to the halt kind, states that a fresh re-invocation must be on a clean tree and a branch that does not already carry this run's commits (so the operator commits or stashes the halting item's work and starts a fresh branch, or cherry-picks the completed items forward by hand), and names the branch and the commit range of the completed items so the operator can reference them. If the halt names an item whose own changes look correct, it also notes that the failure may come from an earlier committed item interacting with this one, which the operator can check by inspecting the branch without this item's changes.
- **Exit:** the skill emits the completion summary naming the run as partially complete (how many items committed, which item halted it and why, and which items were not reached) and stops.

### The project defines no verification commands

- **Entry condition:** the skill cannot find any verification commands in the project's configuration.
- **Sequence:** rather than treating an empty check as a vacuous pass, the skill surfaces this as the run's verification configuration in the plan preview, in plain language (no verification commands were found; the run will check only that each item's changed files match its declared expected paths, with no test, lint, or build re-run), so the operator's confirm of the plan is the conscious confirm of the **scope-check-only** gate — not a separate prompt ([D7](artifacts/decision-log.md#d7-independent-verification-and-scope-check-before-commit), [D17](artifacts/decision-log.md#d17-plan-preview-and-confirmation-before-the-run)).
- **Exit:** on confirmation the run proceeds, each item's verify (both the initial verify and the fix loop's re-verify) performing only the expected-paths scope check. Because no verification commands run, the code-generation exclusion tied to the verification step does not apply, and a fix round's re-verify can only pass (advancing to re-review) or find an out-of-path change (halting the run), never a verification-failure not-cleared round. On decline the run stops before any repository mutation.

## Edge Cases and Failure Modes

| Condition | Required Behavior |
|-----------|-------------------|
| Working tree is dirty at start with changes unrelated to the run's planning artifacts | The skill refuses to start and asks the operator to commit or stash first; the unrelated-change check runs before the planning-artifact commit so nothing extra is folded in. The run's own spec, research, plan, and work-items file are committed as the first commit instead of blocking ([D14](artifacts/decision-log.md#d14-start-preconditions-clean-tree-and-green-suite), [D15](artifacts/decision-log.md#d15-minimum-workspace-preparation)). |
| Test suite is already red at start | The skill refuses to start, because it cannot tell newly introduced breakage from pre-existing breakage, and the refusal names the remedy (get the suite green, or narrow the configured verification command to exclude the known-failing tests, then re-invoke) ([D14](artifacts/decision-log.md#d14-start-preconditions-clean-tree-and-green-suite)). |
| Dependency graph is malformed | The skill refuses to start, names the offending items, and names the fix: break the cycle, de-duplicate the identifier, or repair the `Depends on` reference to a missing item, then re-invoke ([D13](artifacts/decision-log.md#d13-input-validation-preconditions)). |
| A work item is typed `HITL` | The skill refuses to start and names the offending items, because this core drives only `AFK`-typed items; the refusal tells the operator to remove or replace the flagged items (or wait for the follow-on feature that adds the HITL path) before re-invoking ([D13](artifacts/decision-log.md#d13-input-validation-preconditions)). |
| The work-items file is empty or contains no buildable items | The skill reports a startup error stating the file must contain at least one buildable item and stops before any branch or commit, rather than showing an empty preview and reporting zero items done ([D13](artifacts/decision-log.md#d13-input-validation-preconditions)). |
| The expected-paths field is missing on an item | The skill refuses to start, names the item, and tells the operator to re-run the work-item producer to generate the field or add it to the item before re-invoking, because the expected-paths declaration ships with this core and the scope check depends on it; the missing-field fallback the larger design offers is deferred ([D13](artifacts/decision-log.md#d13-input-validation-preconditions), [D7](artifacts/decision-log.md#d7-independent-verification-and-scope-check-before-commit)). |
| The `Type` marker is missing on an item | The skill refuses to start, names the item, and tells the operator to re-run the work-item producer to generate the field or add it to the item before re-invoking, because the `Type` marker ships with this core and the startup HITL check depends on it ([D13](artifacts/decision-log.md#d13-input-validation-preconditions)). |
| The target branch already carries a prior run's planning-artifacts commit | The skill refuses to start and names the branch, directing the operator to a fresh branch, because the run is single-pass with no resume and re-running on the existing branch would rebuild already-committed items ([D14](artifacts/decision-log.md#d14-start-preconditions-clean-tree-and-green-suite), [D18](artifacts/decision-log.md#d18-uncommitted-single-pass-work-state)). |
| A preparation step fails: the branch cannot be created, a required verification command will not run, or the planning-artifact commit is rejected (for example by a pre-commit hook) | The skill reports exactly what failed and stops before processing any item, rather than proceeding without a branch, without working tooling, or without the planning commit ([D15](artifacts/decision-log.md#d15-minimum-workspace-preparation)). |
| Some required tooling is available and some is not (for example tests run but the type-checker is missing) | The skill treats any missing required command as "tooling unavailable" and stops, naming every missing command and telling the operator to install them and make them runnable before re-invoking, rather than silently running a weakened gate ([D15](artifacts/decision-log.md#d15-minimum-workspace-preparation)). |
| No verification commands are configured for the project at all | Distinct from missing tooling: the skill surfaces this in the plan preview as the run's verification configuration (in plain language, naming what will and will not be checked) so the operator's plan confirmation is the conscious confirm of a scope-check-only run, rather than a separate prompt ([D7](artifacts/decision-log.md#d7-independent-verification-and-scope-check-before-commit), [D17](artifacts/decision-log.md#d17-plan-preview-and-confirmation-before-the-run)). |
| Implementer reports green but independent verification reports failures | The skill does not commit; it treats a command that runs and reports failures as a fix-loop round and, if unresolved within the cap, halts the run, trusting the project's own checks over the self-report ([D7](artifacts/decision-log.md#d7-independent-verification-and-scope-check-before-commit), [D6](artifacts/decision-log.md#d6-halt-the-whole-run-on-any-unresolvable-item)). |
| A verification command fails to execute mid-run (a missing or removed tool, a required service down, a full disk), as distinct from one that runs and reports failures | The skill treats this as a tooling or environment problem, surfaces it with its raw output, and halts the run rather than feeding it into the fix loop as if the code were at fault ([D6](artifacts/decision-log.md#d6-halt-the-whole-run-on-any-unresolvable-item), [D7](artifacts/decision-log.md#d7-independent-verification-and-scope-check-before-commit)). |
| Code-generation or sync output, lock files, or ignored files change during the per-item loop | These are not treated as out-of-slice changes; the changed-file inspection excludes files the project ignores, any generation or sync output produced by any step in the per-item loop (build or verify), and the driver's own artifacts (the work-state file and the durable review record) ([D7](artifacts/decision-log.md#d7-independent-verification-and-scope-check-before-commit)). |
| An item's change touches a file outside its declared expected paths, including a rename | The skill halts the run, naming the out-of-path file, rather than committing it; the accept-as-intentional and cross-slice paths the larger design offers are deferred. A rename appears as a delete of the old path plus an add of the new one, so an item that renames a file must declare both paths or the run halts on the undeclared one; a deleted declared path counts as in-scope ([D6](artifacts/decision-log.md#d6-halt-the-whole-run-on-any-unresolvable-item), [D7](artifacts/decision-log.md#d7-independent-verification-and-scope-check-before-commit)). |
| A build sub-agent produces no file changes, or only changes to excluded files | The skill halts the run rather than committing an item with no work behind it; the "no file changes" check is evaluated after exclusions, so a build whose only changes are ignored, generated, or the driver's own artifacts is treated as no change and halts, never producing a semantically empty commit ([D6](artifacts/decision-log.md#d6-halt-the-whole-run-on-any-unresolvable-item), [D16](artifacts/decision-log.md#d16-per-item-implementation-skill)). |
| A `tdd` build report is missing the required test-failure-then-pass evidence | The skill treats the report as untrustworthy and halts the run rather than committing an item that may not have been built test-first ([D6](artifacts/decision-log.md#d6-halt-the-whole-run-on-any-unresolvable-item), [D10](artifacts/decision-log.md#d10-driver-defined-dispatch-contract)). |
| An out-of-path change or an untrustworthy review verdict occurs during a fix round | The skill halts the run immediately, naming the out-of-path file or the untrustworthy verdict, rather than counting it as a not-cleared fix round and later reporting "gate not cleared"; only a verification command that reports failures counts as a not-cleared round ([D5](artifacts/decision-log.md#d5-bounded-fix-loop-cap-then-halt), [D6](artifacts/decision-log.md#d6-halt-the-whole-run-on-any-unresolvable-item), [D9](artifacts/decision-log.md#d9-self-contained-full-coverage-review-with-a-condensed-verdict-gate)). |
| Fix-loop cap is configured as 0 | The fix loop is not entered; the run halts on the first gate-blocking finding with the review findings listed, no fix attempt made ([D5](artifacts/decision-log.md#d5-bounded-fix-loop-cap-then-halt)). |
| Fix loop reaches its cap without clearing the gate | The skill halts the run with the residual findings listed, reserving "unsatisfiable" language for the build-never-passes case and reporting a cap-reached halt as "gate not cleared" ([D5](artifacts/decision-log.md#d5-bounded-fix-loop-cap-then-halt), [D6](artifacts/decision-log.md#d6-halt-the-whole-run-on-any-unresolvable-item)). |
| The review verdict cannot be trusted as a clean pass: empty with no coverage attestation, a partially-covered panel, or not evaluable against the threshold | The skill does not treat it as a cleared gate; it halts the run, and never commits unreviewed or partially-reviewed work ([D9](artifacts/decision-log.md#d9-self-contained-full-coverage-review-with-a-condensed-verdict-gate), [D6](artifacts/decision-log.md#d6-halt-the-whole-run-on-any-unresolvable-item)). |
| A later item's verification fails because of a regression in an already-committed earlier item | The whole-suite re-run surfaces the failure while building the later item, so the halt may name an item whose own changes look correct; the halt's what-to-do-next notes that the cause may be an earlier committed item interacting with this one, which the operator can confirm by inspecting the branch without this item's changes. Automatic culprit attribution and repair-upstream recovery are deferred ([D6](artifacts/decision-log.md#d6-halt-the-whole-run-on-any-unresolvable-item)). |
| A code commit is rejected mid-run (a pre-commit hook, a lock) | The skill does not advance and does not discard the verified, reviewed work; it surfaces the failure and its remedy and halts, leaving the work in the tree ([D6](artifacts/decision-log.md#d6-halt-the-whole-run-on-any-unresolvable-item), [D8](artifacts/decision-log.md#d8-one-commit-per-completed-item)). |
| Review surfaces few or no findings on a tiny slice because of its size calibration | The gate is evaluated against the findings the review actually surfaces at the size it assigns the slice; the skill does not invent findings or force a larger review ([D4](artifacts/decision-log.md#d4-completion-gate-severity-threshold)). |

## User Interactions

- **Affordances:** the operator invokes the skill with a work-items file and optional inputs: the review gate threshold, the fix-loop cap, a model override for the build and fix sub-agents, the branch name, and an override for the auto-detected verification commands. The skill sets the build/fix model explicitly for what those sub-agents do rather than letting them inherit the operator's session model; the models used inside review are governed by the `code-review` skill ([D12](artifacts/decision-log.md#d12-model-selection-policy)). The plan preview ([D17](artifacts/decision-log.md#d17-plan-preview-and-confirmation-before-the-run)) shows the full effective configuration (the gate threshold, the fix-loop cap, the build/fix model, the branch, the verification configuration including scope-check-only mode where the project defines none, and the planning-artifact set), and the operator confirms or declines. This one confirmation is the only planned operator touchpoint after invocation; there is no separate scope-check-only prompt and no mid-run re-prompt, because the run is single-pass and unattended and either completes or halts.
- **Feedback:** the skill keeps an unattended run legible. It narrates the preparation steps as they happen, shows a per-item status header (the item, its position in the run order, and the phase beginning) and a dispatch notification when each sub-agent it dispatches starts, and streams each such sub-agent's compact report (the review stage runs self-contained, so the skill surfaces its dispatch and its returned verdict rather than its inner panel member by member). Because the skill runs the verification commands itself rather than through a sub-agent, it emits the commands it is running at the start of the verify phase and a one-line pass or fail result when each finishes; and it labels each fix round with its number and the cap (for example "fix round 2 of 3") so the operator can gauge how close the item is to a cap-reached halt. It reports each commit's short reference at commit time, emits a one-line run summary at each item boundary (done, remaining), and ends with the completion summary.
- **Error states:** precondition and preparation failures are reported as a refusal to start that names both the reason and the remedy; a halt is presented with the five-part frame (status line, one-sentence reason, tree-state disclosure, evidence with a durable-review-record pointer when review-gated, and what-to-do-next) so the operator can act without a separate `git status` investigation; and a decline is acknowledged with a confirmation that no branch was created and nothing was committed, plus the suggested next step (adjust the work-items file or the invocation inputs and re-invoke).

## Out of Scope

- **Producing or hardening the work items.** Breaking a plan into work items and stress-testing it belong to the planning and work-item skills; this skill consumes a trusted result.
- **Specifying or planning the feature.** Deciding what to build is the job of the feature-spec and implementation-plan skills.
- **Pushing commits or opening pull requests.** The skill commits locally on the run's branch and names that branch in the summary; sharing the result with a remote stays with the operator.
- **Cross-repository orchestration.** A work-items file is single-repository by design; the driver does not coordinate work across repositories.
- **Everything the larger driver design adds beyond the core loop.** The human-in-the-loop item path, interactive-skill items, the clean-stop affordance, resume across sessions, compaction recovery and re-grounding, stall / no-return handling, and the operator-interactive blocker menu (triage, accept-a-flagged-change, gate override, repair-upstream, defer, skip) are all deferred to follow-on features and captured under Deferred (YAGNI).

## Deferred (YAGNI)

Each item below is deferred not because it lacks evidence in the larger design, but because the operator has chosen to build this driver iteratively and ship the core loop first; every deferral names the follow-on feature that reopens it. The full rationale for each lives in the [reference plan](../autonomous-implementation-driver/feature-specification.md).

### Human-in-the-loop items and interactive-skill items

- **Why deferred:** the core drives only `AFK`-typed items. The `Type` (AFK/HITL) marker ships with this core so the driver can refuse `HITL`-typed items at startup, but the HITL handling (the proceed/defer/skip decision gate, the foreground interactive-skill invocation, the confirm-the-work-is-complete checkpoint, and the proceed-mode choice) stays deferred.
- **Reopen when:** the core loop is shipped and the operator plans the follow-on feature that adds the HITL item path (reference plan D6, D21).
- **Source:** operator direction (build the core loop first); reference plan D6, D21.

### Per-item implementation-skill selection

- **Why deferred:** `tdd` is the only non-interactive code-producing build skill in the core today; a per-item `implementation-skill` field would carry exactly one valid value, making it a premature schema hook. An interactive skill cannot be driven unattended by a disposable sub-agent regardless, so narrowing the selection to non-interactive code-producing skills still leaves only `tdd`.
- **Reopen when:** a second non-interactive code-producing skill exists AND the design adds a skill-selection decision tree plus an affordance for the operator to allow non-han skills (for example, "use my skill X for this part").
- **Source:** W-1 implementation, operator direction.

### Clean-stop, cancellation, and mid-run operator interruption

- **Why deferred:** the operator's stated assumption is no interruptions and no cancellation, so the graceful-drain stop affordance and its acknowledge-on-receipt behavior are out.
- **Reopen when:** the follow-on feature that adds the clean-stop affordance is planned (reference plan D18).
- **Source:** operator direction (assume no interruptions, no cancellation); reference plan D18.

### Resume across sessions and committed-ledger integrity

- **Why deferred:** the run is single-pass and the work-state file is uncommitted and assumed always up to date, so the committed resume ledger, the marked bookkeeping commits, the item-to-commit reconciliation, and the skip/defer persistence are all out. The simpler version is a plain uncommitted work-state file used only within the session ([D18](artifacts/decision-log.md#d18-uncommitted-single-pass-work-state)).
- **Reopen when:** the follow-on feature that adds cross-session resume is planned (reference plan D10, D20, D24).
- **Source:** operator direction (single-pass; ledger out of commits, assumed up to date); reference plan D10, D20, D24.

### Compaction recovery and the re-grounding routine

- **Why deferred:** the operator's stated assumption is no compaction, so the re-grounding routine, its durable run-active marker, the conditional startup hook, and all mid-run/mid-preparation compaction handling are out.
- **Reopen when:** the follow-on feature that adds compaction survival is planned (reference plan D26).
- **Source:** operator direction (assume no compaction); reference plan D26.

### Stall and no-return handling

- **Why deferred:** the operator's stated assumption is that commands and sub-agents do not stall, so the no-return detection, the retry/skip/stop stall menu, and the retry-on-a-stronger-model lever are out.
- **Reopen when:** the follow-on feature that adds stall handling is planned (reference plan D17).
- **Source:** operator direction (assume commands and sub-agents/skills don't stall); reference plan D17.

### Operator-interactive blocker recovery

- **Why deferred:** the core halts the whole run on any unresolvable item instead of offering the operator a recovery menu, so on-demand triage, accept-a-flagged-change, gate override, cross-item repair-upstream, defer-this-item, and skip are all out ([D6](artifacts/decision-log.md#d6-halt-the-whole-run-on-any-unresolvable-item)). The simpler version that satisfies the core's evidence is a fail-closed halt with evidence.
- **Reopen when:** the follow-on feature that adds interactive blocker recovery is planned (reference plan D7).
- **Source:** operator direction (halt the whole run; no operator interaction in the core); reference plan D7.

### Reordering items at the plan preview

- **Why deferred:** the reference plan lets the operator reorder items (within the dependency order) at the plan preview, but that affordance needs an input protocol, a dependency display, and constraint-violation feedback that add real interaction surface. The evidence behind the plan preview ([D17](artifacts/decision-log.md#d17-plan-preview-and-confirmation-before-the-run)) is "let the operator see and confirm the run's shape", which the strictly simpler confirm-or-decline preview satisfies; since the run is single-pass, an operator who wants a different order edits the work-items file and re-invokes.
- **Reopen when:** operators routinely need to reorder at the preview rather than by editing the file, or a follow-on feature adds the interaction surface.
- **Source:** review findings (user-experience-designer F-01/F-02 raised the missing reorder protocol; junior-developer F-011 raised it as a YAGNI candidate); operator chose to defer.

### Adding compact structured-output modes to `tdd` and `code-review`

- **Why deferred:** the driver imposes its build-report and review-verdict return contract by dispatch instruction ([D10](artifacts/decision-log.md#d10-driver-defined-dispatch-contract)), so no file change to `tdd` or `code-review` is required for the core. A declared, schema-validated structured-output mode on those skills would make the contract validated rather than merely requested.
- **Reopen when:** the dispatch-instruction contract proves unreliable in practice, or the platform's schema-enforced structured output becomes confirmed for this dispatch path.
- **Source:** operator direction (companion changes limited to the work-item producer fields); reference plan D12.
