# Feature Specification: Autonomous Driver Human-in-the-Loop Support

The autonomous driver (`implement-work-items`) gains the ability to drive work items that need a human — an item whose build runs interactively, whose review is a human read, or which needs a decision before work starts — alongside the fully-autonomous items it already drives, and it gates every review through one normalized verdict so a non-code review can pass or block the loop the same way a code review does.

## Outcome

Given a trusted `work-items.md` whose items may mix fully-autonomous and needs-a-human work, the operator runs the driver once and gets each item built with its recorded implementation skill — dispatched to a sub-agent when the build runs unattended, or run in the foreground with the operator steering when it does not — independently verified whoever built it, reviewed through its recorded review, fixed to the gate, and committed (one item commit, or the adopted commit range when a foreground skill commits its own work, plus an optional decision commit; [D1](artifacts/decision-log.md#d1-scope-hitl-support-and-a-normalized-review-gate), [D14](artifacts/decision-log.md#d14-adopt-a-foreground-skills-own-commits)). The driver reads each item's `Suggested implementation`, `Suggested review`, and `Requires pre-work decisions` markers and routes each phase by them, rather than assuming `tdd` built and `code-review` reviewed ([D2](artifacts/decision-log.md#d2-route-each-phase-by-the-recorded-signals)). Every review — a `code-review` sub-agent, a non-code review agent, or a human read — returns a single normalized verdict the driver gates on identically ([D5](artifacts/decision-log.md#d5-one-normalized-review-gate), [T1](artifacts/feature-technical-notes.md#t1-normalized-review-verdict-and-per-source-severity-mapping)). The run is no longer necessarily unattended: it pauses in-session for a pre-work decision, an interactive build, or a human review, and resumes the moment the operator responds, but it stays single-pass within one session — cross-session resume is not part of this feature ([D9](artifacts/decision-log.md#d9-in-session-state-catch-up-not-compaction-survival)).

The driver still verifies every build itself — a hand-built item is run through the project's verification commands and the scope check exactly like a sub-agent's, so the operator's "it's done" never stands in for a green suite; only the extra build-report parse the driver applies to a sub-agent's return is inapplicable to a foreground build, which is trusted through independent verification and review, not a report ([D3](artifacts/decision-log.md#d3-independent-verification-is-unconditional)). It still processes items one at a time, still owns every commit, and still halts the whole run on the first item it cannot finish cleanly, leaving the finished items committed. What changes is that "cannot finish cleanly" no longer includes "this item needs a human": those items are now driven, not refused.

## Actors and Triggers

- **Actors**
  - **Operator:** the engineer driving a trusted `work-items.md` who is now present during the run — they make each pre-work decision, steer each interactive build, and give each human review its findings, in the same session.
  - **Build sub-agents:** disposable sub-agents the driver dispatches to build an item whose build phase runs unattended (for example `tdd`, `project-documentation`), exactly as today.
  - **Interactive build skill (foreground):** the recorded implementation skill for an item whose build phase does not run unattended (for example `skill-builder`, `refactor`, `runbook`), invoked in the operator's own session so the operator steers it — or, for a bare `none` item, a free-form build the operator and the driver do together with no named skill ([D7](artifacts/decision-log.md#d7-hitl-build-runs-in-the-foreground)).
  - **Review sub-agents and review agents:** the review stage the driver dispatches for an item whose review runs unattended — `code-review` at full specialist coverage as today, or a non-code review agent (`content-auditor`, `information-architect`) — each returning the normalized verdict ([D5](artifacts/decision-log.md#d5-one-normalized-review-gate)).
  - **Human reviewer:** the operator, when an item's review is a human read; they inspect the change and hand the driver their findings in the normalized shape ([D8](artifacts/decision-log.md#d8-hitl-review-collects-human-findings-into-the-normalized-verdict)).
- **Triggers:** the operator invokes the driver against a `work-items.md`, exactly as today, with the same optional inputs (gate threshold, fix cap, model, branch, verification override). No new invocation is required.
- **Preconditions**
  - The work items are already produced and trusted, and carry the per-item markers the producer records (`Suggested implementation`, `Suggested review`, `Requires pre-work decisions`, each build/review marker tagged `AFK` or `HITL`), unchanged from what the producer writes today.
  - Every item's recorded implementation skill is **installed and invocable** — either dispatchable to a sub-agent (an `AFK` skill) or invocable in the operator's session (a `HITL` skill). A named skill (han or non-han) that is neither aborts the whole run at startup ([D4](artifacts/decision-log.md#d4-startup-drivability-abort-only-on-an-undispatchable-named-skill), [D15](artifacts/decision-log.md#d15-drivability-means-installed-and-invocable)).
  - The existing start preconditions hold unchanged: a clean tree apart from the run's planning artifacts, a green suite where the project defines verification commands, a well-formed dependency graph, and a branch that does not already carry a prior run.
  - The operator is present for the run. Because the run pauses in-session for decisions, interactive builds, and human reviews, an unattended invocation of a file containing needs-a-human items will simply wait at the first pause ([D9](artifacts/decision-log.md#d9-in-session-state-catch-up-not-compaction-survival)).

## Primary Flow

1. **Prepare and validate (read-only).** The operator invokes the driver against a `work-items.md`. The driver runs the same read-only preflight it runs today — version check, input resolution, environment detection, planning-artifact identification, clean-tree-and-green-suite confirmation, prior-run refusal, dependency-graph validation — with one change to item validation: it no longer refuses an item because its build or review needs a human, its combination is not `tdd` + `code-review`, or it requires a pre-work decision. Instead it confirms every item is **drivable**: each item's recorded implementation skill is installed and invocable (or is a bare `none` free-form build) and its recorded review is one the driver can turn into a verdict (or falls back to a human read). It aborts the whole run at startup, naming the offenders, only when a named implementation skill is neither dispatchable nor invocable ([D4](artifacts/decision-log.md#d4-startup-drivability-abort-only-on-an-undispatchable-named-skill), [D15](artifacts/decision-log.md#d15-drivability-means-installed-and-invocable)). Nothing is branched or committed in this step.
2. **Confirm the plan, then set up.** The driver shows the run plan as today, and additionally marks each item's **execution mode** so the operator sees where the run will pause: *unattended* (build and review both run in sub-agents, no decision needed), *decision then unattended*, *foreground build* (the operator steers the build in the foreground, whether a named interactive skill drives it or it is a free-form `none` item), or *human review* (the operator reviews before the gate). It discloses once here that the run has no mid-run stop, so the operator knows the commitment before confirming ([D12](artifacts/decision-log.md#d12-mixed-run-legibility-and-pause-signposting)). On confirm, the driver sets up exactly as today (branch, self-ignoring artifact directory, commit-convention detection, run marker, work-state file). On decline, nothing is mutated.
3. The driver processes items one at a time in run order. For each item it drives this loop, narrating each phase, signalling clearly whenever it hands control to the operator versus works unattended, and updating the work-state file:
   1. **Decide, if the item requires it.** When the item's `Requires pre-work decisions` marker is `yes`, the driver pauses before any build with a salient action-needed prompt, presents what the item says must be decided, and waits. The operator makes the decision and records it where the item directs; when the item names no location, the driver asks the operator where to record it (defaulting to the referenced spec or the work item itself). The driver always carries the decision into the build as context, and when the recording produced a durable edit to a committed file it commits that edit and sets the item's scope-check baseline **after** that commit, so the decision edit appears in neither the item's scope diff nor its item commit ([D11](artifacts/decision-log.md#d11-pre-work-decision-gate)). An item with no pre-work decision skips straight to build.
   2. **Build — unattended or foreground.** When the build phase runs unattended, the driver dispatches a build sub-agent running the item's recorded implementation skill and instructs it not to commit, as today ([D2](artifacts/decision-log.md#d2-route-each-phase-by-the-recorded-signals)). When the build phase does not run unattended, the driver marks the foreground boundary, invokes the recorded implementation skill **in the operator's session** with a voiced hand-off ("you are steering; tell me when the build is done and I will verify it"), and waits; a bare `none` item is built free-form by the operator and the driver together, with no named skill ([D7](artifacts/decision-log.md#d7-hitl-build-runs-in-the-foreground)). A foreground build can consume enough context to risk an auto-compaction, so the driver recommends the operator run a manual compaction before it ([D9](artifacts/decision-log.md#d9-in-session-state-catch-up-not-compaction-survival)). When the operator **confirms the work is done**, the driver marks control returned and catches up on run state before continuing ([D9](artifacts/decision-log.md#d9-in-session-state-catch-up-not-compaction-survival)).
   3. **Verify (independent, whoever built it).** The driver runs the project's verification commands itself and performs the scope check against the item's `Expected paths`, exactly as today and regardless of whether a sub-agent or the operator built the item; the build-report parse applies only to a sub-agent's return ([D3](artifacts/decision-log.md#d3-independent-verification-is-unconditional)). A verification failure routes to the fix loop without a review; a tooling-or-environment failure halts. In scope-check-only mode there are no commands to run.
   4. **Review — unattended or human, into one verdict.** When the review phase runs unattended, the driver dispatches the item's recorded review — `code-review` at full specialist coverage, or a non-code review agent — supplying it the reference material it needs to judge the change (the item, the spec sections the item references, and, for a content audit, the prior version of the document being edited), and requires it to return the **normalized verdict** and persist a durable record ([D5](artifacts/decision-log.md#d5-one-normalized-review-gate), [T1](artifacts/feature-technical-notes.md#t1-normalized-review-verdict-and-per-source-severity-mapping)). When the review is a human read, the driver foregrounds it: the operator inspects the change, the driver captures each finding into the same normalized verdict — echoing the captured findings back with each one's tier and whether it gates at the active threshold, and restating that threshold, before the operator **confirms all feedback is given** — and always writes a durable record, recording "none at or above the gate threshold" when the operator reports no findings ([D8](artifacts/decision-log.md#d8-hitl-review-collects-human-findings-into-the-normalized-verdict)). After a foreground review the driver catches up on run state as it does after a foreground build ([D9](artifacts/decision-log.md#d9-in-session-state-catch-up-not-compaction-survival)). Whichever path ran, the driver evaluates one gate against one verdict shape ([T1](artifacts/feature-technical-notes.md#t1-normalized-review-verdict-and-per-source-severity-mapping)). An item whose recorded review is `none` runs no review and has no review gate.
   5. **Fix to the gate (bounded loop, routed by the same signals).** The item clears the gate when verification passed and the normalized verdict reports no finding at or above the threshold; a `none`-review item clears on a verification pass alone, with no verdict required ([D2](artifacts/decision-log.md#d2-route-each-phase-by-the-recorded-signals)). A cleared item commits. Otherwise the driver enters the bounded fix loop, and each round re-enters at the build phase **routed by the same build signal**: an unattended build is fixed by a fresh sub-agent handed the current durable record; an interactive or free-form build is fixed by the operator inline again, with the same foreground boundary markers and state catch-up ([D10](artifacts/decision-log.md#d10-the-fix-loop-routes-back-through-the-same-signals), [D9](artifacts/decision-log.md#d9-in-session-state-catch-up-not-compaction-survival)). The round then re-verifies and, on a pass, re-reviews through the same review path (dispatched agent, or the human again); a `none`-review item re-verifies only. Each review round produces a fresh normalized verdict that overwrites the durable record, so the fix agent reads only the current round's findings and a retracted finding is not re-chased ([D8](artifacts/decision-log.md#d8-hitl-review-collects-human-findings-into-the-normalized-verdict)). The fix agent for an unattended build reads the durable record whether the findings came from an agent or the human, so a human-reviewed item can be fixed unattended. On cap exhaustion the run halts through the existing Halt Procedure, reporting the residual findings.
   6. **Commit.** On a cleared gate the driver commits the item as one clean commit, staged by path — or, when the foreground skill already committed the item's work, reviews the cumulative diff of the item's commits, adopts them as the item's commit(s), and records the commit range instead of forcing an empty commit ([D14](artifacts/decision-log.md#d14-adopt-a-foreground-skills-own-commits)). It records the item done in the work-state file with the commit reference (or range) and review-record path, and advances.
4. The driver repeats until every item is complete or the run halts, then reports the completion summary, which now names each item's execution mode alongside its outcome so a mixed run reads clearly ([D12](artifacts/decision-log.md#d12-mixed-run-legibility-and-pause-signposting)).

## Alternate Flows and States

### An item needs a decision before it starts

- **Entry condition:** the next item's `Requires pre-work decisions` marker is `yes`.
- **Sequence:** the driver pauses before any build with an action-needed prompt, presents what the item says must be decided, and waits. The operator makes the decision and records it where the item directs, or where the driver asks when the item is silent (defaulting to the referenced spec or the item). If that produced a durable edit to a committed file, the driver commits the edit and sets the item's scope-check baseline after that commit, so the edit is not later flagged as a scope escape and is visible to a build sub-agent; it always carries the decision into the build as context ([D11](artifacts/decision-log.md#d11-pre-work-decision-gate)).
- **Exit:** the item proceeds into its build phase (unattended or foreground) with the decision in hand.

### An item's build runs in the foreground

- **Entry condition:** the item's build marker is `HITL`, or the item is a bare `none` (free-form) build.
- **Sequence:** the driver marks the foreground boundary, invokes the recorded interactive skill in the operator's session (or, for `none`, builds free-form with the operator) with a voiced hand-off, recommends a manual compaction first, and waits for the operator to confirm the work is done. On confirm, the driver marks control returned, catches up on run state, then verifies the item independently, exactly as it would a sub-agent's build ([D7](artifacts/decision-log.md#d7-hitl-build-runs-in-the-foreground), [D3](artifacts/decision-log.md#d3-independent-verification-is-unconditional), [D9](artifacts/decision-log.md#d9-in-session-state-catch-up-not-compaction-survival)).
- **Exit:** the item continues to Verify. If the operator reports the work is not done, or the tree is unexpectedly unchanged, the driver does not commit nothing: it either re-foregrounds the skill so the operator can finish, or, when the operator signals the item is unfinishable, halts the run through the Halt Procedure — there is no skip or defer, which stay deferred ([D7](artifacts/decision-log.md#d7-hitl-build-runs-in-the-foreground), [D1](artifacts/decision-log.md#d1-scope-hitl-support-and-a-normalized-review-gate)).

### An item's review is a human read

- **Entry condition:** the item's recorded review is a human read (review marker `HITL`).
- **Sequence:** after verification passes, the driver foregrounds the review: it points the operator at the item's change and the spec sections the item references, and captures each finding the operator gives into the normalized verdict (a tier, a location — a `file:line` for code or a document anchor for prose, and a one-line claim). When a finding is missing a required field the driver asks the operator to supply it rather than guessing. Before the operator confirms all feedback is given, the driver echoes the captured findings back with each one's tier and whether it gates at the active threshold, and restates the threshold. The driver always writes a durable record — "none at or above the gate threshold" when there are no findings — and catches up on run state ([D8](artifacts/decision-log.md#d8-hitl-review-collects-human-findings-into-the-normalized-verdict), [D9](artifacts/decision-log.md#d9-in-session-state-catch-up-not-compaction-survival)).
- **Exit:** the driver evaluates the gate against the captured verdict exactly as for an agent-produced one. Gate-blocking findings enter the fix loop; a clean verdict commits.

### The operator opts in to a review pause on an unattended item

- **Entry condition:** an item's review runs unattended. By default the driver runs it and proceeds straight to the gate without pausing, so a run of fully-autonomous items is uninterrupted and the operator can leave it going in the background and do other things.
- **Sequence:** as each unattended review is about to run, the driver notes that the operator may ask to pause after it finishes, then starts the review immediately without waiting. An operator who wants to weigh in sends that message while the review runs. If the request has arrived by the time the review sub-agent returns its verdict, the driver pauses, lets the operator add findings, and merges the operator's findings and the agent's into the one normalized verdict and durable record. Absent such a request the driver does not stop — it gates on the agent's verdict and continues ([D8](artifacts/decision-log.md#d8-hitl-review-collects-human-findings-into-the-normalized-verdict)).
- **Exit:** with a pending request, the merged verdict gates the item and the operator's findings are fixed in the same loop as the agent's; without one, the agent's verdict gates the item and the run continues uninterrupted.

## Edge Cases and Failure Modes

| Condition | Required Behavior |
|-----------|-------------------|
| An item's recorded implementation skill (han or non-han) is neither dispatchable to a sub-agent nor invocable in-session | The driver aborts the whole run at startup, naming the item and the skill, and tells the operator to install or replace it before re-invoking — the same all-or-nothing startup posture as the core loop ([D4](artifacts/decision-log.md#d4-startup-drivability-abort-only-on-an-undispatchable-named-skill), [D15](artifacts/decision-log.md#d15-drivability-means-installed-and-invocable)). |
| An item's implementation is a bare `none` | Not a refusal: the driver drives it as a free-form foreground build (operator and driver build it together with no named skill), still independently verified and reviewed like any other item ([D4](artifacts/decision-log.md#d4-startup-drivability-abort-only-on-an-undispatchable-named-skill), [D7](artifacts/decision-log.md#d7-hitl-build-runs-in-the-foreground)). |
| A foreground interactive skill commits its own work | The driver does not force an empty commit: it reviews the cumulative diff of the item's commits, adopts them as the item's commit(s), and records the commit range in the work-state file ([D14](artifacts/decision-log.md#d14-adopt-a-foreground-skills-own-commits)). |
| An item's recorded review is one the driver cannot turn into a verdict (for example a `guidance` step that emits no findings) | The driver falls back to treating the review as a human read, foregrounding it for the operator, rather than halting; the companion producer change makes this rare by recording a human read for those items in the first place ([D6](artifacts/decision-log.md#d6-companion-catalog-correction-plus-driver-fallback)). |
| A non-code review agent returns output the driver cannot map into the normalized verdict (a missing section, or an absent coverage attestation) | The driver treats it as an untrustworthy verdict and halts through the existing Halt Procedure, exactly as it treats a malformed `code-review` verdict — it never commits on a verdict it cannot trust as a clean pass. The coverage attestation is generalized per source (a single agent attests it ran to completion; a human read attests the operator reviewed it), so a single-agent or human review does not trip the panel-shaped halt ([D5](artifacts/decision-log.md#d5-one-normalized-review-gate), [T1](artifacts/feature-technical-notes.md#t1-normalized-review-verdict-and-per-source-severity-mapping)). |
| A `none`-review item fails independent verification | It enters the fix loop and re-verifies each round with no review; it clears on a verification pass alone, since it has no review gate to satisfy ([D2](artifacts/decision-log.md#d2-route-each-phase-by-the-recorded-signals), [D10](artifacts/decision-log.md#d10-the-fix-loop-routes-back-through-the-same-signals)). |
| A hand-built (interactive or free-form) item fails independent verification | The driver routes it to the fix loop, which re-enters at the build phase and asks the operator to fix it inline again; the operator's confirm-done never bypasses verification ([D3](artifacts/decision-log.md#d3-independent-verification-is-unconditional), [D10](artifacts/decision-log.md#d10-the-fix-loop-routes-back-through-the-same-signals)). |
| An interactive-build item's tree is unexpectedly unchanged after the operator confirms the work is done | The driver does not commit an empty change: it re-foregrounds the skill, or halts the run when the operator signals the item is unfinishable ([D7](artifacts/decision-log.md#d7-hitl-build-runs-in-the-foreground)). |
| A human-reviewed item has gate-blocking findings and an unattended build | The fix loop routes back to the build signal, so a fresh build sub-agent fixes the item from the human's findings in the durable record; the human is not asked to hand-fix an item a sub-agent built ([D8](artifacts/decision-log.md#d8-hitl-review-collects-human-findings-into-the-normalized-verdict), [D10](artifacts/decision-log.md#d10-the-fix-loop-routes-back-through-the-same-signals)). |
| A non-code AFK build has no test surface (documentation, a vendoring step) | Verification is the scope check plus any project verification commands that apply; the driver does not require test evidence for a deliverable that has none, consistent with the build report's existing untestable path ([D3](artifacts/decision-log.md#d3-independent-verification-is-unconditional)). |
| A non-han skill's autonomy was not declared by the operator | The producer defaults it to not-unattended, so the driver runs its build in the foreground — the safe default — rather than dispatching an unattended sub-agent it cannot trust to be non-interactive ([D2](artifacts/decision-log.md#d2-route-each-phase-by-the-recorded-signals), [D7](artifacts/decision-log.md#d7-hitl-build-runs-in-the-foreground)). |
| A pre-work-decision commit is rejected mid-run (a hook, a lock, a git error) | The driver routes it to the existing Halt Procedure with the five-part frame, naming the rejection and disclosing that no build has started — the same class as the existing commit-rejection halt ([D11](artifacts/decision-log.md#d11-pre-work-decision-gate)). |
| The fix loop reaches its cap on a foreground-built item | The run halts through the existing Halt Procedure with the residual findings; because the tree holds the operator's own hand-built work, the halt names a preserve-the-effort path (commit the work-in-progress on a separate branch before a fresh run) rather than implying it is discardable ([D10](artifacts/decision-log.md#d10-the-fix-loop-routes-back-through-the-same-signals)). |
| An auto-compaction fires during a long foreground build and truncates the driver's own instructions | Surviving this is out of scope (it belongs to the deferred compaction-survival chunk); the driver recommends a manual compaction before a foreground build to avoid it, and if it detects it cannot re-establish its instructions and run state it halts fail-closed rather than continuing on partial state ([D9](artifacts/decision-log.md#d9-in-session-state-catch-up-not-compaction-survival)). |
| The operator's session ends mid-run (a needs-a-human item stranded, a crash) | The run does not resume; a re-invocation starts fresh from the first item on a clean tree and a fresh branch, exactly as the core loop's single-pass model — cross-session resume is out of scope ([D9](artifacts/decision-log.md#d9-in-session-state-catch-up-not-compaction-survival)). |

## User Interactions

- **Affordances:** the operator invokes the driver as today. During the run they make each pre-work decision, steer each interactive build to completion and confirm it is done, hand each human review its findings and confirm the feedback is complete, and may opt in to add feedback on an unattended review by sending a message while it runs, asking to pause after it finishes (the driver announces the option and starts the review immediately, so the operator can decide while it runs); absent such a message the run does not pause for review. The invocation inputs are unchanged; `--model` governs only the sub-agent (AFK) build and fix, not a foreground build or an inline fix.
- **Feedback:** the plan preview marks each item's execution mode and discloses that the run has no mid-run stop, so the operator knows where the run will pause and what the commitment is before confirming. The preview also states how to opt in to a review pause, and as each unattended review begins the driver notes the pause-after-review option and starts the review immediately, so the operator can decide while it runs. Each pause emits a salient action-needed prompt as the last line, carrying the same status line (item, position in the run order, phase, awaiting-you) the Halt Procedure uses; each confirm prompt states its consequence and finality inline ("this closes review for this item and evaluates the gate — you cannot add findings after"); and on handback the driver emits a resumption cue saying whether the operator is free to step away before the next pause. Foreground work is bounded by explicit "you are steering" / "control returned" markers. The completion summary names each item's execution mode alongside its outcome ([D12](artifacts/decision-log.md#d12-mixed-run-legibility-and-pause-signposting)).
- **Error states:** a startup abort names the undispatchable skill and the remedy. A halt uses the existing five-part Halt frame, disclosing any hand-built work left in the tree and, for a foreground-built item, how to preserve it. An untrustworthy or unmappable review verdict is surfaced as a review-gated halt pointing at the durable record.

## Coordinations

| Coordinating System | Direction | Interaction | Ordering / Consistency Requirement |

## Out of Scope

- **Cross-session resume and mid-run clean-stop.** The run stays single-pass within one session; HITL pauses are in-session. Resuming a partially-complete run in a later session, and a mid-run stop affordance, remain deferred to their own follow-ons. The absence of a mid-run stop is disclosed to the operator, not solved here.
- **Compaction-survival re-grounding.** The state catch-up this feature adds is the in-session refresh after inline work erodes context, not the durable-triggered routine that survives an auto-compaction truncating the driver's own instructions. The driver recommends a manual compaction before a foreground build and halts fail-closed if it detects it cannot recover, but full auto-compaction survival is deferred ([D9](artifacts/decision-log.md#d9-in-session-state-catch-up-not-compaction-survival)).
- **The rich blocker menu, skip/defer, and repair-upstream.** A gate the fix loop cannot clear, or any state the driver cannot resolve, halts the whole run through the existing single Halt Procedure; the interactive blocker menu (triage, accept-a-flagged-change, gate override, repair-upstream, defer, skip) stays deferred ([D1](artifacts/decision-log.md#d1-scope-hitl-support-and-a-normalized-review-gate)).
- **Changing the build and review skills or agents themselves.** No changes to `tdd`, `code-review`, `content-auditor`, `information-architect`, `skill-builder`, and so on; the two skills this feature changes are the driver (`implement-work-items`) and, for the catalog correction, the producer (`plan-work-items`).
- **Parallel execution across items.** Items are still built one at a time in a shared working tree.

## Deferred (YAGNI)

### A dedicated non-code reviewer for items kept as human reads

- **Why deferred:** the research found no separate automated reviewer that produces actionable pass/fail findings for new skills, agents, ADRs, coding standards, or runbooks, and their builders already need a human, so those items are kept human-reviewed rather than given a pretend automated gate. Building a new reviewer agent for them has no evidence of need now.
- **Reopen when:** a reference-grounded reviewer that emits gate-able findings exists for one of those deliverable types.
- **Source:** conversation; `reviewing-non-code-work-items.md` (research recommendation O5).

### A single spec-anchored reviewer (`gap-analyzer`) for all non-code items

- **Why deferred:** the operator chose per-source normalization over routing every non-code item through one `gap-analyzer` gate against its acceptance criteria; the single-reviewer option trades domain depth for simpler routing and was not selected. It remains a viable alternative if per-source normalization proves too heavy to maintain.
- **Reopen when:** the per-source severity mapping proves costly to maintain across many reviewers and a single spec-anchored gate would demonstrably simplify it.
- **Source:** conversation (review-gate decision); `reviewing-non-code-work-items.md` (research option O6).

### Convergence / no-new-findings detection for non-code fix loops

- **Why deferred:** the fix loop is already bounded by the configurable cap, which terminates and escalates with the residual findings; a semantic-convergence detector would only escalate a few rounds earlier, and the supporting evidence for it is weak.
- **Reopen when:** non-code fix loops routinely burn their full cap on a finding an earlier convergence signal would have escalated sooner.
- **Source:** `reviewing-non-code-work-items.md` (caveated single-source evidence).
