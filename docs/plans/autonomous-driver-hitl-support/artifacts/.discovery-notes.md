## Authoring guidance that governs the implementation (user-directed: Skill Composition)

`han-plugin-builder/skills/guidance/references/skill-building-guidance/`:

- **`skill-composition.md` (the user's flag — load-bearing for HITL).** Two composition patterns: *orchestration* (thin caller hands heavy work to a sub-skill via the `Skill` tool — supported with discipline) and *data-fetch* (avoid). Sharp edges directly relevant here: (1) *"A Skill call mid-workflow is the moment the calling model is most likely to stop, treating the sub-skill's output as its own final answer"* — must instruct continuation explicitly; (2) *"the more logic the orchestrator carries across a Skill call, the more likely it is to lose track of its own workflow after the sub-skill returns"* — keep the orchestrator thin. **The driver is a HEAVY orchestrator** (whole verify/review/commit/fix loop after any build), so a `Skill`-tool call for a foreground HITL build is the exact high-risk case. A `Skill` caller must also add `Skill` to `allowed-tools`. **Implication (a plan decision):** implement the foreground HITL build as an **operator hand-off** — the driver tells the operator to run the interactive skill in their session and waits for a confirm-done message — rather than the driver calling the `Skill` tool. This keeps the driver's Agent-only dispatch discipline, needs no `Skill` grant, and matches the spec's "the operator steers" (D7). D9's state catch-up covers the context the pause erodes.
- **`agent-dispatch-namespacing.md`.** Dispatch/reference by defining-plugin namespace: `han-coding:code-review`, `han-coding:tdd`, `han-core:content-auditor`, `han-core:information-architect`. Note the **shape difference**: `code-review` is a SKILL (run by a general-purpose sub-agent that fans out its own panel); `content-auditor`/`information-architect` are AGENTS. The normalized-verdict dispatch (a depth-1 general-purpose sub-agent that runs the recorded review and returns the normalized verdict) generalizes cleanly over both — the sub-agent runs the skill OR dispatches/embodies the agent, then maps to the verdict.
- **`context-hygiene.md`.** SKILL.md persists under a ~25k shared post-compaction budget, ~5k/skill; a bloated body can be dropped after compaction. The driver body is already large. **Push new detail to `references/`** (normalized-verdict contract, HITL foreground/hand-off protocol, severity mapping, mixed-run signposting) and keep SKILL.md lean — also mitigates F17 (compaction during a long foreground build). Front-load constraints, back-load checklists; recency bias within steps.
- **`workflow-patterns.md`.** Human gates belong before irreversible actions (commit) and should be 2–3 per skill "circuit breakers"; a HITL driver legitimately has more because HITL is the feature, but keep them at real decision points. `AskUserQuestion` is the structured-gate tool BUT must **not** be added to `allowed-tools` (documented bug — see `allowed-tools-AskUserQuestion.md`). The async opt-in pause (F25) and confirm-done are message-based, not blocking `AskUserQuestion` prompts — fits the walk-away model.

## Conventions the change must follow (CONTRIBUTING.md + root CLAUDE.md)

- Every skill/agent gets a long-form doc under `docs/`; update indexes + root CLAUDE.md when adding/moving. This change edits existing skills, so update their long-form docs and any changed behavior; no new skill/agent is added.
- Writing voice: **no em-dashes**; direct second person; no "leverage/utilize/just/actually/robust/Importantly". `allowed-tools` per-prefix, not wildcards. Context-injection `` !`cmd` `` must stay simple; complex ops go in `scripts/`.
- Plugin boundaries: `han-coding` (driver) and `han-planning` (catalog) both depend on `han-core`, so the driver may dispatch `han-core` agents (`content-auditor`, `information-architect`) freely.
