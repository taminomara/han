# Implementation Discovery Notes: implement-work-items First-Run Hardening

Single source of truth for project context. Specialists: read this first; do not re-grep for what is here. Search further only for what your domain needs that this file does not cover.

## Tech stack

- **This is a Claude Code plugin suite, not a conventional codebase.** The "implementation" is editing a skill: a `SKILL.md` (markdown + shell directives), a set of `references/*.md`, and `scripts/*.sh`. There is no compiled code and no application runtime.
- **Shell is bash.** All scripts use `#!/usr/bin/env bash` and rely on bash features (arrays, `[[ =~ ]]` regex, `mapfile`). There are 18 `.sh` files in the repo.
- **No Python anywhere.** Zero `.py` files in the repo. `python3` appears only in the target skill's `allowed-tools` list and as a *manifest-detection string* in `detect-driver-context.sh` (it detects that the **user's** project uses Python; the skill itself never runs Python).
- **`jq` is optional, not required.** `SKILL.md` Project Context runs `which jq || echo "not installed"`. `jq` is used at exactly one site (Step 2.2, maintaining the ignored `state.json` "if jq is available"); when absent, the model maintains that file by hand. Both shell scripts are pure bash and use **no** `jq`.
- **The skill runs in arbitrary user repositories.** It cannot assume any language runtime, `jq`, or `python3` is installed — the user's repo may be Go, Ruby, JS, etc. The only hard dependency is `git` (the skill halts without it) and a recent Claude Code version.

## Current run-record format (central to the ledger decision)

- **Durable ledger:** `.implement-work-items/progress.md` — **tracked and committed per entry**. Format: a labeled opening config block + one line per entry following the grammar `- <token>: <W-N>`, `<token>` ∈ {`start-of-item`, `done`, `no-commit-done`, `skip`}. Reconstructed by `scan-run-history.sh` with a **pure-bash regex** (`^-[[:space:]]+(start-of-item|no-commit-done|done|skip):...`) plus git trailers read via `git log --format='%(trailers:key=...)'`. No `jq`.
- **Machine state:** `.implement-work-items/state.json` — **gitignored** JSON, per-item `{state, fix-round, scope-baseline, decision, commit-range}`, maintained by `jq`-if-available-else-by-hand. `durable-record-protocol.md` notes most of these fields (fix-counter, decision, body-hash) are re-established within the session, not durable.
- **Ignore rule (Step 2.2):** `.implement-work-items/.gitignore` is two lines — `*` then `!progress.md` — so `progress.md` is tracked and everything else (incl. `state.json`, `reviews/`) is ignored.
- **Trailers (`durable-record-protocol.md`):** run identity `Implement-Work-Items-Run: <normalized path>`, per-item code commit `Implement-Work-Items-Item: <W-N>`, matched by exact trailer key. Done entries reference their commit **positionally** (no stored hash). Integrity is default-deny: any entry not positively classified safe is surfaced-and-asked.
- **Precedent for new scripts:** both existing scripts emit **line-oriented `key: value` pairs plus marker-delimited blocks** (`items-start`/`items-end`, `uncommitted-start`/`uncommitted-end`) and make **no proceed/discard judgment** — they are deterministic detectors the model interprets. Any new bookkeeping script should follow this shape.
