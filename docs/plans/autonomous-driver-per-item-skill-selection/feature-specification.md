# Feature Specification: Per-Item Skill Selection for Work Items

When `plan-work-items` breaks a plan into work items, it now chooses the han skill best suited to build each item's deliverable (its **implementation skill**) and the skill or agent best suited to review it (its **review**), and records — per item — whether the build phase runs unattended, whether the review phase runs unattended, and whether a human decision is required before work starts. These three signals replace the single AFK/HITL `Type` marker; the AFK/HITL distinction becomes a value derived from them. The autonomous driver reads the implementation skill, the review, and the three signals, and dispatches per item instead of assuming `tdd` and `code-review` for everything ([D1](artifacts/decision-log.md#d1-scope-producer-selects-and-driver-consumes)). This reopens the core loop's deferred "Per-item implementation-skill selection" ([reference plan](../autonomous-driver-core-loop/feature-specification.md)); its reopen trigger is only partly met — the decision tree and the non-han affordance are delivered, but no *second* fully-autonomous code skill turned out to exist (`refactor` is interactive), so the reopening rests on the broader per-item value, on recording the signals a human-in-the-loop driver will need, and on operator direction ([D1](artifacts/decision-log.md#d1-scope-producer-selects-and-driver-consumes)).

## Outcome

Given a trusted plan, the operator runs `plan-work-items` and gets a `work-items.md` in which every item carries an **implementation skill**, a **review**, and three recorded signals: whether its **build phase runs unattended**, whether its **review phase runs unattended**, and whether a **human decision is required before work starts** ([D4](artifacts/decision-log.md#d4-recorded-autonomy-signals-replace-the-afkhitl-type)). The producer chooses the skill and review by classifying each item's deliverable nature ([D2](artifacts/decision-log.md#d2-deliverable-nature-decision-tree-and-skill-catalog)), never reaching for `tdd` on a deliverable that has no tests to lead ([D3](artifacts/decision-log.md#d3-tdd-only-for-testable-deliverables)). For a han skill it derives the phase's autonomy from the skill's known behavior; for a user-defined (non-han) skill, whose behavior it cannot infer, it takes the operator's declaration and defaults to not-autonomous when none is given ([D8](artifacts/decision-log.md#d8-non-han-skills-suggested-only-when-no-han-skill-fits)). An item is **fully autonomous** (the derived "AFK") only when its build and review both run unattended and no human decision is needed first; otherwise it **needs a human** (the derived "HITL"). The operator can override the skill, the review, or a non-han skill's declared autonomy for any item ([D7](artifacts/decision-log.md#d7-overrides-by-invocation-instruction-and-pre-written-marker)). Where no han skill fits an item the producer suggests an installed non-han skill or records the item for a human to build, and where the best-fit han skill is not installed it records the item as a bare human item (implementation skill `none`) rather than guessing a substitute ([D8](artifacts/decision-log.md#d8-non-han-skills-suggested-only-when-no-han-skill-fits), [D9](artifacts/decision-log.md#d9-uninstalled-best-fit-falls-back-to-bare-hitl)). The autonomous driver reads all of this and dispatches the recorded skill and review per item; it drives the file only when *every* item is fully autonomous and its skill-and-review combination is one it supports (today, `tdd` built and `code-review` reviewed), and otherwise refuses the whole run at startup, naming the items it cannot drive, before creating a branch ([D5](artifacts/decision-log.md#d5-driver-drivability-is-computed-from-the-signals), [D6](artifacts/decision-log.md#d6-per-item-fields-implementation-skill-review-and-autonomy-signals)).

## Actors and Triggers

- **Actors**
  - **Operator:** the engineer breaking a trusted plan into work items, who may additionally instruct the producer to use a specific skill or review for a named item and to declare a user-defined skill's autonomy.
  - **Work-item producer (`plan-work-items`):** classifies each item's deliverable nature, selects its implementation skill and review, records the three autonomy signals, and writes all of it on the item.
  - **Autonomous driver (`implement-work-items`):** reads the recorded implementation skill, review, and signals on each item, computes whether the item is fully autonomous, and dispatches the skill and review per item — replacing its previously fixed `tdd` + `code-review` assumption and its reliance on a stored `Type` marker ([D1](artifacts/decision-log.md#d1-scope-producer-selects-and-driver-consumes)).
- **Triggers:** the operator invokes `plan-work-items` against a plan or context, exactly as today; the skill selection happens while the items are drafted. No new invocation is required.
- **Preconditions**
  - A plan or context to break down exists (unchanged from today).
  - The candidate skills the producer classifies against are known by name; some ship in plugins that may be absent (`skill-builder`, `agent-builder`, and `guidance` ship in `han-plugin-builder`, not alongside the coding skills), so the producer detects which are installed rather than assuming ([D9](artifacts/decision-log.md#d9-uninstalled-best-fit-falls-back-to-bare-hitl)).
  - For the driver to rely on the new per-item data, every item must carry it; the producer records the implementation skill, the review, and the three signals on every item — a bare item carries an explicit `none` implementation skill, distinct from a field the producer never wrote — and the driver refuses a file whose items omit the fields entirely (a file produced before this feature). The producer change and the driver companion change ship together, because the driver no longer reads the core loop's `Type` field ([D6](artifacts/decision-log.md#d6-per-item-fields-implementation-skill-review-and-autonomy-signals)).

## Primary Flow

1. **Invoke and read overrides.** The operator invokes `plan-work-items` on a plan or context. Alongside locating the plan and inventorying reference artifacts as today, the producer collects any operator overrides: an implementation-skill, review, or non-han-autonomy instruction for an item given in the invocation, or a per-item marker left in the source plan or context, which the producer reads without modifying the source ([D7](artifacts/decision-log.md#d7-overrides-by-invocation-instruction-and-pre-written-marker)).
2. **Classify each item's deliverable nature and select its implementation skill.** For each item the producer classifies what the item produces and selects the matching han skill: new or changed testable code builds with `tdd`; a behavior-preserving restructuring of already-tested code builds with `refactor`; a new Claude Code skill builds with `skill-builder`; a new agent with `agent-builder`; vendoring or refreshing the plugin-building guidance with `guidance`; feature or system documentation with `project-documentation`; an architectural decision record with `architectural-decision-record`; a coding standard with `coding-standard`; a runbook with `runbook` ([D2](artifacts/decision-log.md#d2-deliverable-nature-decision-tree-and-skill-catalog)). It never selects `tdd` for a deliverable that has no tests to drive it, such as documentation or a vendoring step ([D3](artifacts/decision-log.md#d3-tdd-only-for-testable-deliverables)). A work item that spans two deliverable natures (for example, code plus its runbook) is split into separate items following the producer's existing vertical-slice discipline; when it cannot be cleanly split, the producer records the dominant skill and flags the uncovered nature in the breakdown rather than silently dropping it ([D11](artifacts/decision-log.md#trivial-decisions)).
3. **Select each item's review.** The producer selects the review by the same deliverable nature: code is reviewed with `code-review`; a new skill or agent is reviewed against the plugin-building guidance; documentation is reviewed by a content audit (`content-auditor` or `information-architect`); an ADR, runbook, or standard is left for a human read; and a vendoring or guidance step, whose output has no applicable automated review and is verified by re-running, is recorded `none`. The review field's value is a review skill, a review agent, `human read`, or `none` (a bare item, or a step to which no review applies) ([D6](artifacts/decision-log.md#d6-per-item-fields-implementation-skill-review-and-autonomy-signals)).
4. **Record the three autonomy signals.** For each item the producer records whether the **build phase runs unattended**, whether the **review phase runs unattended**, and whether a **human decision is required before work starts**. For a han skill it derives the build signal from the skill's known behavior — `tdd`, `project-documentation`, and `guidance` run unattended; `refactor`, `skill-builder`, `agent-builder`, `architectural-decision-record`, `runbook`, and `coding-standard` stop for a human mid-run — and the review signal from the review's known behavior (`code-review`, `content-auditor`, and `information-architect` run unattended; a `human read` does not; `none` means no review runs). For a user-defined skill it cannot infer behavior, so it takes the operator's declaration and defaults the phase to not-unattended when none is given ([D4](artifacts/decision-log.md#d4-recorded-autonomy-signals-replace-the-afkhitl-type), [D8](artifacts/decision-log.md#d8-non-han-skills-suggested-only-when-no-han-skill-fits)). The pre-work-decision signal marks an item that needs a human decision before any work starts (an architectural decision or a design gate) — a gate resolved once, distinct from a skill that needs a human throughout. A bare item (implementation skill `none`) has no unattended build. From the three signals the producer derives the item's label: **fully autonomous** when the build and review both run unattended and no pre-work decision is required, otherwise **needs a human** ([D4](artifacts/decision-log.md#d4-recorded-autonomy-signals-replace-the-afkhitl-type)).
5. **Apply overrides.** An operator override replaces the selected implementation skill, review, and/or a non-han skill's declared autonomy for its named item; the item's signals are recomputed. A han override re-derives the affected signal from the new skill; a non-han override uses the operator's declaration (defaulting to not-unattended). An override that pairs a skill with a deliverable of a different kind — `tdd` on a non-testable deliverable, or any skill on a mismatched nature — is honored (the operator has final say) but flagged as a mismatch in the breakdown. The producer binds each override to an item by the operator's description and reports how it resolved — applied to which item, unmatched, or ambiguous — rather than silently dropping one ([D7](artifacts/decision-log.md#d7-overrides-by-invocation-instruction-and-pre-written-marker)).
6. **Fall back when no han skill fits or the best fit is absent.** When no han skill matches an item's nature, the producer scans the installed skills and, if a non-han skill plausibly fits, suggests it in the breakdown as a low-confidence recommendation rather than assigning it, and leaves its autonomy not-unattended unless the operator declares otherwise ([D8](artifacts/decision-log.md#d8-non-han-skills-suggested-only-when-no-han-skill-fits)); if none fits, or the best-fit han skill is not installed, it records the item as a bare human item with implementation skill `none` and never substitutes `tdd`, because an unverifiable substitute would let the driver attempt work it cannot check. When an item fell back because its best-fit han skill is not installed, the producer keeps the recommended skill as a note on the item and prints an install recommendation at the end of the run, so the operator can install the plugin and re-run (or ask for those items to be re-derived) without any mid-run prompt ([D9](artifacts/decision-log.md#d9-uninstalled-best-fit-falls-back-to-bare-hitl)).
7. **Record, print, and write.** The producer records the implementation skill, the review, and the three signals on every item, prints them in the breakdown — each item marked driver-ready or needs-a-hand, with the derived fully-autonomous / needs-a-human label — alongside any low-confidence flags, non-han suggestions, not-installed notes, mismatch flags, and override-resolution notes, and writes the `work-items.md`. Its closing recommendation sorts the items into three groups: those the autonomous driver can build unattended today (implementation skill `tdd`, review `code-review`); those an operator runs by invoking the named skill(s) themselves — a fully-autonomous item whose combination the driver does not yet support, with no human judgment needed (for example `project-documentation` reviewed by `content-auditor`, a `guidance` step with review `none`, or a declared-autonomous user skill); and those that need a human (an interactive build, a human review, a pre-work decision, or a bare item) ([D10](artifacts/decision-log.md#trivial-decisions)).
8. **The driver dispatches per item, or refuses the whole run.** When the operator later runs the autonomous driver on the file, the driver validates at startup — before any branch or preview — that every item carries the implementation skill, the review, and the three signals, and computes from those signals whether each item is fully autonomous. It drives the file only when every item is fully autonomous *and* its skill-and-review combination is one the driver supports (today, `tdd` built and `code-review` reviewed); if any item needs a human, or is fully autonomous but of an unsupported combination, it refuses the whole run at startup, naming the offending items, rather than driving a partial set ([D5](artifacts/decision-log.md#d5-driver-drivability-is-computed-from-the-signals)). Otherwise it names each item's implementation skill and review in the plan preview and, per item, dispatches the recorded implementation skill to build (in both the initial build and each fix round) and the recorded review to review, preserving that skill's dispatch contract — for `tdd`, the observed test-failure-then-pass evidence requirement is unchanged ([D6](artifacts/decision-log.md#d6-per-item-fields-implementation-skill-review-and-autonomy-signals)). The per-phase signals are what a future human-in-the-loop driver reads to gate on a pre-work decision, run an unattended phase in a sub-agent, and route a human phase to the operator ([D4](artifacts/decision-log.md#d4-recorded-autonomy-signals-replace-the-afkhitl-type)).

## Alternate Flows and States

### The best-fit skill is a han skill that is not installed

- **Entry condition:** an item's deliverable nature best matches a han skill that is not installed in the current environment (for example a "build a new skill" item when `han-plugin-builder` is absent).
- **Sequence:** the producer records the item as a bare human item with implementation skill `none` (never a `tdd` substitute), keeps the recommended skill as a note on the item, and finishes writing the file so no work is lost ([D9](artifacts/decision-log.md#d9-uninstalled-best-fit-falls-back-to-bare-hitl)).
- **Exit:** at the end of the run the producer prints the recommendation for each such item (install the named plugin, then re-run `plan-work-items` — or ask for those items to be re-derived). The run does not pause for the operator; the bare items stand until the operator acts ([D9](artifacts/decision-log.md#d9-uninstalled-best-fit-falls-back-to-bare-hitl)).

### No han skill fits an item's nature

- **Entry condition:** an item's deliverable matches none of the han catalog's natures.
- **Sequence:** the producer scans the installed skills and, if a non-han skill plausibly fits, surfaces it in the breakdown as a low-confidence suggestion, leaves its autonomy not-unattended unless the operator declares otherwise, and does not assign it. If nothing plausibly fits, the item is recorded as a bare human item with implementation skill `none` ([D8](artifacts/decision-log.md#d8-non-han-skills-suggested-only-when-no-han-skill-fits)).
- **Exit:** the operator either adopts a suggestion by override (declaring its autonomy if it is drivable) or accepts the bare item.

### The operator overrides a skill, review, or a non-han skill's autonomy

- **Entry condition:** the operator names an implementation skill, review, or non-han-autonomy for a specific item, by invocation instruction or a pre-written marker.
- **Sequence:** the producer binds the override to an item by the operator's description, records the operator's choice, and recomputes the item's signals — re-deriving from a han skill, or taking the declaration for a non-han skill. It flags a mismatch when the override's skill does not match the item's nature, records the override as a recommendation but leaves the item bare when the named skill is not installed, and reports how each override resolved ([D7](artifacts/decision-log.md#d7-overrides-by-invocation-instruction-and-pre-written-marker)).
- **Exit:** the overridden choice, the recomputed signals, the derived label, its drivability marker, and any mismatch or resolution note appear on the item and in the breakdown.

## Edge Cases and Failure Modes

| Condition | Required Behavior |
|-----------|-------------------|
| An item's deliverable nature is ambiguous (uncertain whether code or documentation) | The producer selects the best fit and flags it low-confidence in the breakdown; it does not default to `tdd` for a possibly non-testable item ([D3](artifacts/decision-log.md#d3-tdd-only-for-testable-deliverables)). |
| An item's deliverable is definitively two natures at once (for example, code plus its runbook) | The producer splits it into separate vertical-slice items, one per deliverable and skill; when it cannot be cleanly split, it records the dominant skill and flags the uncovered nature so the second deliverable is never silently dropped ([D2](artifacts/decision-log.md#d2-deliverable-nature-decision-tree-and-skill-catalog)). |
| An override names `tdd` for a non-testable deliverable | Honored (operator authority) but flagged as a mismatch; if the operator hands such an item to the driver, the driver's `tdd` report contract may halt it mid-run when no test evidence appears — the flag warns of exactly this ([D3](artifacts/decision-log.md#d3-tdd-only-for-testable-deliverables), [D7](artifacts/decision-log.md#d7-overrides-by-invocation-instruction-and-pre-written-marker)). |
| An override names a han skill that is semantically wrong for the item but installed | Honored and flagged as a mismatch; driver-readiness is judged by matching the item's recorded combination against the driver's supported combination (`tdd` + `code-review`), not merely by whether it is fully autonomous, so a mismatched combination is marked needs-a-hand ([D5](artifacts/decision-log.md#d5-driver-drivability-is-computed-from-the-signals), [D7](artifacts/decision-log.md#d7-overrides-by-invocation-instruction-and-pre-written-marker)). |
| An override names a skill that is not installed | Treated like an uninstalled best-fit: the item becomes a bare human item (implementation skill `none`) with the override kept as a recommendation and printed at the end — a distinct outcome from an honored-but-flagged mismatch, and named as such ([D9](artifacts/decision-log.md#d9-uninstalled-best-fit-falls-back-to-bare-hitl)). |
| A user-defined skill is used but its autonomy is not declared | The producer cannot infer a non-han skill's behavior, so it records the phase as not-unattended; the item needs a human unless the operator declares the phase autonomous ([D8](artifacts/decision-log.md#d8-non-han-skills-suggested-only-when-no-han-skill-fits)). |
| A user-defined skill is declared autonomous by the operator | The producer records the declared autonomy, so the item can be fully autonomous; it is still not driver-drivable today (the current driver supports only the `tdd` + `code-review` combination) and lands in the run-the-skill-yourself group, but the recorded signal lets a future driver run it ([D4](artifacts/decision-log.md#d4-recorded-autonomy-signals-replace-the-afkhitl-type), [D8](artifacts/decision-log.md#d8-non-han-skills-suggested-only-when-no-han-skill-fits)). |
| An autonomous-build item is given a review that requires a human (for example `tdd` built but reviewed by a `human read`) | The item needs a human (a human must review before merge); it is sorted into the needs-a-human group and the driver refuses it. The implementation-skill and review fields plus the two autonomy signals still record that the build is autonomous and the review is not, so a future human-in-the-loop driver can build it in a sub-agent and route the review to the human ([D4](artifacts/decision-log.md#d4-recorded-autonomy-signals-replace-the-afkhitl-type)). |
| An item needs a human decision before work starts, but its build and review are both autonomous | The pre-work-decision signal marks it needs-a-human; the driver refuses it. Because the build and review signals still record both phases as autonomous, a future driver can resolve the gate with the operator and then run both phases in sub-agents ([D4](artifacts/decision-log.md#d4-recorded-autonomy-signals-replace-the-afkhitl-type)). |
| A `guidance` (vendoring) item has no applicable automated review | Its review is recorded `none`; the item is fully autonomous (autonomous build, no review, no gate) and lands in the run-the-skill-yourself group rather than being left with an undefined review ([D2](artifacts/decision-log.md#d2-deliverable-nature-decision-tree-and-skill-catalog), [D6](artifacts/decision-log.md#d6-per-item-fields-implementation-skill-review-and-autonomy-signals)). |
| A work-items file produced before this feature (items carry the old `Type` marker, not the new fields) is handed to the driver | The driver refuses at startup, naming the missing fields and directing the operator to re-run `plan-work-items`; because the driver no longer reads `Type`, the producer and driver companion changes ship together ([D6](artifacts/decision-log.md#d6-per-item-fields-implementation-skill-review-and-autonomy-signals)). |
| A file contains any item that is not fully autonomous, or is fully autonomous but of an unsupported combination | The driver refuses the whole run at startup (fail-fast, before any branch or commit), naming the offending items, rather than driving a partial set — consistent with the core loop's all-or-nothing startup posture and avoiding running an item whose dependency was skipped ([D5](artifacts/decision-log.md#d5-driver-drivability-is-computed-from-the-signals)). |

## User Interactions

- **Affordances:** the operator can override the implementation skill, the review, and a non-han skill's declared autonomy for a named item, either as an instruction in the invocation ("use `skill-builder` for the new-skill item"; "my `deploy-notes` skill has an autonomous build") or as a per-item marker left in the source plan or context, which the producer reads read-only. Because item identifiers are assigned during drafting, an override names its target by description; the producer binds it and reports the binding ([D7](artifacts/decision-log.md#d7-overrides-by-invocation-instruction-and-pre-written-marker)).
- **Feedback:** the breakdown prints, per item, the implementation skill, the review, the three autonomy signals, the derived fully-autonomous / needs-a-human label, and a driver-ready / needs-a-hand marker, plus low-confidence flags, non-han suggestions, not-installed notes, override-mismatch flags, and how each override resolved. Each flag names its remedy (how to override). The closing recommendation groups items into driver-ready, run-the-skill-yourself, and needs-a-human ([D10](artifacts/decision-log.md#trivial-decisions)).
- **Error states:** the producer runs autonomously end to end as today, with no added prompt; when items fell back to bare human items because a best-fit skill is not installed, it prints the install recommendation at the end and exits ([D9](artifacts/decision-log.md#d9-uninstalled-best-fit-falls-back-to-bare-hitl)). Driver-side refusals name the offending items, the reason, and the remedy, consistent with the driver's existing startup refusals.

## Out of Scope

- **Building the human-in-the-loop driver that consumes the signals.** This feature records the per-phase autonomy and pre-work-decision signals; the driver that gates on a decision, runs an unattended phase in a sub-agent, and foregrounds a human phase is the core loop's separately deferred HITL path.
- **Expanding the current driver beyond the `tdd` + `code-review` combination.** Even a fully-autonomous item of another combination (a declared-autonomous user skill, or `project-documentation` + `content-auditor`) is refused today; the field records it for a future driver.
- **Changing the build and review skills themselves.** No changes to `tdd`, `code-review`, `skill-builder`, and so on; the producer (`plan-work-items`) and the driver (`implement-work-items`) are the two skills this feature changes.
- **Auto-installing missing plugins.** The producer prints the recommendation; installing is the operator's step.
- **Reliably classifying arbitrary non-han skills.** Non-han suggestions are best-effort and low-confidence; a non-han skill's autonomy comes from the operator's declaration, not inference.
- **The override-marker grammar, the autonomy-declaration syntax, and the installed-skill detection mechanism.** These are implementation concerns for `plan-implementation`; the spec fixes only the behavior.

## Deferred (YAGNI)

### The human-in-the-loop driver that consumes the autonomy signals

- **Why deferred:** this feature records the per-phase autonomy and pre-work-decision signals so a driver can sub-agent an unattended phase, foreground a human phase, and gate on a decision — but building that driver is the core loop's deferred HITL path, with its own decision gate, foreground invocation, and checkpoint. Recording the signals now is justified because the HITL driver is named upcoming work (a direct dependency), not because the mixed execution belongs in this feature.
- **Reopen when:** the human-in-the-loop driver is planned (the core loop's HITL follow-on).
- **Source:** conversation (operator direction — this feature is the groundwork); reference plan's deferred "Human-in-the-loop items and interactive-skill items."

### Expanding the driver's supported combinations beyond `tdd` + `code-review`

- **Why deferred:** `tdd` is the only build skill that is both autonomous and test-verifiable through the driver's `tdd` report contract, and `code-review` is the right review for the code it produces, so that pairing is the only combination the current driver can build, verify, and gate. A fully-autonomous item of another combination (a declared-autonomous user skill, `project-documentation` + `content-auditor`) is recorded for a future driver but refused today.
- **Reopen when:** a verifiable dispatch contract exists for a second autonomous build-and-review combination.
- **Source:** conversation ([D5](artifacts/decision-log.md#d5-driver-drivability-is-computed-from-the-signals)).

### Reliable, machine-readable classification of non-han skills

- **Why deferred:** the producer cannot reliably tell whether an arbitrary installed skill is code-producing or interactive, so it only suggests non-han skills at low confidence and takes autonomy from the operator's declaration rather than inferring it.
- **Reopen when:** installed skills expose a machine-readable capability declaration the producer can trust.
- **Source:** conversation ([D8](artifacts/decision-log.md#d8-non-han-skills-suggested-only-when-no-han-skill-fits)).

### Auto-installing a missing best-fit plugin, and an in-session re-derive prompt

- **Why deferred:** the not-installed fallback prints the recommendation and lets the operator install and re-run; both auto-installing and an in-session prompt-and-re-derive add environment-mutation or interaction surface with no stated need, and an in-session prompt would break the producer's autonomous, never-gate identity.
- **Reopen when:** operators routinely hit uninstalled best-fits and ask for one-step install or in-session re-derive.
